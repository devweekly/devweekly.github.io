# Article De-AI

## Goal

把 AI 起草的中文技术文章编辑成更自然的技术文章。

目标不是“写得更花”，也不是把文章改成另一种风格，而是：

> **保留作者原来的观点和证据，只去掉机械、重复、模板化和过度加工的表达。**

核心原则：

> **可以重写表达，不可以偷换观点。**
>
> **可以压缩重复，不可以删除有效信息。**
>
> **可以降低语气，不可以降低事实准确性。**

---

# 1. 什么可以改

允许修改：

* 句子表达
* 句子顺序
* 段落合并
* 段落拆分
* 连接词
* 标点
* 加粗
* 引用块
* 列表
* 重复总结
* 机械排比
* 模板化小标题
* 同义词重复
* 不自然的中英混排
* AI 腔的结论句

允许进行轻度重写，只要不改变原意。

例如：

原文：

> 这其实是一个非常重要的问题。
> 更重要的是，这个问题值得我们深入思考。

可以改为：

> 这里真正需要解决的是……

---

# 2. 什么绝对不能改

以下内容属于语义保护区。

不得修改：

### 2.1 核心观点

例如：

> BPMN 与 Agent 不应该二选一。

不能改成：

> Agent 比 BPMN 更先进。

---

### 2.2 因果关系

原文：

> A 导致 B。

不能改成：

> A 与 B 有关。

也不能把：

> 可能导致

改成：

> 导致。

---

### 2.3 证据强度

严格保持：

* 可能
* 通常
* 部分
* 当前
* 已经
* 官方明确
* 作者认为
* 研究发现
* 案例显示

不能把：

> 一个案例说明……

升级成：

> 这证明行业未来一定会……

同样不能把明确事实弱化成猜测。

---

### 2.4 数据与数字

不得修改：

* 百分比
* 金额
* 日期
* 数量
* 版本号
* benchmark
* latency
* token
* 性能数字
* 论文编号

---

### 2.5 技术事实

不得擅自改变：

* 产品名称
* API 名称
* 架构组件
* 协议
* 技术术语
* 模型名称
* 版本
* 开源项目名称

---

### 2.6 引用和来源

不得删除或改写：

* 引用
* reference
* URL
* citation marker
* footnote
* reference definition

---

# 3. AI 味处理规则

## 3.1 碎段

连续多个只有一句话、甚至几个词的段落：

```text
这很重要。

更重要的是：

这是未来方向。

所以：
```

合并成自然段。

不要为了“短句感”保留大量单句成段。

---

## 3.2 机械排比

降低以下模板：

```text
首先……
其次……
最后……

一方面……
另一方面……

第一……
第二……
第三……

不是……
而是……

不仅……
而且……

这不是……
这也不是……
真正的是……
```

不是禁止使用，而是：

> **连续使用超过 2 次时重新组织。**

特别是：

> “不是 A，而是 B”

属于常见有效表达，可以保留，但不要连续重复成整篇文章的固定句式。

---

## 3.3 模板化连接词

重点检查：

* 首先
* 其次
* 最后
* 更重要的是
* 值得注意的是
* 需要强调的是
* 换句话说
* 也就是说
* 从这个角度来看
* 进一步来看
* 归根结底
* 本质上
* 毫无疑问
* 显然
* 事实上
* 特别值得注意的是
* 一个非常重要的问题是
* 一个容易被忽略的问题是
* 这里必须强调一点
* 需要特别说明的是

处理原则：

> 删除、替换或直接并入句子。

不要机械地把每个连接词换成另一个同义词。

例如：

> 值得注意的是，Snowflake……

可以直接：

> Snowflake……

---

# 4. 重复总结

识别以下模式：

```text
段落总结
↓
章节总结
↓
Part 总结
↓
全文总结
```

如果后面的总结只是重复前面的内容：

> 删除重复表述，保留信息密度最高的一次。

### 例子

前文：

> BPMN 保证流程确定性，Agent 负责认知任务。

后文：

> 综上所述，BPMN 和 Agent 各自承担不同职责，因此 BPMN 保证确定性、Agent 负责认知任务。

第二句属于重复。

保留第一处，删除第二处。

---

# 5. 同义反复

处理：

```text
非常重要
十分重要
极其重要
尤其重要
至关重要
```

连续出现时，只保留自然的一次。

同样处理：

```text
核心问题
根本问题
关键问题
真正问题
```

如果其实指同一件事，不要反复换词制造“新观点”。

---

# 6. 机械强调

减少：

```text
真正
非常
尤其
必须
关键
核心
根本
本质
显然
实际上
```

原则不是全部删除，而是：

> **只有强调确实改变语义时才保留。**

例如：

> Agent 不能绕过权限系统。

这里“不能”本身已经足够。

不要写成：

> Agent **绝对不能**绕过统一的身份、权限、工具和审计边界。

除非原始论点确实要求这种强约束。

---

# 7. “金句”降级

以下模式需要重点检查：

```markdown
> 这就是未来。
```

```markdown
> 真正的问题不是 A，而是 B。
```

```markdown
> 这才是真正的 AI-native architecture。
```

不是全部删除，而是：

> 只有真正承担全文中心论点的 1～3 处保留引用块。

其他并入正常段落。

---

# 8. 加粗规则

默认不使用整句加粗。

优先：

```markdown
**Agent Task Contract**
```

而不是：

```markdown
**Agent Task Contract 是整个架构最重要的核心抽象。**
```

全文建议：

* 关键术语：可以加粗
* 小段标题：正常标题
* 完整观点：默认不加粗
* 每节最多 1～2 个强调点

不要让每个段落都有粗体。

---

# 9. 列表规则

列表不是 AI 味的根源，但 AI 经常把所有东西都拆成列表。

### 保留列表

当项目确实可以独立理解：

* Policy
* Identity
* Audit
* Evidence

### 改成正文

当它们其实构成一个连续句：

> Agent 负责 reasoning、tool use、context 和 planning。

不要写成：

```text
- reasoning
- tool use
- context
- planning
```

### 改成表格

当每一项都有对应属性：

| Layer    | Responsibility |
| -------- | -------------- |
| Workflow | Process state  |
| Agent    | Reasoning      |
| Policy   | Authority      |

---

# 10. 对仗句检查

重点检查连续结构：

```text
A 负责……
B 负责……

A 解决……
B 解决……

A 不是……
B 不是……

A 是……
B 是……
```

如果对仗超过 3 组：

> 优先合并成表格，或者改成普通段落。

不要为了“节奏感”维持大段机械对仗。

---

# 11. “定义 → 再解释 → 再总结”压缩

AI 文章经常出现：

```text
定义：

解释：

换句话说：

因此：

这意味着：

最终：
```

如果这些内容表达同一件事，只保留：

> 定义 + 必要解释。

不要重复总结五遍。

---

# 12. 技术文章中的自然表达

优先：

> 具体、直接、少修饰。

例如：

原文：

> 在这个背景下，我们可以进一步看到，一个非常值得关注的现象是，Workflow 的角色正在发生非常明显的变化。

建议：

> 这里发生了一个变化：Workflow 的角色正在改变。

---

原文：

> 这实际上也是为什么我们不能简单地认为 Agent 出现以后 BPMN 就已经过时了。

建议：

> 因此，不能简单认为 Agent 出现后 BPMN 就过时了。

---

原文：

> 这个方向其实非常值得我们进一步关注和深入研究。

建议：

> 这个方向值得继续观察。

---

# 13. 防止“AI 论文腔”

重点降低：

```text
值得注意的是
需要指出的是
需要强调的是
从某种意义上来说
在某种程度上
可以看到
不难发现
由此可见
这意味着
这进一步说明
这揭示了
这反映出
这实际上说明
```

原则：

> 如果删除后句子仍然成立，就删除。

例如：

> 由此可见，BPMN 仍然有价值。

改成：

> BPMN 仍然有价值。

---

# 14. 防止“过度宏大结论”

这是技术文章最重要的一条。

检查：

```text
一个案例
↓
一个行业趋势
↓
一个未来预测
```

如果原文只有前两层证据，不允许自动升级第三层。

例如：

> AWS 的这个案例说明 Agent 可以参与合规审查。

不能自动改成：

> 这说明未来金融合规将全面由 Agent 驱动。

---

# 15. 保留作者的不确定性

不要把：

```text
可能
大概率
倾向于
目前来看
一种可能的方向
值得观察
还没有定论
```

改成：

```text
必然
已经
一定
明确
未来将
```

同样，不要为了“显得专业”削弱原本明确的结论。

---

# 16. 处理重复术语

建立全文术语表。

例如全文第一次定义：

> Agent Runtime

后续默认统一写：

> Agent Runtime

不要交替改成：

* Agent Execution Runtime
* Agent Runtime Layer
* Agent Execution Layer
* Agent Engine

除非它们实际上指不同概念。

### 术语表原则

第一次出现：

> 中文术语（English）

后续：

> 优先使用统一短名称。

---

# 17. 英文与中文混排

技术术语保持原英文，不为了“中文化”破坏术语准确性。

例如：

> Agent Runtime、Workflow Runtime、Durable Execution

可以保留。

但避免：

> Agent Runtime 是一个非常 important 的 execution layer。

除非原文确实有特殊表达。

---

# 18. 标题规则

默认：

> **不修改标题文字与层级。**

但标题内部如果存在纯 AI 模板词，例如：

```text
为什么这件事非常重要？
值得深入思考的未来方向
最终结论：我们到底应该怎么做？
```

是否修改必须单独授权。

本 Skill 默认：

> **不修改标题。**

---

# 19. 代码块与结构化内容

以下内容默认完全不改：

* mermaid
* yaml
* json
* code
* sql
* shell
* xml

包括：

* 节点名称
* 字段
* 缩进
* 版本号
* API 名称
* 注释
* Mermaid 结构

除非用户明确要求同时执行对应的代码 / Mermaid Skill。

---

# 20. 与其他文章 Skill 的职责边界

本 Skill 不负责：

* Mermaid 重构
* ASCII → Mermaid
* 技术事实核查
* 引用核查
* 架构设计
* 内容补充
* 重新组织文章观点

例如发现：

> Mermaid 图重复。

本 Skill 默认不修改图，只避免文字围绕该图反复解释。

如果需要图优化，应调用：

> `text-to-mermaid`

如果需要事实核查，应使用专门的 research / fact-check Skill。

---

# 21. 全局一致性检查

局部编辑完成后，必须进行第二遍全文检查。

重点检查：

### 21.1 术语一致

同一个概念不要出现多个叫法。

### 21.2 语气一致

不要前面：

> 可能

后面：

> 必然

### 21.3 结论一致

不要前面：

> Agent 不应该决定 Workflow。

后面：

> Agent 可以动态决定 Workflow。

除非文章明确解释这是不同上下文。

### 21.4 重复观点

检查同一观点是否出现：

* 开头
* 小节
* Part 总结
* 结尾

超过两次就重新判断。

---

# 22. 大文件策略

超过约 1500 行：

1. 按 `#` / `##` 标题边界切块。
2. 不切断代码块。
3. 不切断引用块。
4. 不切断表格。
5. 不切断连续段落。
6. 每块独立去 AI 味。
7. 最后必须进行一次全局一致性检查。

### 特别注意

不要让不同块独立决定：

* 同一术语的叫法
* 同一产品的简称
* 同一观点的语气
* 同一核心结论的表达

处理前先建立：

```text
Global Terminology
Global Claims
Global Tone
```

---

# 23. 修改前后必须执行的语义检查

不能只做 diff。

需要验证：

### Claim preservation

每一个重要命题仍然存在。

### Evidence preservation

每一个数据、案例、论文、引用仍然存在。

### Qualification preservation

“可能 / 通常 / 当前 / 部分 / 预计”等限定没有消失。

### Causal preservation

原因、结果、条件没有改变。

### Scope preservation

“金融领域”不能被改成“整个企业”。

“当前实践”不能被改成“未来趋势”。

---

# 24. 格式检查

检查：

1. Heading 数量、文字、层级不变。
2. Frontmatter 不变。
3. Code fence 数量和类型不变。
4. Mermaid 数量不变。
5. YAML / JSON 数量不变。
6. Markdown table 数量不变。
7. Reference 定义完整。
8. URL 完整。

---

# 25. De-AI 检查项

最终检查以下信号：

* 是否连续出现多个单句段落？
* 是否每节都有粗体金句？
* 是否每节都有 `>`？
* 是否大量使用“首先 / 其次 / 最后”？
* 是否大量使用“值得注意的是”？
* 是否连续使用“不是 A，而是 B”？
* 是否每隔几段就出现“这意味着”？
* 是否反复说“非常重要 / 关键 / 核心”？
* 是否同一个观点被反复总结？
* 是否出现明显的“定义 → 换句话说 → 这意味着 → 由此可见”链条？
* 是否有大量三项或四项对仗？
* 是否把一个案例扩大成行业结论？
* 是否把作者的“可能”改成“必然”？
* 是否为了显得专业而添加没有信息量的句子？

---

# 27. 最重要的总原则

> **“去 AI 味”不是把文字变得更口语，也不是把所有 AI 常用词替换成同义词。**
>
> **真正要去掉的是：机械结构、重复强调、模板化连接词、无意义总结、过度对仗和证据强度与结论强度不匹配。**
>
> **文章的观点、证据、限定条件和作者真正想表达的判断必须保持不变。**
