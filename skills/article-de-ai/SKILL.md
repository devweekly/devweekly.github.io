# Article De-AI

## Goal

把 AI 起草的中文技术文章编辑成更自然的技术文章。

目标不是“写得更花”，也不是把文章改成另一种风格，而是：

> **保留作者原来的观点和证据，只去掉机械、重复、模板化和过度加工的表达。**

核心原则：

> **可以重写表达，不可以偷换观点。**
>
> **可以压缩重复，不可以删除有效信息。**
>
> **可以降低语气，不可以降低事实准确性。**

---

# 1. 什么可以改

允许修改：

* 句子表达
* 句子顺序
* 段落合并
* 段落拆分
* 连接词
* 标点
* 加粗
* 引用块
* 列表
* 重复总结
* 机械排比
* 模板化小标题
* 同义词重复
* 不自然的中英混排
* AI 腔的结论句

允许进行轻度重写，只要不改变原意。

例如：

原文：

> 这其实是一个非常重要的问题。
> 更重要的是，这个问题值得我们深入思考。

可以改为：

> 这里真正需要解决的是……

---

# 2. 什么绝对不能改

以下内容属于语义保护区。

不得修改：

### 2.1 核心观点

例如：

> BPMN 与 Agent 不应该二选一。

不能改成：

> Agent 比 BPMN 更先进。

---

### 2.2 因果关系

原文：

> A 导致 B。

不能改成：

> A 与 B 有关。

也不能把：

> 可能导致

改成：

> 导致。

---

### 2.3 证据强度

严格保持：

* 可能
* 通常
* 部分
* 当前
* 已经
* 官方明确
* 作者认为
* 研究发现
* 案例显示

不能把：

> 一个案例说明……

升级成：

> 这证明行业未来一定会……

同样不能把明确事实弱化成猜测。

---

### 2.4 数据与数字

不得修改：

* 百分比
* 金额
* 日期
* 数量
* 版本号
* benchmark
* latency
* token
* 性能数字
* 论文编号

---

### 2.5 技术事实

不得擅自改变：

* 产品名称
* API 名称
* 架构组件
* 协议
* 技术术语
* 模型名称
* 版本
* 开源项目名称

---

### 2.6 引用和来源

不得删除或改写：

* 引用
* reference
* URL
* citation marker
* footnote
* reference definition

---

# 3. AI 味处理规则

## 3.1 碎段

连续多个只有一句话、甚至几个词的段落：

```text
这很重要。

更重要的是：

这是未来方向。

所以：
```

合并成自然段。

不要为了“短句感”保留大量单句成段。

---

## 3.2 机械排比

降低以下模板：

```text
首先……
其次……
最后……

一方面……
另一方面……

第一……
第二……
第三……

不是……
而是……

不仅……
而且……

这不是……
这也不是……
真正的是……
```

不是禁止使用，而是：

> **连续使用超过 2 次时重新组织。**

特别是：

> “不是 A，而是 B”

属于常见有效表达，可以保留，但不要连续重复成整篇文章的固定句式。

---

## 3.3 模板化连接词

重点检查：

* 首先
* 其次
* 最后
* 更重要的是
* 值得注意的是
* 需要强调的是
* 换句话说
* 也就是说
* 从这个角度来看
* 进一步来看
* 归根结底
* 本质上
* 毫无疑问
* 显然
* 事实上
* 特别值得注意的是
* 一个非常重要的问题是
* 一个容易被忽略的问题是
* 这里必须强调一点
* 需要特别说明的是

处理原则：

> 删除、替换或直接并入句子。

不要机械地把每个连接词换成另一个同义词。

例如：

> 值得注意的是，Snowflake……

可以直接：

> Snowflake……

---

# 4. 重复总结

识别以下模式：

```text
段落总结
↓
章节总结
↓
Part 总结
↓
全文总结
```

如果后面的总结只是重复前面的内容：

> 删除重复表述，保留信息密度最高的一次。

### 例子

前文：

> BPMN 保证流程确定性，Agent 负责认知任务。

后文：

> 综上所述，BPMN 和 Agent 各自承担不同职责，因此 BPMN 保证确定性、Agent 负责认知任务。

第二句属于重复。

保留第一处，删除第二处。

---

# 5. 同义反复

处理：

```text
非常重要
十分重要
极其重要
尤其重要
至关重要
```

连续出现时，只保留自然的一次。

同样处理：

```text
核心问题
根本问题
关键问题
真正问题
```

如果其实指同一件事，不要反复换词制造“新观点”。

---

# 6. 机械强调

减少：

```text
真正
非常
尤其
必须
关键
核心
根本
本质
显然
实际上
```

原则不是全部删除，而是：

> **只有强调确实改变语义时才保留。**

例如：

> Agent 不能绕过权限系统。

这里“不能”本身已经足够。

不要写成：

> Agent **绝对不能**绕过统一的身份、权限、工具和审计边界。

除非原始论点确实要求这种强约束。

---

# 7. “金句”降级

以下模式需要重点检查：

```markdown
> 这就是未来。
```

```markdown
> 真正的问题不是 A，而是 B。
```

```markdown
> 这才是真正的 AI-native architecture。
```

不是全部删除，而是：

> 只有真正承担全文中心论点的 1～3 处保留引用块。

其他并入正常段落。

---

# 8. 加粗规则

默认不使用整句加粗。

优先：

```markdown
**Agent Task Contract**
```

而不是：

```markdown
**Agent Task Contract 是整个架构最重要的核心抽象。**
```

全文建议：

* 关键术语：可以加粗
* 小段标题：正常标题
* 完整观点：默认不加粗
* 每节最多 1～2 个强调点

不要让每个段落都有粗体。

---

# 9. 列表规则

列表不是 AI 味的根源，但 AI 经常把所有东西都拆成列表。

### 保留列表

当项目确实可以独立理解：

* Policy
* Identity
* Audit
* Evidence

### 改成正文

当它们其实构成一个连续句：

> Agent 负责 reasoning、tool use、context 和 planning。

不要写成：

```text
- reasoning
- tool use
- context
- planning
```

### 改成表格

当每一项都有对应属性：

| Layer    | Responsibility |
| -------- | -------------- |
| Workflow | Process state  |
| Agent    | Reasoning      |
| Policy   | Authority      |

---

# 10. 对仗句检查

重点检查连续结构：

```text
A 负责……
B 负责……

A 解决……
B 解决……

A 不是……
B 不是……

A 是……
B 是……
```

如果对仗超过 3 组：

> 优先合并成表格，或者改成普通段落。

不要为了“节奏感”维持大段机械对仗。

---

# 11. “定义 → 再解释 → 再总结”压缩

AI 文章经常出现：

```text
定义：

解释：

换句话说：

因此：

这意味着：

最终：
```

如果这些内容表达同一件事，只保留：

> 定义 + 必要解释。

不要重复总结五遍。

---

# 12. 技术文章中的自然表达

优先：

> 具体、直接、少修饰。

例如：

原文：

> 在这个背景下，我们可以进一步看到，一个非常值得关注的现象是，Workflow 的角色正在发生非常明显的变化。

建议：

> 这里发生了一个变化：Workflow 的角色正在改变。

---

原文：

> 这实际上也是为什么我们不能简单地认为 Agent 出现以后 BPMN 就已经过时了。

建议：

> 因此，不能简单认为 Agent 出现后 BPMN 就过时了。

---

原文：

> 这个方向其实非常值得我们进一步关注和深入研究。

建议：

> 这个方向值得继续观察。

---

# 13. 防止“AI 论文腔”

重点降低：

```text
值得注意的是
需要指出的是
需要强调的是
从某种意义上来说
在某种程度上
可以看到
不难发现
由此可见
这意味着
这进一步说明
这揭示了
这反映出
这实际上说明
```

原则：

> 如果删除后句子仍然成立，就删除。

例如：

> 由此可见，BPMN 仍然有价值。

改成：

> BPMN 仍然有价值。

---

# 14. 防止“过度宏大结论”

这是技术文章最重要的一条。

检查：

```text
一个案例
↓
一个行业趋势
↓
一个未来预测
```

如果原文只有前两层证据，不允许自动升级第三层。

例如：

> AWS 的这个案例说明 Agent 可以参与合规审查。

不能自动改成：

> 这说明未来金融合规将全面由 Agent 驱动。

---

# 15. 保留作者的不确定性

不要把：

```text
可能
大概率
倾向于
目前来看
一种可能的方向
值得观察
还没有定论
```

改成：

```text
必然
已经
一定
明确
未来将
```

同样，不要为了“显得专业”削弱原本明确的结论。

---

# 16. 处理重复术语

建立全文术语表。

例如全文第一次定义：

> Agent Runtime

后续默认统一写：

> Agent Runtime

不要交替改成：

* Agent Execution Runtime
* Agent Runtime Layer
* Agent Execution Layer
* Agent Engine

除非它们实际上指不同概念。

### 术语表原则

第一次出现：

> 中文术语（English）

后续：

> 优先使用统一短名称。

---

# 17. 英文与中文混排

技术术语保持原英文，不为了“中文化”破坏术语准确性。

例如：

> Agent Runtime、Workflow Runtime、Durable Execution

可以保留。

但避免：

> Agent Runtime 是一个非常 important 的 execution layer。

除非原文确实有特殊表达。

---

# 18. 标题规则

默认：

> **不修改标题文字与层级。**

但标题内部如果存在纯 AI 模板词，例如：

```text
为什么这件事非常重要？
值得深入思考的未来方向
最终结论：我们到底应该怎么做？
```

是否修改必须单独授权。

本 Skill 默认：

> **不修改标题。**

---

# 19. 代码块与结构化内容

以下内容默认完全不改：

* mermaid
* yaml
* json
* code
* sql
* shell
* xml

包括：

* 节点名称
* 字段
* 缩进
* 版本号
* API 名称
* 注释
* Mermaid 结构

除非用户明确要求同时执行对应的代码 / Mermaid Skill。

---

# 20. 与其他文章 Skill 的职责边界

本 Skill 不负责：

* Mermaid 重构
* ASCII → Mermaid
* 技术事实核查
* 引用核查
* 架构设计
* 内容补充
* 重新组织文章观点

例如发现：

> Mermaid 图重复。

本 Skill 默认不修改图，只避免文字围绕该图反复解释。

如果需要图优化，应调用：

> `text-to-mermaid`

如果需要事实核查，应使用专门的 research / fact-check Skill。

---

# 21. 全局一致性检查

局部编辑完成后，必须进行第二遍全文检查。

重点检查：

### 21.1 术语一致

同一个概念不要出现多个叫法。

### 21.2 语气一致

不要前面：

> 可能

后面：

> 必然

### 21.3 结论一致

不要前面：

> Agent 不应该决定 Workflow。

后面：

> Agent 可以动态决定 Workflow。

除非文章明确解释这是不同上下文。

### 21.4 重复观点

检查同一观点是否出现：

* 开头
* 小节
* Part 总结
* 结尾

超过两次就重新判断。

---

# 22. 大文件策略

超过约 1500 行：

1. 按 `#` / `##` 标题边界切块。
2. 不切断代码块。
3. 不切断引用块。
4. 不切断表格。
5. 不切断连续段落。
6. 每块独立去 AI 味。
7. 最后必须进行一次全局一致性检查。

### 特别注意

不要让不同块独立决定：

* 同一术语的叫法
* 同一产品的简称
* 同一观点的语气
* 同一核心结论的表达

处理前先建立：

```text
Global Terminology
Global Claims
Global Tone
```

---

# 23. 修改前后必须执行的语义检查

不能只做 diff。

需要验证：

### Claim preservation

每一个重要命题仍然存在。

### Evidence preservation

每一个数据、案例、论文、引用仍然存在。

### Qualification preservation

“可能 / 通常 / 当前 / 部分 / 预计”等限定没有消失。

### Causal preservation

原因、结果、条件没有改变。

### Scope preservation

“金融领域”不能被改成“整个企业”。

“当前实践”不能被改成“未来趋势”。

---

# 24. 格式检查

检查：

1. Heading 数量、文字、层级不变。
2. Frontmatter 不变。
3. Code fence 数量和类型不变。
4. Mermaid 数量不变。
5. YAML / JSON 数量不变。
6. Markdown table 数量不变。
7. Reference 定义完整。
8. URL 完整。

---

# 25. De-AI 检查项

最终检查以下信号：

* 是否连续出现多个单句段落？
* 是否每节都有粗体金句？
* 是否每节都有 `>`？
* 是否大量使用“首先 / 其次 / 最后”？
* 是否大量使用“值得注意的是”？
* 是否连续使用“不是 A，而是 B”？
* 是否每隔几段就出现“这意味着”？
* 是否反复说“非常重要 / 关键 / 核心”？
* 是否同一个观点被反复总结？
* 是否出现明显的“定义 → 换句话说 → 这意味着 → 由此可见”链条？
* 是否有大量三项或四项对仗？
* 是否把一个案例扩大成行业结论？
* 是否把作者的“可能”改成“必然”？
* 是否为了显得专业而添加没有信息量的句子？

# 27. 对话稿转成稿：剥离对话与附录化

第 1–26 节处理的是**语言层**的 AI 味。这一节处理**文档形态层**的 AI 味：稿件是作者与 AI 一轮轮对话攒出来的，正文里混着对话句、起草过程语和方法说明。这部分不剥掉，文字再干净也不像成稿。

顺序固定：

> **先做形态剥离（本节），再做语言 de-AI（第 1–26 节）。**
> 反过来做，后面会反复打磨一批最终要被删掉的句子。

适用范围不限清单：报告、方案、周报、评审文档都适用同一套判据。

---

## 27.1 三类非交付内容与处置

| 类型 | 典型句 | 处置 |
| --- | --- | --- |
| 对话开场 / 应答 | 「可以。基于你们现在的实际架构，…」「这样改可以吗？」「如不合预期我改」 | **删** |
| 起草过程语 | 「这一块是上一版明显不够重视的地方」「review 草稿在…重复用了 289」 | **删**（版本差异集中收进一个附录小节） |
| 方法 / 框架 / 评分 / 使用说明 | 「评审框架」「评分板」「与 X 标准的对应关系」 | **搬附录**，正文只留实体内容（清单 / 论断 / 数据 / 证据） |

判据只有一条，用来避免过度删除：

> 句子的主语是**起草过程**或**对方的原话** → 是对话，删。
> 句子的主语是**事实、标准、平台、技术** → 是正文，留（即使写成「你们」也留 —— 那是顾问语气，不是对话）。

混血句（既有对话又有事实）**不要整句删**，改写成中性事实句：

```text
原文：这一项上一版也明显不足：不是「有没有 HITL」，而是 **Human 是否可能被 Agent 操纵**。
改为：本组检查的不是「有没有 HITL」，而是 **Human 是否可能被 Agent 操纵**。
```

同理，导语里带「我」的句子改为无主语祈使句：「我会要求团队现场回答」→「应要求团队现场回答」。

---

## 27.2 目标骨架

正文只放实体，方法说明一律后置。以清单类文档为例（落地案例：`temp/agent研究checklist.md`，1729 → 1716 行）：

```text
# <标题>                                + 极短导语：依据 / 规模 / 指向附录
# 一、Checklist 主表（P01–P14，N 项）      ← 原 `# P01` 降 H2，`## P01.1` 降 H3
# 二、Architecture Invariants
# 附录 A — 上一版保留项（独立编号 A01..，不计入主表）
# 附录 B — 评审框架与说明（B.1 三层结构 … B.9 版本差异）
# 参考
```

三个要点：

1. **加一层包装 H1**（「主表」），把原来一堆并列 H1 收进去，层级立刻清晰；正文由「标题 + 内容」变成「容器 + 内容」。
2. **头尾说明合并进同一个附录**，用 B.1…B.9 平铺，**不要保留原来的「一、二、三」章号** —— 旧一级章号进附录会和正文抢层级。附录内保留原有小节名与顺序，读者找得到。
3. **导语保持极短**（依据 / 规模 / 方法指引三行以内）。它承担导航，不承担论述；论述一律在附录。

## 27.3 用脚本搬运，不要逐条 Edit

几百行的文档逐条手改必然漏、也不可复现。用「行区间搬运 + 定点替换 + 整块层级变换」一次成稿：

```python
src = open("backup.md", encoding="utf-8").read().split("\n")

def block(a, b, drops=(), repls=None, xform=None):
    res = []
    for i in range(a, b + 1):
        if i in drops:                          # 删：对话句行号
            continue
        t = (repls or {}).get(i, src[i - 1])    # 改：行号 → 新句
        res.append(xform(t) if xform else t)
    # 折叠连续空行 + 去掉块尾空行（否则拼接处会出现连续空行）
    out = []
    for t in res:
        if t.strip() == "" and out and out[-1].strip() == "":
            continue
        out.append(t)
    while out and out[-1].strip() == "":
        out.pop()
    return out

def demote(line):                               # 层级降级：只认目标前缀，别写通用规则
    if re.match(r"^# P\d\d — ", line): return "#" + line     # H1 → H2
    if re.match(r"^## P\d\d\.", line): return "#" + line     # H2 → H3
    return line

out  = [TITLE, "", *INTRO]
out += ["# 一、Checklist 主表（P01–P14，542 项）", ""] + block(
    167, 1112, drops={205, 264, 282, 284, 286, 325, 361, 910},
    repls={290: "本组不检查「有没有」，而检查「是否达到 … 的深度」。"},
    xform=demote)
out += ["# 二、Architecture Invariants", ""] + block(1117, 1138, repls={1117: "…"})
out += ["# 附录 A — 上一版保留项", ""] + block(1429, 1705)
out += ["# 附录 B — 评审框架与说明", ""] + ["## B.1 三层结构", ""] + block(9, 30) + …
```

- 三个参数就够：`drops`（删哪几行）、`repls`（改哪几行）、`xform`（整块变换，如降级）。
- 先写 `/tmp/<task>/out.md`，`diff -q` 通过后再 `cp` 回仓库；同时留 `backup.md`（改前）与 `prev_repo.md`（落盘前快照）。
- 附录内的小节标题同样要改层级/编号（本次 `## Case 1` → `### Case 1`，原「1.1–1.4」→「B.1–B.4」）。
- 重型重排（换目录、章节合并、跨版本拼接）用 `longform-md-restructure`；本节只讲「对话稿」这一输入形态的特有处置。

## 27.4 删完之后必须回扫的两处

**① 指向旧章号的交叉引用。** 本次 2 处（「一、评审框架」→「附录 B.1」、「三、P0 十项红线」→「附录 B.5」）。这类引用**不在被搬运的块里**，脚本永远不会替作者改：

```bash
grep -nE "第 ?[0-9一二三四五六七八九十]+ ?[章节点部分]|附录 ?[A-Z]|见上|见下" "$f"
```

**② 残留对话词。** 交付前最后一次 grep，命中即回查：

```bash
grep -nE "如不合预期|我会|我发现|你看|这样改|review 草稿|上一版 Checklist|这比重新造|可以。基于" "$f"
```

注意别把合法的成稿表述一起杀掉：本次保留「附录 A — 上一版保留项」（它确实是被保留的上一版条目）、保留「你们平台的真实控制点」。判据仍是 27.1 那一条 —— 看主语。

## 27.5 验收判据（可量化，不要只看 diff）

| 检查 | 判据 | 本次结果 |
| --- | --- | --- |
| 实体编号连续 | 主表 `1..N` 无缺号；附录 `A01..` 无缺号 | 542 / 181 全连续 |
| 引用闭合 | 使用集 = 定义集 | `[1]–[19]` 一致 |
| 结构完整 | 标题层级计数、围栏数偶数、表格数量 | H1/H2/H3 = 6/33/40，围栏 54 |
| 内容不丢 | 行级差异**全部可归因**为三类：层级变化 / 有意删除 / 有意改写 | 88 条全归因 |
| 真丢失筛查 | 词元归零法：旧有新无的拉丁词元应只剩被删对话句里的词 | 仅 4 个（`Pattern`/`Process`/`enforcement`/`DeepAgents`） |
| 无对话残留 | 27.4 的坏词 grep 为空 | 空 |

最有用的两条：

- **行级差异必须能「批量归因」而不是逐条解释。** 一旦出现第 4 类归因（既非层级变化，也非有意删改），就是意外丢失，必须回查。
- **词元归零法**能一次性证明「删的只是对话、不是内容」：把「未逐字命中的旧行」里、在新文件中一次都没出现的拉丁词元筛出来，剩下的就是真候选（本次只剩 4 个，全部来自被删的对话句）。

## 27.6 交付说明怎么写

报告里明确三件事，别让作者自己去 diff、也不要只说「已重构完成」：

1. **删掉了哪几句对话** —— 逐条列出原文，便于作者回退。
2. **改写了哪几句** —— 给「原文 → 中性句」对照，说明为什么判定为对话。
3. **回改了哪些交叉引用**，以及备份路径 + 可复现的构建脚本路径（`/tmp/<task>/build.py`）。

同时给出新骨架的一张表（各区块 → 内容 → 规模），让作者一眼确认结构是否符合预期。

## 27.7 版本自指语气：把「本版 / 上一版」从正文里清出去

成稿是给人看结论的，不是给作者看修订史。**只要一句话的主语是「这份文档」或「它的上一版」，就是 AI 味的重灾区。**

典型形态（都是同一类）：

```text
**这一版收紧的两处**            ← 加粗小标题 + 变更宣告 + 编号列表
本版新增一条写作规则：……        ← 主语是文档
上一版只写了 A，没有回答 B。本版明确 C。   ← 三段式对照
Architecture Invariants 从八条补到十二条   ← 数量变化写进正文
```

处置分三档：

| 形态 | 处置 |
| --- | --- |
| 加粗小标题式变更宣告 | **删**，内容并进相邻段落，或改成一句陈述（`平面模型在两处做了收紧：`） |
| 「本版 / 这一版 + 动词」 | 换成直接陈述：`本版在这一层新增一个判定环节` → `这一层需要一个判定环节` |
| 「上一版 X，本版 Y」对照 | 只留当前结论；若「撤回 / 降级」本身是内容，**把主语换成判断本身**：`上一版报告建议拆除 → 「长期拆成独立 Retrieval Service」这个强建议撤回` |
| 整章的变更对照表 | 保留内容、改列名：`上一版 \| 本版处置` → `原判断 \| 现在的处置` |

判据只有一条：**读者需要知道的是「现在的架构是什么」，不是「这篇文章改了几次」。** 撤回、降级、命名变更这类判断变化是内容，可以留；但主语必须是判断，不是版本号。

### 打标时最容易踩的坑：子串替换

整行替换必须**先定位整行、再替换整行**。直接 `text.replace(key, new)` 会留下行尾残渣，产生半新半旧的句子（本次真实踩过：`…不是安全边界**。：把「Policy Plane」改名为…`）：

```python
lines = text.split("\n")
for key, new in ROW:                      # key 是唯一子串，new 是整行新文本
    idx = [i for i, l in enumerate(lines) if key in l]
    assert len(idx) == 1, (len(idx), key[:60])
    lines[idx[0]] = new
text = "\n".join(lines)
```

跨行的键（表格分隔行 + 首行）要单独放一组「特例」，且**必须包含整段原文**，否则同样会残留。

### 收尾必做的三次扫描

```bash
# ① 版本自指是否清零
grep -nE "本版|上一版|这一版|前一版|改名为|前 ?[0-9一二三四五六七八九十]+ ?条" "$f"
# ② 其余元叙述是否成灾（少量可接受，>5 处就要处理）
grep -nE "本章|这一章|本节|综上所述|值得注意的是|不难看出" "$f"
# ③ 脚本化多轮编辑留下的硬伤：重复段落 / 重复表行 / 标题前缺空行
```

③ 用段落级扫描（按空行切段、跳过围栏内、文本长度 ≥ 25）：多轮区间 op 叠加极易留下**整段重复**与**两行被压成一行**。本次扫出 8 处重复段落、1 处表格行重复、1 处标题前缺空行 —— 这些不是「语气问题」，是必须修掉的客观缺陷，且顺手修不会引起内容争议。

# 28. 最重要的总原则

> **“去 AI 味”不是把文字变得更口语，也不是把所有 AI 常用词替换成同义词。**
>
> **真正要去掉的是：机械结构、重复强调、模板化连接词、无意义总结、过度对仗和证据强度与结论强度不匹配。**
>
> **文章的观点、证据、限定条件和作者真正想表达的判断必须保持不变。**

# 29. 架构类技术文章的专门去 AI 味检查

前面的规则适用于通用中文文章。架构报告还需要检查另一类问题：文章看似完整，实际却把通用词汇和组件名称拼成一份“看上去专业”的方案，读者仍然不知道该如何实现。

## 29.1 每个建议都要落到具体决策

检查以下常见空话：

- 「采用云原生架构，提高系统可扩展性」
- 「通过统一治理保证数据质量」
- 「建立完善的监控体系」
- 「使用事件驱动解耦系统」
- 「采用最佳实践，确保安全可靠」

这些句子只有在说明了对象、约束与验收方法后才有价值。把它们改成可以评审的设计，例如：

- 哪个工作负载需要横向扩容，扩容时会增加什么资源，怎样避免把下游数据库压垮？
- 要核对哪些业务金额、记录数或源端水位，出现差异由哪个作业修复？
- 监控哪些延迟、失败率和积压；超过什么由谁收到告警？
- 哪种事件从哪里发布，消费者如何处理重复、乱序与重放？
- 谁能调用哪条 API，身份从哪个 Token Claim 映射到业务授权，数据层还要设置什么限制？

如果无法写出具体对象，不要用更多形容词补足它。

## 29.2 区分建议、事实和推断

架构文章要让读者分辨：

- **已证实事实**：官方文档明确说明的产品能力、限制、协议或产品状态。
- **案例事实**：某个公司描述了自己如何构建系统。
- **设计建议**：基于当前场景、风险和成本作出的选择。
- **待验证假设**：还需要 PoC、负载测试或组织确认的部分。

不能把「AWS 提供了一个 EKS 参考架构」写成「金融企业都应该按该图部署」；也不能把某家公司的特定规模、旧版产品或内部平台当成普遍标准。每个架构图都应标明来源、图的性质、可借鉴之处与适用边界。

## 29.3 不用“行业最佳实践”代替取舍

出现「最佳实践」「标准架构」「成熟方案」时，追问三个问题：

1. 谁给出的实践：规范、产品文档、工程团队复盘，还是作者推断？
2. 它针对什么问题和规模？有没有前提、反例或代价？
3. 在当前系统里为什么选择它，放弃了什么？

应优先写明真实取舍，例如「把长查询异步化会增加任务状态和结果保留机制，但可以避免 HTTP 请求长期占用线程」，而不是写「采用异步架构提升用户体验」。

## 29.4 避免“先列术语，再用术语证明架构正确”

CQRS、DDD、Event Sourcing、Data Mesh、Hexagonal Architecture、Semantic Layer 等词不应成为论据本身。只在它解释实际边界时使用。必须能回答：

- 哪一个写入路径或读取路径因此发生改变？
- 哪个组件拥有数据和规则？
- 失败发生时谁重试、谁对账、谁能恢复？
- 哪个具体需求证明需要这一模式？
- 不引入它是否也能解决问题？

不要为了让架构图看起来先进而增加没有明确责任的中间层、代理、消息系统或抽象接口。

## 29.5 让图体现真实系统，不要只把名词装进方框

架构图至少应表达它真正要解释的关系：

- 系统上下文图：使用者、外部身份系统、业务服务、权威数据源和分析平台之间的调用与数据流。
- 部署图：网络边界、可用区、入口、EKS 工作负载、数据库子网、外部 SaaS 及网络连接假设。
- 逻辑分层图：模块所有权、调用依赖、Command / Query 分工与数据适配器。
- 时序图：请求方向、同步提交点、异步事件、失败边界以及最终一致性的窗口。

不要在不同图里随意改变组件名字；不要用无语义的虚线排版；不要把外部 SaaS 画成 AWS VPC 内部组件；不要把可选组件画成必需组件。图中无法确认的部分应标注为假设或待验证。

## 29.6 真正的大厂图与本文建议图要分开

引用外部架构图时，分清四种情况：

| 图的来源 | 正确写法 |
|---|---|
| 厂商的产品参考图 | 称为「厂商参考架构」，指出哪些组件只是示例 |
| 大厂工程团队公开的系统设计 | 称为该公司的工程设计或平台架构，不外推为全行业标准 |
| 客户案例 | 说明它是客户案例，并把客户披露的事实与作者推断分开 |
| 本文根据需求绘制的方案图 | 明确称为「建议设计」或「逻辑示意图」，不能冒充现有生产系统 |

产品生命周期必须检查。引用旧图时，若其中组件已停止服务、改变 GA/Preview 状态或有关键限制，要直接标注，不能只在文末悄悄加个链接。官方图可以引用，但不要删除来源标识，也不要把它改造后仍称作原厂原图。

# 30. 架构文章的逐段审查表

逐节检查下面的问题。不是要求每节都变成清单，而是确认每个重要判断都有内容支撑。

| 检查项 | 合格标准 | 不合格信号 |
|---|---|---|
| 具体场景 | 写清现有组件、工作负载和数据路径 | 用「企业通常」「现代系统」概括全部读者 |
| 责任边界 | 写清谁定义规则、谁保存权威状态、谁做计算 | 只说「分层解耦」 |
| 同步语义 | 标记同步 / 异步、延迟、重试、重复、重放 | 只说「数据实时同步」 |
| 安全边界 | 说明身份、业务授权、数据权限分别在哪里执行 | 把 SSO 当成全部授权 |
| 生产行为 | 讨论超时、并发、故障、恢复和对账 | 只画正常流程 |
| 成本与规模 | 说明资源成本由什么驱动，哪些数字需要实测 | 无依据地宣称低成本、高性能或无限扩展 |
| 选型结论 | 把适用条件、代价和替代方案写清 | 「A 是最佳方案」但没有比较依据 |
| 证据 | 关键产品能力有官方文档，案例有原始工程来源 | 只引用转述、宣传页或无来源图 |
| 图文一致 | 所有图中的组件、术语和路径与正文一致 | Mermaid 用一套名字，正文再换一套 |
| 篇幅 | 每一段都添加事实、解释、取舍或操作方法 | 同一个结论在导语、各节末尾、结论反复出现 |

## 30.1 技术文章的“空话替换”检查

扫描这些表达，但不要机械删除关键词。命中后，逐句判断是否提供了可验证信息：

```text
最佳实践 / 业界标准
现代化 / 云原生 / 企业级
高可用 / 高性能 / 可扩展
端到端 / 全链路 / 统一治理
无缝集成 / 充分利用 / 赋能
完善的监控体系 / 强大的数据能力
本质上 / 归根结底 / 值得注意的是
核心是 / 关键在于 / 真正重要的是
这意味着 / 由此可见 / 不难发现
```

如果它只是在下一句引出另一个抽象说法，删掉前面的引导语并重写整段。若它表达的是具体的非功能要求，例如多可用区部署或端到端追踪，则保留技术内容并说明怎么实现和验证。

# 31. 更可操作的 De-AI 验收方法

去 AI 味不能靠某个 AI 检测器给分。编辑后应该能指出哪些结构被改了、哪些事实需要核验、哪些内容仍有重复。

对架构文章采用以下内部检查表，每项记 0、1 或 2 分：

- **0 分**：有明显问题，内容空泛、重复或证据不足。
- **1 分**：大体可读，但仍有几处未解释的抽象判断或机械结构。
- **2 分**：内容具体，表达自然，取舍和证据边界清楚。

| 维度 | 评审问题 |
|---|---|
| 场景贴合 | 是否明确响应读者给出的实际组件和约束？ |
| 事实与来源 | 是否区分厂商能力、真实案例和本文推断？ |
| 决策质量 | 是否解释了为什么选它、什么情况下不选？ |
| 结构自然 | 是否避免每节都遵循同一模板、固定三段式和重复总结？ |
| 语言 | 是否有大量单句段落、加粗金句、套话或连续机械排比？ |
| 图的价值 | 每一张图是否回答一个正文很难讲清楚的问题？ |
| 工程深度 | 是否覆盖失败路径、权限、数据新鲜度、监控和恢复？ |
| 术语一致 | 相同的组件、数据模型和业务定义是否使用统一名称？ |

总分仅用于编辑者判断下一轮改哪里，不是文章质量的科学测量，也不能代替事实核查。低分维度必须回到具体段落修改，不能通过添加更多标题或列表来“补分”。

## 31.1 完稿前的自动扫描

可以使用脚本做候选提示，不能将命中结果直接批量删除：

```bash
grep -nE "本质上|归根结底|值得注意的是|由此可见|不难发现|这意味着|核心是|关键在于|最佳实践|无缝集成|赋能" "$f"
grep -nE "本版|上一版|这一版|我发现|如不合预期|我们可以看到|本文将深入" "$f"
```

扫描结果需要人工判断。同一词在技术语义中可能是准确表达，不应因为它属于检查词表就一律删掉。还要逐节检查是否出现「导语说一次、章节结尾再说一次、结论又说一次」的重复。通常保留最有信息量的一处，其余删除或改为新的限定条件。

## 31.2 架构文档新增或重画图后的检查

当作者明确要求增加架构图时，图不属于语言润色的保护区，应使用 text-to-mermaid 的职责进行设计和验证。至少核对：

1. 每个组件的名称与正文一致，系统边界、部署位置和网络方向没有混淆。
2. 同步请求、异步数据流、数据库提交点和最终一致性窗口标记清楚。
3. 外部身份提供商、外部数据平台与内部云网络边界明确。
4. 图中的可选方案、待验证网络能力和示例数据值明确标注。
5. Mermaid 围栏闭合，关键连线有意义，不以无语义连接换取布局。
6. 真实公司图片直接链接到原始文章或官方资产，并注明图的来源和适用限制。

# 32. 架构技术文章最后一轮检查

交付前做一次从头到尾的连贯阅读，不要只看局部 diff：

- 开头是否直接交代要解决的设计问题，而不是先写一段放之四海皆准的背景？
- 结论是否真的从正文的证据和取舍推出？
- 每节是否有新的解释或决策，而不是变换措辞重复旧结论？
- 是否把一个厂商图或一个客户案例外推成全行业结论？
- 是否有未核实的产品版本、地区能力、生命周期、限制或费用声明？
- 是否把架构假设写成了当前环境中的既成事实？
- 关键术语、组件名称、业务规则和引用是否一致？
- 是否为填充篇幅加上与决策无关的章节、列表或图？
- 是否还有「现代化、智能化、高可用、可扩展」却未说明实现条件的句子？
- 是否保留了技术上重要的边界、失败路径与不确定性？

最终目标不是把文章压短，也不是追求极口语化。应删掉没有信息增量的部分，同时保留工程师做决定需要的细节。
