# Article De-AI

## 目标与职责

把已有初稿编辑成可以直接交付给读者的成稿。重点不是把文字改得更漂亮，而是让内容具体、自然、有判断，读者能看懂作者在回答什么问题、依据是什么、结论是什么。

核心原则：

- 改表达，不偷换观点；压缩重复，不删除有效信息。
- 去掉没有信息增量的内容，不以缩短篇幅作为目标。
- 语言可以直接，但不能牺牲技术准确性、证据强度和必要限定。
- **检查不等于必须修改。** 初稿已经自然、准确、结构合理时，可以零修改；不得为了证明执行过 Skill 而制造改动。

本 Skill 负责最终成稿的语言、叙述结构、文档形态和全文一致性。它不代替研究、事实核验、架构设计、图表设计或技术审查。

## 适用范围

适用于中文技术文章、研究报告、论文调研、架构分析与评审、技术选型、项目进展、问题诊断、根因分析、复盘、行业与产品分析，以及面向管理层、工程团队或客户的交付文档。

凡是 Agent 生成准备交付给读者的报告，默认必须执行本 Skill，即使用户没有单独提出“去 AI 味”。

以下情况不做语言改写：原样数据导出、日志、JSON/YAML/SQL 等机器可读产物、逐字记录，以及用户明确要求保持原文或禁止润色的内容。可以按用户要求做格式或结构检查，但不能擅自改写内容。

## 规则优先级

发生冲突时，按以下顺序处理：

1. 用户对范围、格式、保留内容和修改权限的明确要求。
2. 事实、证据、数字、因果、技术语义及来源保护规则。
3. 原文明确的文档用途、结构约定和格式约束。
4. 本 Skill 的编辑建议。

因此，不能为了去 AI 味而改动受保护内容；不能因为某条编辑建议而违反用户指定格式；也不能把“通常应该这样写”变成所有文档都必须遵循的固定模板。

## 执行流程

按顺序处理。简单文本可以合并步骤，但不能跳过语义保护和最终通读。

### 1. 判断文档类型与编辑范围

先确认文档是文章、报告、方案、清单、评审材料还是对话记录整理稿，并识别读者、目的和用户要求。

先读取完整文档及必要的相邻内容。保留有价值的既有结构、Frontmatter、标题、链接、引用、代码和图表。不要仅因为发现一种更整齐的结构，就重写整份文档。

### 2. 先处理文档形态，再处理语言

如果正文混入了对话和起草过程内容，先清理这些内容，再润色语言。

需要识别的非交付内容包括：

- 对话开场、应答和面向当前对话对象的确认语，例如“可以，下面我来……”“这样是否符合预期”。
- Agent 工作过程，例如“我搜索了……”“根据前面的分析”“接下来我将介绍……”。
- 版本自指和编辑过程记录，例如“本版新增了……”“上一版遗漏了……”。
- 临时提示、写作指令、未清理的占位文字和内部协作备注。

处置时看句子实际承担的作用，不要只按关键词删除。若一句话同时包含过程描述和有效事实，应改写为中性事实句，不要整句删除。真正属于正文的作者判断、方法说明、标准定义和适用边界应保留。

方法、评分框架、版本差异或使用说明是否放入附录，取决于读者是否需要它们以及它们是否影响正文论证。**不得把“方法说明一律放附录”或某一种固定章节骨架套用到所有文档。**

### 3. 编辑语言与叙述结构

逐段检查以下问题，并按上下文处理：

- **碎段与断句：** 连续出现大量只有几个字或一句话的段落时，判断是否应合并。短段落有强调或节奏作用时可以保留。
- **机械排比：** 检查连续的“首先/其次/最后”“一方面/另一方面”“不是 A 而是 B”“不仅……而且……”等句式。不是禁用，而是避免整篇文章依赖同一种节奏。
- **模板连接词：** 检查“值得注意的是”“需要强调的是”“换句话说”“由此可见”“不难发现”“从这个角度来看”等表达。删除没有实际作用的引导语，不要机械替换成同义词。
- **重复解释：** 删除同一观点在段落总结、章节总结、执行摘要和结论中的重复表述。后文只有在增加新证据、新限定或新决策时才保留。
- **同义反复与机械强调：** 避免连续堆叠“核心、关键、根本、重要、显著、全面、深入”等词。强调词确实改变语义时可以保留。
- **金句与加粗：** 不要让每节都以粗体观点或引用块收尾。完整句子默认不加粗；引用块应有真实引用或明确的强调价值。
- **列表与表格：** 独立事项适合列表，有共同属性且需要比较时适合表格，连续论述则写成正文。不要把所有内容都拆成列表。
- **定义链条：** 避免“定义—换句话说—这意味着—由此可见—总结”反复解释同一件事。
- **宏大结论：** 不把一个实验、单个客户案例或局部观察扩大成行业定论或未来必然趋势。
- **自然表达：** 优先明确主语、具体动作和真实取舍。避免空泛被动句、名词堆砌和没有信息量的形容词。

这些检查是诊断线索，不是关键词黑名单。不能因为某个词出现在检查表中就批量删除。

#### 段落优先，避免排比驱动全文

技术文章应由论证推动，而不是由整齐的句式推动。编辑时要专门检查以下倾向：

- **连续排比：** 相邻段落反复使用三段式、四段式或六点式结构，尤其是连续出现“不是……而是……”“既……又……”“从 A 到 B”“一方面……另一方面……”时。只有确实存在并列关系时才保留；否则改为解释因果、条件或取舍的普通段落。
- **伪对称句：** 不要为了节奏把两个并不对等的概念硬写成对仗句，也不要每节都用一句“不是 X，而是 Y”制造观点感。直接说清楚具体问题和判断即可。
- **列表膨胀：** 列表适合列出可独立检查、执行或比较的项目。若条目之间实际构成一段因果解释、一个连续过程或同一判断的不同侧面，应改写为段落。不要把一句完整论述拆成多个短 bullet，也不要把每个章节都写成“引入句 + 五点列表 + 总结句”。
- **表格滥用：** 只有当读者需要横向比较字段、选项或责任边界时才用表格。把一段普通解释拆成两列表格，通常只会增加视觉噪声。
- **章节节奏同质化：** 相邻章节不应重复同一种开场、分点、加粗结论和总结结构。根据内容选择叙述方式：先给判断、从案例切入、解释一次调用过程，或直接讨论设计取舍都可以。
- **结论复述：** 结论不应把前文标题改写成编号清单。只留下读者做决策时真正需要记住的判断，以及它成立的条件；前文已经解释过的内容不要再逐条复述。

列表密度没有适用于所有文档的固定百分比，但若连续多个章节都以列表为主体，或一页中短 bullet 明显多于完整论述段落，应重新判断是否把文章写成了检查表。架构矩阵、威胁分类、角色职责、阶段验收等确实需要枚举的内容可以保留表格；解释原因、边界和取舍时优先使用连贯段落。

#### 反对把正文写成项目符号清单

技术文章默认采用段落叙述。**有多个并列事实，不等于必须使用列表；内容可以分项，不等于读者需要看到项目符号。** 编辑时逐个检查列表是否真的帮助读者理解、比较或执行。

以下内容通常应该改写成自然段落：

- **优点、特点和价值罗列：** 不要写成“某技术的优势包括”后面跟五条泛化 bullet。把有关联的内容组织成两三句话，说明它们如何影响成本、部署或维护。例如介绍 LoRA 时，可以直接说明它只训练少量参数、Adapter 可以按任务保存和切换，以及在什么条件下能够合并回基础模型。
- **假设性例子：** 不要把“A 是代码任务、B 是金融任务、C 是写作任务”单独列成清单。将例子嵌入解释句，例如“假设 A、B、C 分别来自代码生成、金融分析和中文写作微调……”。只有读者需要逐项核对输入输出时才保留列表。
- **常规做法与背景枚举：** 如果只是说明过去的 LLM 优化工作会调整 Prompt、训练代码、超参数、数据处理或评估流程，应在一个句子中列举，不要每个术语占一行。
- **同一机制的多个结果：** 若条目之间是因果、补充或递进关系，应解释关系，而不是只把名词排在一起。比如“参数少、显存占用低、训练成本低”不能默认当作三个互不相关的优点；应交代参数规模如何影响资源成本，并保留必要条件。

列表应留给真正需要逐项处理的信息，例如安装步骤、按顺序执行的操作、验收标准、互斥选项、风险控制项、实验配置和可独立检查的事实。即使保留列表，也要检查每一项是否有独立意义；不要为了凑成三点、五点或七点而拆分句子。

**不要只把 bullet 合并成一个超长句。** 先判断条目之间的逻辑：能合并的内容写成段落；有先后关系的写清步骤；需要比较的用表格；确实独立的检查项才保留列表。段落可以有长有短，句子也应有变化，不要把列表改成一串由分号连接的名词。

编辑完成后，做一次“反向列表检查”：逐个查看正文中所有非目录、非标签、非代码、非参考文献列表。问自己：如果删掉项目符号，把这些内容放进一个段落，读者是否仍能更顺畅地理解？如果答案是肯定的，就改成段落。不要为了降低列表数量而破坏步骤、清单、对照表或可扫描性。

编辑排比时不能只把“首先”替换成“其一”，也不能将列表机械合并成很长的复合句。应重新识别句子之间的逻辑关系，按读者理解所需的顺序重写。句长应有变化，段落也不必等长；自然的技术写作允许直接、短促的判断，但不应让每一段都像一个口号。

### 3.1 识别结构性 AI 写作痕迹

检查的不只是词语，还包括句子和段落为什么这样组织。模型常用固定结构制造完整感：先铺垫重要性，再解释常识，最后重复结论。编辑时识别以下模式，但不要把它们当成必须清零的禁用清单。

**铺垫代替陈述。** “这不是简单的 X，而是 Y”“真正的问题在于”“归根结底”“让我们深入看看”“说实话”等表达，如果没有纠正真实误解、提供必要对照或承担实际转场作用，就直接陈述事实和判断。尤其检查跨句的否定式对照，以及段尾“这才是真正的价值”“这说明了重要性”一类重复收尾。例子已经说明的内容，不必再用一句话解释它说明了什么。若正文没有提出某种异议，也不要凭空写“有人可能认为……”。

**节奏由模板决定。** 检查强凑三项、连续句子使用相同开头、每段长度相近、每节都采用相同的“引入 + 三点 + 总结”结构。三项并列必须代表三个不同概念；两项就写两项，重复近义项应删掉。句首和句型可以变化，但不要为了避免重复而生硬倒装。破折号也不应成为万能连接符：先判断分句之间是解释、补充、转折还是因果，再选择标点或重写。中文写作不必机械禁用破折号，作者样本中的标点习惯优先。

**普通事实被包装成重大意义。** 对“里程碑、开启新时代、深刻改变行业格局、发挥关键作用、为未来奠定基础”等表达追问：事实是否足以支持这个判断？局部功能上线或单个实验通常只需说明时间、范围和结果。类似“充分体现、进一步彰显、推动了……”的分词短语若没有独立证据，不要附加在事实后面。营销式形容词、抽象名词和复杂动词也要检查，能准确使用“是、有、做、支持”的地方，不必写成“发挥作用、提供赋能、构建能力”。

**模糊关系和借用权威。** “与……密切相关”“形成联动”“业内专家认为”“多份报告指出”可能掩盖真实关系或缺失的来源。证据明确时，写出实际关系是调用、依赖、隶属、引用还是竞争，并指出具体来源；证据没有说明时，不得自行补全，也不要用模糊权威替代引用。

**格式装饰。** 检查每个列表项是否都加粗标签、标题是否写成口号、标题后第一句是否重复标题、emoji/箭头/分隔线是否只是装饰。若标签没有独立信息，可改成自然段。真正便于扫描、比较或执行的列表保留。正文也不要反复说“下表展示了”“本节将介绍”“本文分为三个方面”，除非这种说明确实影响读者使用文档。

**对话和知识边界残留。** 清除“当然可以”“很好的问题”“希望对你有帮助”“如果还需要……”等对话包装。不要写“根据我目前掌握的信息”“公开资料较少，因此可能……”来描述模型知识边界或掩饰猜测。应准确说明来源没有披露什么；没有必要时删除。不能用猜测填补资料空白。

**面向错误读者。** 回复、项目更新和评审意见容易重新复述对方刚提出的问题，再铺陈双方都知道的背景，最后才给决定。读者已有的信息无需重讲；先给结论，只保留会影响判断的新增依据、限制和动作。独立发布的教程或研究报告仍需提供理解主题所必需的背景，不能借此删掉关键上下文。

### 3.2 词语观察清单及判断阈值

以下表达在模型文本中容易成组出现，值得检查：赋能、彰显、凸显、深度、全面、关键、核心、显著、稳健、生态、格局、交织、推动、促进、确保、体现、展现、构建、打造、助力、引领、范式、里程碑、不可或缺、值得关注、具有重要意义。

它们不是禁用词。“稳健估计”“核心转储”“确保事务原子性”“关键路径”都可能是准确的技术表达。只有当词语承担夸大、装饰或空泛概括作用时才修改，不要把一个空泛词替换成另一个空泛词。

明显的对话残留、无依据事实、重复收尾和营销式夸大，确认语境后单次即可处理。单独一个破折号、三项并列、被动句、正式词汇、粗体标签或限定词通常只是弱信号；需要结合段落和全文的重复模式再决定。真实的幽默、口语、插话、情绪、犹豫和不对称句式都可能是作者声音，应予保留。引用、标题、专有名称和正在被讨论的表达也不能误判成作者自己的写作习惯。

不能以“检测器会不会标记”为编辑依据。目标是让读者更容易理解作者的真实意思，不是绕过检测器、伪装人工来源或制造所谓的人类写作特征。

### 3.3 重写和复核

先完整阅读并标记段落级、全文级模式，不要看到某个词就逐个替换。相同问题可能跨越多个句子或章节，例如每节都采用相同开场、三点列表和总结句，需要调整整体叙述，而不是只修其中一个句子。

重写时围绕段落的主要判断组织内容，可以调整句序、合并或拆分段落，也可以改变原有结构。每个保留的句子都应提供读者尚未获得的信息，例如事实、推理、限制、例子或决定。删除重复句时，确认其中没有独有的条件或信息。

完成后按自然语速朗读或默读，检查句长是否过于平均、段落是否总以相同方式开头和收尾。再定向搜索最容易残留的模式：无效 A/B 对照、重复收尾、强凑三项、破折号过密、装饰性粗体和标题、对话残留。最后逐项对照原文和来源，确认没有增加或丢失事实、名称、数字、日期、引文、引用、排名、因果关系、同时发生关系或限定条件。若一句话需要当前没有的事实才能写得自然，就简化句子或标记待核实，不得自行补造。

### 3.4 作者声音优先

如果用户提供写作样本，先读样本，再决定如何编辑。尽量匹配其句长、常用词、标点、开头方式、转折习惯和有意保留的口语表达。样本中的稳定习惯优先于本 Skill 的一般建议。

没有样本时，根据文档类型判断语气。技术说明、事实报告和参考资料保持清楚、克制、准确；观点文章可以保留作者的判断、犹豫、幽默和个人反应。不要把所有文档都改成同一种“客观、简洁、正式”的声音。去除 AI 痕迹不等于消除作者个性。

### 4. 保持作者判断与内容密度

成稿应围绕要回答的问题组织，而不是按检索资料的顺序罗列。

- 开头尽快交代问题、结论或需要读者作出的决策。背景只保留理解问题所必需的内容。
- 每一节都应推进论证：提供证据、解释原因、比较方案、说明边界或导出行动。没有新增信息的章节应考虑合并或删除。
- 方案比较不能停在“各有优劣”。应结合实际约束说明更适合哪一种、为什么，以及什么情况下结论会改变。
- 建议尽量明确对象、动作、前置条件、责任边界、验证方式和代价。证据不足时标明假设或待验证事项。
- 事实、分析、判断和建议可以自然衔接，不必强行拆成固定的四段式；但不能让读者误把推断当成事实。
- 不要为了“内容丰富”补入未经核实的案例、数字、作者经历或行业共识。

如果发现的是实质内容缺口，而不是表达问题，不要用扩写空话来掩盖。应指出缺少的证据、案例、决策依据或工程细节，并交由相应研究/审查流程补足；获得可靠内容后再编辑成稿。

### 5. 保护语义、证据和技术内容

以下内容属于保护区。除非用户明确授权进行事实或技术修订，否则不得在 De-AI 编辑中改变：

- 核心观点、结论和作者立场。
- 因果关系、条件关系、适用范围和责任归属。
- 证据强度与不确定性，例如“可能、通常、部分、当前、预计、案例显示、研究发现”。
- 数据、金额、百分比、日期、数量、版本号、benchmark、性能指标和单位。
- 产品、模型、API、协议、组件、标准、法规和开源项目名称。
- 引用、URL、citation marker、脚注、参考资料及其与正文的对应关系。
- 用户指定必须保留的标题、章节层级、术语、代码和图表。

特别注意：

- 不能把“可能导致”改成“导致”，也不能把明确事实弱化成猜测。
- 不能把一个案例写成普遍规律，也不能把相关性写成因果关系。
- 不能把“当前实践”改成“未来趋势”，不能把局部适用范围扩大成全行业。
- 不要为了显得专业而统一掉原文中有意义的不同概念。
- 同一概念应统一术语；但只有在确认指向同一概念时才合并叫法。

默认不改标题文字和层级。若标题本身存在明显对话痕迹，先保留并提示，除非用户已授权结构编辑。标题层级确需调整时，必须检查目录、锚点、内部链接和交叉引用。

### 6. 保护格式与机器可读内容

默认不改代码块、SQL、Shell、JSON、YAML、XML、配置文件及 Mermaid 源码。不要为了语言自然而改动字段、节点、标识符、缩进、注释、版本号或执行语义。

用户明确要求修改图表或结构化内容时，转由相应 Skill 或技术审查流程处理；本 Skill 只负责核对最终图文是否一致，不擅自设计或重画图。

编辑 Markdown 时，检查 Frontmatter、标题层级、代码围栏、表格、列表、引用、链接定义、脚注和图片引用是否完整。不能为了整齐而改变文档格式约定。

## 专项编辑要求

### 技术文章与架构报告

技术内容不能只靠语言润色变得可信。对重要架构建议，成稿应尽可能说明适用场景、组件职责、关键边界、方案取舍、失败路径、运维责任和验收方法。

重点清理以下空泛表达，但不能机械删词：

- “企业级、现代化、云原生、智能化”却没有具体含义；
- “高可用、高性能、可扩展”却没有实现条件或验证指标；
- “统一治理、端到端、全链路、无缝集成”却没有说明实际控制点；
- “最佳实践、业界标准”却没有来源或适用条件；
- “加强监控、完善治理、持续优化”却没有责任人、触发条件和具体动作。

图表属于技术内容，不是语言装饰。核对正文与图中的组件名称、系统边界、调用方向、数据路径、权限控制和失败分支是否一致。图的设计、Mermaid 语法和技术正确性由专门的图表/架构流程负责。

### 研究型文章与证据

当前产品能力、论文、标准、法规、客户案例和行业趋势必须由研究与证据审查流程核实。编辑时：

- 保留来源链接，并确认引用仍然支持相邻论点。
- 区分法律/监管要求、正式标准、指导框架、学术实验、厂商声明、客户案例和本文建议。
- 不把官方文档存在等同于生产成熟度，不把客户故事当作独立验证。
- 不补写来源没有披露的内部实现、效果或指标。
- 若证据无法支持原文结论，标出问题并交由 evidence review 处理；不要仅靠降低语气或改写句子掩盖证据缺口。

### 对话稿整理为正式文档

把对话转成文章、方案或报告时，清除应答语、提问残留、Agent 工作过程、临时指令和版本编辑记录。保留真正有价值的事实、决策、理由、约束和未决事项。

不要将所有“你们”或“我”一律删除：如果它们准确表达了组织职责、作者立场或实际操作主体，可以保留或改写；只有面向当前对话的应答语和起草过程语才应清理。

## 全文一致性与最终验收

局部修改后必须从头到尾通读一次，不能只看 diff。重点核对：

1. **观点一致：** 开头、正文和结论没有互相矛盾；同一观点没有换词重复多次。
2. **证据一致：** 每个关键结论都有对应依据，引用没有丢失或错位。
3. **限定一致：** 可能性、时间、范围、条件和例外没有被悄悄改变。
4. **术语一致：** 同一概念使用统一名称，不同概念没有被错误合并。
5. **结构合理：** 标题层级、章节顺序和段落衔接服务于读者，不是套用固定模板。
6. **格式完整：** Frontmatter、标题、链接、表格、代码围栏、引用和图表引用没有损坏。
7. **文档成稿：** 正文不残留对话语、Agent 工作记录、临时提示或无关版本说明。
8. **信息有效：** 每一段至少提供事实、解释、判断、取舍、操作方法或必要限定；没有价值的内容才删除。

对大文件可以按完整章节分块编辑，但必须先建立全局术语、核心主张和语气约束。不能切断代码块、表格、引用块或连续论证；完成后必须做全篇一致性检查。

## 报告生成的强制 De-AI 流程

凡是 Agent 生成准备交付的报告，必须在交付前执行本 Skill。固定顺序：

1. 完成研究、数据分析、事实核验、架构判断和必要图表。
2. 形成内容完整、证据明确的初稿。
3. 使用本 Skill 对整份报告进行文档形态和语言结构检查，必要时编辑。
4. 回查结论、证据、数字、日期、因果、范围、限定条件、引用、术语和图表。
5. 通读最终稿，确认它是一份面向读者的报告，而不是 Agent 的工作记录。

适用范围包括技术研究、论文调研、架构分析/评审、方案比较、技术选型、项目进展、问题诊断、根因分析、审计复盘、行业/产品分析和管理层报告。

**必须执行检查，不代表必须改写。** 如果报告已达到要求，应保留原文，并在交付说明中如实写明“已检查，无需修改”。不得只在任务说明中提到本 Skill，也不得只删除几个高频词就宣称完成。

不适用于原样数据导出、机器可读结构、逐字记录或用户明确禁止改写的材料。

## 交付说明

执行文件编辑任务后，简要说明实际完成的工作，不要为了填数字而编造统计。至少交代：

- 检查/编辑了哪些文件或章节。
- 处理了哪些主要问题：对话残留、重复观点、模板表达、结构问题、术语不一致等。
- 是否调整了标题、结构、代码、图表或引用；没有调整也可明确说明。
- 语义保护检查是否通过；若发现无法确认的内容，列出待核实项。
- 实际执行过哪些验证，以及哪些验证没有执行。

可使用以下简洁格式；没有发生的项目不要强行填数字：

```text
De-AI:
  edited sections: ...
  removed dialogue/process residue: ...
  consolidated repetition: ...
  simplified template phrasing: ...
  structural changes: ...

Protection:
  claims / evidence / data / qualifications: unchanged
  references / code / structured content: preserved
  unresolved items: ...

Validation:
  full-document read: passed / not run
  links / formatting: passed / not run
  build / CI: passed / failed / not run
```

若没有必要修改，应明确报告“检查完成，无需改写”，不要为了产生 diff 而改动原文。
