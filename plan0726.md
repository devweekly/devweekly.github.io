# 第一部分：脚本调整（最高优先级）

我认为脚本应该承担：

> Deterministic Intelligence

而不是：

Data Dump。

---

## ① Evidence Store → Findings Store

这是最大的变化。

目前：

```
Architecture

Capability

Ranking

EntryPoint

...
```

建议改成：

```
Finding

Question

Evidence

Counter Evidence

Confidence

Coverage

Importance

Limitations
```

例如：

```json
{
  "id":"F-001",

  "question":
  "Does the repository implement Retrieval?",

  "finding":
  "Repository contains retrieval pipeline.",

  "confidence":0.93,

  "importance":"critical",

  "coverage":0.84,

  "support":[...],

  "counter":[...],

  "limitations":[...]
}
```

注意：

不是 Markdown。

是：

JSON Schema。

GLM 最喜欢这种。

---

## ② 每个 Finding 必须回答一个 Question

不要：

```
Architecture
```

这种分类。

改成：

```
Q1

How does request enter the system?

Q2

Where is orchestration?

Q3

Does retrieval really exist?

Q4

Where is prompt management?

Q5

What contradicts README?
```

Finding

一定属于某个 Question。

以后 Report 就稳定很多。

---

## ③ 增加 Conflict Detection

这是目前脚本最值得加的。

例如：

```
Analyzer A

Retrieval exists.

Analyzer B

No embedding.

Analyzer C

README claims retrieval.
```

自动：

生成：

```
Conflict

Topic

Retrieval

Evidence

...

Need Review
```

GLM：

专门处理：

Conflict。

---

## ④ Finding 自动评级

例如：

```
Importance

Critical

High

Medium

Low
```

不是：

LLM 判断。

Analyzer：

自己算。

例如：

```
Architecture

Critical

README

Low

Prompt

High
```

---

## ⑤ Confidence 不再人工

例如：

```
AST

+

Graph

+

Git

+

Runtime

↓

Confidence=0.96
```

不是：

```
High
```

## ⑥ 增加 Coverage

例如：

```

2100

132

```

## 我认为最关键的一条原则

综合官方文档、论文以及你和我、Gemini 的讨论，我会把整个系统的设计原则浓缩成一句话：

> **让脚本负责“确定性事实（Deterministic Facts）”，让 GLM-5.2 负责“验证、解释和综合（Verification, Reasoning, Synthesis）”。**

这比简单地“多做脚本”或“多依赖 1M Context”都更符合 GLM-5.2 的 Agentic Engineering 定位，也最符合你希望构建的高质量、可验证、可追溯的 Repository Research Agent。
