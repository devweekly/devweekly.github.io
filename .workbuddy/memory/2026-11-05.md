## 追加：托管会话 SDK 卡死的根因与修复（上一节结论已过时）

手动跑 `codebuddy -p "..." --model hy4free` 报 `EADDRINUSE 127.0.0.1:51246`：SDK fork 的 CLI 继承宿主会话变量后，会去监听 WorkBuddy 主进程占用的服务端口，随即卡住，表现成模型调用超时。仅去掉 `CODEBUDDY_SERVICE_PROXY_URL` 不够；`env -u CODEBUDDY_SERVICE_PROXY_URL -u CODEBUDDY_HOST -u CODEBUDDY_SESSION_ID -u WORKBUDDY_CONFIG_DIR -u ACC_PRODUCT_CONFIG_PATH codebuddy -p ... --port 0` 可正常返回「可用」，`--port 0` 让 CLI 自选端口。

**采纳的做法**（参考 `modelCatalog.ts` / `workbuddy.ts` / `check-codebuddy-connectivity.mjs`）：
- 模型目录：`ACC_PRODUCT_CONFIG_PATH` 解析不出模型时**仍要扫** `~/.codebuddy/local_storage/*.info`（旧实现只要 env 有值就不扫）；缓存按 mtime 全量尝试、不设窗口；再叠加 user/project `models.json`。`auto` / 空值一律视为未配置，不能当模型 id 传给 CLI。

- 调用生命周期改为**逐条消息**与超时竞速（旧实现只对整体 collect 竞速），超时/异常时 `abortController.abort()` + `stream.interrupt()` + `iterator.return()`；`timer.unref()`；长任务每 30s 打心跳到 stderr；检查 `result.subtype !== 'success'` 把 CLI 错误抛出来，不误报「空输出」。抽出 `applyAgentMessage` 便于单测。

**两个真机坑**（都靠实测发现，别再踩）：
1. SDK 类型里有 `requestTimeoutMs`，但传给本机 CLI 会变成 `--request-timeout-ms`，CLI 立刻退出并报 `CLI process stdout closed unexpectedly`。超时只能由本地竞速 + interrupt 控制，`buildQueryOptions` 里已加注释禁止再加回去。
2. CLI 日志文件名是 `<cwd 目录名>__*.log`（本项目 `novel-generation__*.log`），不是参考项目的 `workspace__*.log`；按 `basename(cwd)` 前缀匹配，否则第 5 步永远「无新增记录」。日志里 `agent=unknown, model=wb-lite` 是 CLI 自己的轻量探测，统计时要过滤掉 `agent != cli` 的行。
