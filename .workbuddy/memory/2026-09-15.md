### 三处最关键的修正（这三处决定了 skill 是否可用）

1. **`S0–S5` 单轴拆成 `Source Type T0–T5` + `Authority` + `Independence IND0–IND5`**。
   旧 S0 里「官方文档 / 论文 / RFC / 源码」并列，但它们的权威性完全不同。
   新规则：T0 的 Authority=5 **只在回答主体自己的事实时成立**；一旦 Claim 变成 comparing/maturity，
   T0 立刻退化为 interested party，Authority 降为 1。这一条解释了为什么「引用全是官方文档」
   撑不起一篇成熟度评估。
2. **Confidence 不由独立性决定**。旧规则 `High = 一手 + 最新 + 直接 + 独立 corroboration`
   会把所有能力事实系统性误判成 Medium（因为「产品支持 X」本来就只有厂商一个权威源）。
   新规则按 Claim 类型分流：FACT/CAPABILITY/LIMITATION 型允许 `Confidence HIGH + Independence LOW`；
   PERFORMANCE/MATURITY/COMPARISON/PREDICTION 型不得只凭厂商来源给 High。
3. **`I — Independence` 升为正式评分维度**（旧的四维 F/S/R/T → 五维 F/S/I/R/T）。

### 新增的维度里，价值最高的两个

- **`Scope / Applicability`**：判据是 `证据 scope ⊇ claim scope`。
  这是「证据被错误泛化」这类错误唯一的检出手段 —— 所有证据都真，结论仍可错。
  与上一轮审 Snowflake 成稿时的发现直接对应（「Cortex Search 已成熟」实际只覆盖
  Snowflake-native + medium scale）。
- **`Silent Evidence` + `Absence of counter-evidence ≠ Evidence of absence`**：
  把「搜了没找到」和「没搜」分成两个结论。要求记录 `searched / found / plausible_reasons`，
  并列出四条结构性原因（内部事故不公开 / 失败 POC 不公开 / case study 挑成功 / 社区 selection bias）。

### 可执行化的两个构件

- **§4.1 Required Actions**：17 步，每步留可核对记录。
- **§4.2 Stop / Continue Conditions**：明确何时必须继续搜（类型是 MATURITY/COMPARISON 却只有单一来源、
  涉及数值、涉及 GA·Preview 状态、用 benchmark 做比较）、何时可以收工
  （FACT/CAPABILITY + 当前官方一手来源 + 版本日期已确认 + 无显式反证）、
  何时**必须降级结论**（只有厂商来源却判 maturity → 最高 CONDITIONALLY_SUPPORTED）。
  这一节是 v1 → v2 性质变化最大的地方：v1 讲「要判断权威性」，v2 讲「满足什么条件才能收工」。

### 校验方式（可复用）

脚本检查：控制字符为零、围栏按长度配对平衡、表格管道符计数分组自洽（3/4/6/14）、
重复实义行扫描（9 处全部是 YAML 字段回显，非冗余散文）、逐项确认 17 条 review 落地、
残余 `S0–S5` 只出现在附录 B.3 对照表。

**保留的一条历史纪律**：v1 第 32 节的核心原则（不要只找支持证据）没有被削弱，
而是升级成了 15 步主线链：
`Claim → Type → Scope → Evidence → Directness → Authority → Independence → Freshness →

## 第十六轮：`evidence-and-claim-review` v2.0.0 → v2.1.0（模型正交化，随后冻结）

用户就 v2 审核的实际运行结果提出第二轮 review，核心判断是：**v2 的方法论已成立，不需要推倒重写；
但内部模型还有「把两个不同维度压成一个字段」的问题**。定为 v2.1 精修，共 7 条（P0×3 / P1×3 / P2×1），
外加 review 正文里散落的 4 条。用户明确要求：**「v2.1 应该做模型正交化 + negative claim + evidence sufficiency
+ applicability + outcome verification，然后冻结。」**

### 最重要的一处：Claim Type 与 Epistemic Status 正交化

原 v2 的 §1.3 是「Fact / Interpretation / Prediction 三选一且互斥」，但同时 §1.2 又有一张 13 类的
Claim Type 表 —— 两套分类混用。用户给的例子说明问题：

```text
「Cortex Agent 是 Data-Native Managed Agent Runtime」
  Claim Type = STRATEGIC      Epistemic = INTERPRETATION     ← 两个字段，不是一个
「Cortex Agent Evaluations 已于 2026-03-13 GA」
  Claim Type = FACT           Epistemic = FACT
「Frontier Agent Runtime primitives 正在快速商品化」
  Claim Type = PREDICTION     Epistemic = INFERENCE
```

改为两个正交字段：`type`（问哪类问题）× `epistemic`（这句话本身是事实/推论/预测/意见）。
分工写清楚了：**Type 决定要多少证据，Epistemic 决定这句话的强度上限。**
`epistemic = PREDICTION` 一律不得判 SUPPORTED；`epistemic = OPINION` 不得作论证前提。

### 其余六条

- **Evidence Sufficiency（新 §2.9）**：`SUFFICIENT / PARTIALLY_SUFFICIENT / INSUFFICIENT`。
  与 Confidence 的分工是：Confidence 答「我有多确定」，Sufficiency 答「手头的证据够不够回答这类问题」。
  价值在于抓「看起来很有把握、其实答非所问」—— 例如问成熟度却只给能力证据。
  现在共**三个正交结论**：Status × Confidence × Sufficiency。
- **Negative claim 规则（§1.2 新增）**：LIMITATION 的取证必须满足三条之一（官方明写 unsupported /
  schema·API·runtime 明确排除 / 可重复实验确认）；只凭「文档没写」最高 INSUFFICIENT_EVIDENCE。
  写成一句判据：`absence in docs ≠ explicitly unsupported`。
  并说明了它与「缺席的反证 ≠ 反证不存在」是同一纪律的两面。
- **Applicability Conditions（新 §1.5）**：Scope 回答「到哪里为止」，Conditions 回答「拿什么换」。
  条件是 `required / required_for_write / recommended`，**含未满足的 required 则最高 CONDITIONALLY_SUPPORTED**，
  且必须是可核对对象（角色/流程/配置/数据质量），不能写成「取决于治理成熟度」。
- **Outcome Verification（新 §3.2）**：`Successful` 从来没说清「是谁定义的」。
  拆为 `NONE / SELF_REPORTED / REPRODUCIBLY_REPORTED / INDEPENDENTLY_VERIFIED`。
  关键判据：独立验证的核心是**验证方与被验证方无利益关系**，不是「写得详细」。
  `SELF_REPORTED` 的数字不得写成既成事实，必须保留归因。
- **Counter Evidence Severity（§2.6 新增）**：`Cosmetic / Operational / Economic / Reliability /
  Governance / Safety-Security`。规则是**严重度不可平均** —— 一条已确认的 Governance 级反证权重高于
  任意数量 Cosmetic 反证之和。本轮 Snowflake 案例里 Search owner's rights 正属此列。
- **搜索深度按 Claim Type 分级（§2.6 表 + §4.1 三级）**：取消了「每 Claim 至少 4–6 个反证变体」的一刀切。
  反证搜索方向也按类型走 —— 例如 LIMITATION 的反证搜索是**反向的**（去找「其实支持」的证据）。
  §4.1 的 17 步改为三级：Level 1 Basic Fact（6 步）/ Level 2 Decision Claim（+8 步）/
  Level 3 Strategic Claim（+4 步）。理由写进 SKILL：战略预测类条目往往只占少数，

## 第十七轮：原则层补齐 —— 五条 → 六条（v2.1.0 → v2.1.1）

用户就 v2.1 的「五条不可违反原则」提出第三轮意见。核心判断是：**五条方向都对，但作为一个 Evidence Review
Skill 的完整认识论基础还不够。**缺的不是更多原则，而是两句总原则：

> ① 证据强度必须与结论强度匹配。
> ② 从证据到结论的推理链本身也必须被审查。

并指出一处**实质性错误**：把「absence of evidence ≠ evidence of absence」当成绝对命题是过头了。
现代证据论（Bayesian confirmation）的结论是**条件性的** —— 缺席何时具有负证据价值，
取决于「若假设成立，该证据原本有多大概率被观察到」。

### 定稿的六条（顺序即推理主线，已写进 SKILL 且标注「不要重排」）

```text
1. 结论强度不得超过证据强度。
2. 引用不是证据，引用只是证据的入口。
3. 证据到结论之间的推理链必须被单独审查。
4. 官方文档证明 capability，不自动证明 maturity。
5. 客户案例证明 feasibility，不自动证明 generality。
6. 缺席的证据不自动构成反证（条件化）。
```

原第 4 条（缺席的反证 ≠ 反证不存在）与原第 5 条（证据缺席只降低可信度）**合并为新的第 6 条**，
并改写成条件化表述 —— 这两条本来就有重复，用户指出的这一点在合并时自然解决了。

### 关键的结构性说明：三条覆盖三个不同失效模式

写进 SKILL 的一张对照，用来防止读者以为六条在说同一件事：

```text
Evidence Quality    证据本身可靠吗？            由 2 保证
Inference Validity  从证据到结论的推理成立吗？   由 1、3 保证
Applicability       结论能推广到哪里？          由 4、5 保证
```

### 三处操作化（这是本轮真正的工作量）

原则如果只是口号就等于没有。每条新增/修正的原则都配了可执行的判定件：

- **原则 1 → 「证据档位 → 结论上限」表**：官方能力文档最高只支持 CAPABILITY 级陈述、
  单个客户案例最高只支持该案例的 feasibility、未复现 benchmark 只能 directional-only、
  多来源 IND≥4 + 生产证据才可支撑 MATURITY。判定话术是**反查**：
  「我手上的证据，最多能支持到哪一档？」，而不是正着数「我搜到了几条」。
- **原则 3 → inferential chain 四段式**：`directly established` / `indirectly supported` /
  `additional assumptions` / `alternative explanations`。四类 Claim 必走（CAUSAL / STRATEGIC /
  PREDICTION / RECOMMENDATION），并加进 Claim Record 的 `inference_chain` 字段。
- **原则 6 → detection probability 两步判定**：先问「这个证据在假设成立时有多容易被观察到」，
  再问「我们的搜索是否覆盖了它可能出现的渠道」。配了高/中/低检测概率对照表
  （官方 release note / 定价 = 高；独立 benchmark = 中；内部事故 / 失败 POC = 低）。
  并落成 `absence_assessment` 字段（coverage_complete / detection_probability / verdict）。
  三种组合的读法也写明：**coverage 不全时，不得作任何结论，只能记 Missing Evidence。**
