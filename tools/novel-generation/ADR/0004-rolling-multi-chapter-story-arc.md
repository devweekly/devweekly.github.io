# ADR 0004：滚动式多章节故事规划与自动续写闭环

- 状态：Proposed for implementation
- 日期：2026-11-07

## 背景

当前系统已有长期 Story Plan、Story State、单章主线/创意/章节规划和上一章正文接续。但每次写作仍以单章为规划单位。长期方向与当前章节之间缺少一段可持续维护的中期因果链，容易出现“本章写得完整、下一章不知道自然发生什么”的问题。

## 决策

采用滚动式多章节规划（Rolling Story Arc），不是一次性锁死全书，也不是连续生成多章正文。

规划分三层：

1. **Story Plan（长期）**：核心冲突、人物长期目标、重大阶段节点、长期情节线与结局方向。
2. **Story Arc（中期，默认 5–8 章）**：一个完整故事场景/阶段的起因、推动力量、人物选择、冲突升级、阶段性结果，以及后续开放问题。按需要延伸到自然段落，不强制固定章数。
3. **Chapter Plan（短期）**：本章视角、场景、人物目标与阻力、关键行动、信息变化、情绪变化、结尾状态。

Scene 是写作和状态提取的最小单位；Chapter 是交付单位；Story Arc 是因果规划单位。

## 运行闭环

1. 点击“生成下一章”。
2. 系统自动检查世界设定、上一章、故事状态和计划版本；能安全修复的准备项自动补齐，不要求用户逐项确认。
3. 如果没有可执行的 Story Arc，或剩余计划不足以支持下一章，自动生成/扩展中期 Story Arc。
4. 根据当前已发生事实、Story Arc 和相邻章节因果关系，生成下一章 Chapter Plan。
5. 正文生成以**上一章完整正文**作为直接连续性上下文；同时注入本章计划、前后相邻章节的必要信息、Story State 和相关人物/情节图谱。
6. 完成必要的文学编辑与硬伤检查。编辑不能为了显示工作量而重写有效表达。
7. 终审通过后自动提取并提交 Story State、人物变化、事件、伏笔/MacGuffin 状态和 Story Arc 进度。
8. 对照实际正文与后续计划。若正文发生合理偏离，保留正文和已发生事实，自动修订尚未执行的章节计划；不得强行把正文改回旧计划。
9. 剩余章节计划不足时自动滚动扩展。

任何计划都不能凌驾于已发生事实、人物生命力和文学表达。规划是为了让故事有方向，不是限制故事创造性。

## 人物与情节原则

- 不把人物固定为性格标签或预设善恶路线。人物可以转变、反复、做出意料之外但有内在依据的选择。
- 每章不要求所有主线、人物弧光、伏笔和 MacGuffin 都推进。
- 允许局部故事闭环、日常、关系戏和暂时偏离主线。
- 人物变化应记录“触发事件、人物选择、代价/后果、文本证据”，但字段可以为空，不强制每次都产生弧光。
- 伏笔可以长期悬置、改变解释或被放弃，不以清单完成率评价文学质量。

## 持久化

沿用 SQLite，不引入独立图数据库。新增/扩展实体：

- story_arcs：中期故事阶段，含目标、因果链、状态、版本、来源和时间戳。
- chapter_plans：章节顺序、所属 arc、计划内容、状态、前后依赖、实际正文关联。
- scene_plans：场景顺序、视角、地点、人物目标/阻力、预期状态变化。
- plan_revisions：记录正文偏离后对未执行计划的修订及理由。

这些实体与现有人物、事件、情节线、伏笔和 MacGuffin 通过稳定 ID 关联。数据库为权威来源；JSON/Markdown 仅作为可读快照与诊断产物。

所有计划必须带版本和状态：planned / in_progress / completed / revised / deferred / abandoned。只允许更新未执行计划；已完成章节和已发生事件不可被重规划覆盖。

## Workbench UI

章节页以“继续写下一章”为唯一主操作：

- 顶部展示当前故事阶段、已完成/剩余章节计划和下一章标题/一句话方向。
- 一个主按钮“生成下一章”。
- 计划和场景以只读时间线呈现；用户不需要确认、批准或逐项填写。
- 运行中只展示总体进度和当前阶段；详细 Agent 产物折叠到“运行诊断”。
- 生成后展示正文、阶段结果和计划变化；不把审核变成前置门禁。
- 提供“重新推演后续主线”作为显式操作，但常规生成自动滚动维护。

## 流水线简化

保留：
- 一次中期 Story Arc 推演（仅在需要时）
- 本章规划
- 正文生成
- 一次聚焦文学性的整体编辑（可按问题触发）
- 一次事实/连续性终审
- 状态与计划回写

合并/按需：
- 对白与叙事声音编辑优先合并为一次整体编辑；只有检测到明显问题时才拆分。
- 反 AI 检查默认诊断；只有具体问题影响文本时才编辑。编辑后必须做差异验证，若损伤有效意象、人物动作、信息揭示或节奏，自动恢复原文。
- 不再对同一问题重复执行多轮泛化“润色”。

## 失败与恢复

- 任何阶段失败都必须明确标记 run failed，并保留阶段输入、原始模型响应、错误和 checkpoint。
- 终审 pass 不等于全流程完成；只有状态与计划回写成功后才允许标记 completed。
- 状态提交必须幂等，避免重试重复追加事件。
- 失败重试从最近有效 checkpoint 恢复；不重新生成已经通过且输入指纹未变化的阶段。
- 不允许把空的/无效的审查文件当作 pass，也不允许缺少终审或状态更新时显示“章节已完成”。

## 验收标准

1. 连续点击生成下一章时，第二章必定引用上一章完整正文和对应 Chapter Plan。
2. 至少能自动规划并显示一个多章节 Story Arc；按顺序消费，不要求用户确认。
3. 完成一章后，已发生事实、人物状态、事件与 Arc 进度自动更新。
4. 正文合理偏离计划时，只重规划未来未执行章节，不篡改正文。
5. UI 可见当前 Arc 与下一章计划，但没有审批门禁。
6. 失败的终审/状态提交不会显示成功；重试可从 checkpoint 恢复。
7. 文学质量优先；不能因计划未完成、人物弧光未推进或伏笔未回收而判失败。
