# ADR 0005：独立故事宇宙与任意章节分支续写

- 状态：Accepted（已实现新宇宙创建与章节历史分叉；原文只读共享和存储去重继续演进）
- 日期：2026-11-07
- 相关决策：ADR 0004（滚动式多章节故事规划）

## 背景

当前续写工作台以一个 world 为一个连续故事运行。Story State、Story Arc、Story Plan、人物/事件图谱和生成章节都落在同一 world 下，因此无法安全地从任意原文章节创建多个独立续写方向。简单复制当前 world 目录也不够：它可能把已有续写状态、滚动计划、生成记录带入新分支，造成故事事实串线。

需要支持同一原文派生多个独立续写故事。每个故事可以从任意原文章节开始，可以延续原著主线、扩展支线、聚焦配角或走向平行发展。各分支互不影响。

## 决策

### 1. 原文项目与故事宇宙分离

- 原文项目（Source Canon）是共享的只读来源，包含原文、章节目录、原文分析结果、原著人物/事件/关系证据及原始风格参考。
- 故事宇宙（Story Universe）是独立的续写分支，有稳定的 universeId，并记录 sourceWorldId。
- 一个原文项目可以派生任意多个故事宇宙；一个宇宙只绑定一个原文来源。
- 原文不会被续写流程覆盖，生成章节只写入所属宇宙。
- 物理存储可以先采用独立目录/副本实现隔离；逻辑上原文是共享只读资产。后续可以用只读共享库、内容寻址或硬链接减少重复，但不能以存储优化牺牲隔离。

### 2. 任意章节作为分支起点

创建宇宙时必须指定原文起始章节（可选章节内具体位置/段落），并提供创作意图。起点不是“从该章之后机械接一章”：Agent 应读取起点章节及必要前情，理解当时人物处境、事件因果和未解决冲突，再确定新宇宙的第一章如何展开。

支持的创作意图是提示，不是不同的工作流：
- 原著主线延续
- 原著支线扩展
- 人物独立故事
- 平行发展/关键事件改写
- 自由续写

以上全部使用同一套生成、审查、状态更新和滚动规划流水线。

### 3. 每个宇宙独立维护的状态

每个宇宙必须独立拥有：
- Story Plan、Story Arc、Chapter Plan、Scene Plan 和未来计划修订历史；
- Story State、人物当前状态/弧光、人物关系；
- 派生剧情图、事件因果、伏笔生命周期、MacGuffin 状态；
- 生成章节、章节编号/顺序、运行历史、阶段缓存和质量报告；
- 宇宙自己的创作 brief、风格配置和工作台设置。

这些状态都必须按 universeId 隔离。不得把另一个宇宙的续写章节、人物变化、事件、伏笔、计划或生成缓存注入当前宇宙。

### 4. 共享与隔离边界

| 数据 | 共享规则 |
|---|---|
| 原文章节与原文文本 | 共享，只读 |
| 原著人物/事件/关系抽取和证据 | 可共享，只读；必须标记为 canon/source |
| 原著章节目录与检索索引 | 可共享，只读 |
| 宇宙内新人物、新事件和状态变化 | 严格隔离 |
| Story Plan / Story Arc / Chapter Plan | 严格隔离 |
| 续写人物图、剧情图、伏笔、MacGuffin | 严格隔离 |
| 生成正文、运行记录、阶段缓存 | 严格隔离 |
| 宇宙内创作配置与风格调整 | 严格隔离 |

必须区分原文事实、当前宇宙已发生事实和 Agent 创作推断。创作推断不能升级为原文事实；某宇宙发生的事不能变成其他宇宙的已知事实。

### 5. 复制/分叉语义

- “新建宇宙”从原文只读来源初始化空的续写状态。
- “从现有宇宙分叉”复制该宇宙在指定章节/版本时点之前的派生状态，并记录 parent universe 与 fork point；后续写入完全独立。
- 不能将原文项目目录当作一个已经生成的宇宙来覆写。
- 删除或归档宇宙不得删除原文或其他宇宙；删除操作应先归档，避免误删唯一创作成果。

### 6. 生成上下文规则

每次生成的上下文由四部分构成：
1. 共享原文上下文：起点章节、必要前情、原著证据；
2. 当前宇宙上下文：该宇宙上一章完整正文、Story State、图谱和计划；
3. 当前章节任务：本章蓝图、局部场景目标和创作意图；
4. 风格上下文：原著风格参考与当前宇宙认可/配置的风格材料。

绝不跨宇宙读取其他分支的生成内容。原著人物基础画像可以作为只读参考，但人物在当前宇宙的动机、认知、关系和发展必须由该宇宙独立维护。

### 7. UI

- 原文项目页增加“故事宇宙”列表和创建入口。
- 创建时从原文章节目录选择起点，输入宇宙名称和简短创作方向；不要求用户填写复杂表单。
- 工作台始终显示当前宇宙名称、原文来源和起始章节。
- 可切换宇宙；切换必须同时切换章节列表、规划、人物、图谱、状态和运行历史。
- 支持从现有宇宙分叉；不提供跨宇宙合并状态的功能。
- 宇宙支持归档与恢复；归档不删除任何文件或历史，归档状态禁止继续生成和分叉。分支树根据 `parentUniverseId` 展示父子关系。
- 日常创作仍以“生成下一章”为唯一主操作，不增加逐章审批门禁。

## 当前实现边界补充

宇宙目录创建和章节分叉使用 staging 目录构建，完成数据库身份重绑定、状态/计划写入和历史产物复制后才通过目录 rename 发布；失败时清理 staging 与分叉输出。归档通过临时元数据文件原子替换。新建、分叉、归档与章节启动进入同一 World 串行队列，避免管理操作和生成启动交错。

**原著知识的时点隔离采用保守白名单策略。** 新建宇宙生成独立的只读章节索引，仅包含起点及此前的原文分块；CLI 对宇宙缺少本地截断索引时直接失败关闭，不回退到全书原文库。 `novel.db` 按起点章节 ordinal 截断，保留章级事件/关系/人物状态及此前章节目录；全书聚合的 `story_analysis`、人物总画像、人物小传、卷级摘要、主线/伏笔聚合、实体注册和 annotations 暂时清除，因为它们可能包含未来剧情。分叉时重新构建同一时点的章节索引并再次截断知识库，避免旧宇宙继承未过滤的全书数据。 原文项目的 Vane 向量索引也不复制；宇宙只能从自己的截断索引重建 Vane。Corpus Craft 产物按 universeId 独立存放，不继承原文项目的全书素材整理结果。 数据库过滤采用显式安全表白名单；未知表默认清空，章级表缺少章节定位字段时整表清空，起点无法验证时删除副本。过滤异常时也清理 staging 中的未过滤数据库，防止失败回退为保留全书知识。 这是一项保守的防泄漏措施，不代表已经具备完整的历史时点人物/剧情分析；后续需基于起点以前证据重新生成这些聚合信息，并审查 Vane、语料 craft 等旁路数据源。

## 实施约束

1. 不引入图数据库；沿用 SQLite 与当前文件产物。
2. 所有派生数据表必须有 universeId 或通过独立 universe 数据库实现强隔离；不能仅靠 UI 过滤。
3. 每次运行的 worldId/universeId、原文来源 ID、起始章节和上下文来源必须写入 manifest，便于审计与复现。
4. 运行缓存键必须包含 universe ID 和状态/计划版本，避免不同宇宙复用错误缓存。
5. 创建宇宙时不得复制源宇宙的 story.db、Story Arc、Story Plan、续写输出或 run history。
6. 原文索引和原文分析只能由原文导入/分析流程更新；续写流程只能读取。
7. 原文项目与宇宙的目录/数据库迁移必须向后兼容现有单宇宙项目。

## 分阶段实施

### 第一阶段：可用的分支隔离垂直切片
- 增加宇宙元数据与列表/创建 API。
- 支持指定原文章节作为起点，并把起点与创作意图写入宇宙元数据。
- 每个宇宙使用独立 Story State、Story Arc、Story Plan、输出目录和运行历史。
- 工作台可查看/切换/创建宇宙。
- 新建宇宙不得继承源项目或其他宇宙的续写状态。

### 第二阶段：章节时点分叉与隔离（已实现第一版）
- 从已有宇宙任意已完成章节创建新宇宙。
- 从该章的 `08-state-update.json` 恢复当时 Story State，而不是复制父宇宙当前状态。
- 从该次运行的 `00-story-arc.md` 恢复当时 Story Arc。
- 复制截至分叉章节的已完成章节正文、运行产物和 Workbench 历史，并重写路径到子宇宙。
- 分叉时拒绝父宇宙仍有活动章节任务、状态快照缺失/归属不符或产物路径越界的情况。

### 后续阶段：存储规范化与知识库共享
- 原文 `library/` 已通过 `source-canon.json` 指针共享读取，不再复制到每个宇宙；CLI 检索直接定位原文项目资料库，宇宙侧禁止 ingest/analyze 写入共享原文索引与标注。
- 原著人物/事件/关系分析库 `novel.db` 目前仍复制为宇宙本地副本，便于后续分支独立演进；后续可将纯原著证据层拆成只读共享库，把宇宙推断与创作记录留在本地库。
- 分支树 UI 根据父宇宙关系缩进展示；归档只更新 `universe.json` 的 `archivedAt`，不物理删除目录。归档/恢复前检查活动章节任务，防止运行中状态被切换。
- 为派生知识表、状态表、图谱与运行记录补充 universe 外键和隔离测试。

### 并发与失败恢复补充决策

- 创建宇宙、章节生成启动、分叉和归档/恢复必须通过同一 worldId 的串行队列；归档与分叉再使用短时 mutation lock。章节生成只在 queued/running 记录写入且子进程启动后释放队列，不持有整章生成周期的锁。
- 创建/分叉使用 staging 目录，所有文件和状态快照准备并验证完成后才 rename 发布。分叉的历史输出和运行记录路径必须全部指向子宇宙；失败时清理 staging、子宇宙目录及其输出/运行记录。
- Story State 的加载验证必须针对 staging 目录中的快照执行，不能在正式目录尚未发布时误读不存在的路径。
- 该并发控制是单个 Workbench 进程内的协调机制；若未来支持多进程/多实例部署，必须改为跨进程锁或数据库事务协调，不能把内存 Map/Set 当成分布式锁。

## 验收标准

1. 同一原文可从任意两个不同章节创建多个宇宙。
2. 宇宙 A 的章节、人物死亡/生还、事件、伏笔和 Story Arc 更新不改变宇宙 B。
3. 宇宙 B 的生成上下文不会包含宇宙 A 的任何续写正文或状态。
4. 所有宇宙均可检索同一份原文和原著证据。
5. 新宇宙从所选章节的原文事实开始，而不是错误继承原文末尾或其他宇宙的状态。
6. 从一个宇宙任意已完成章节分叉后，子宇宙恢复该章时点的 Story State/Story Arc，并保留截至该章的章节链；父子宇宙在分叉点之后独立演进。
7. 生成失败不会消费/污染其他宇宙的计划或状态。
8. 原有 world 项目可以平滑迁移为默认宇宙，不丢失既有章节与状态。
9. 文学性、文笔、艺术风格仍高于其他约束；计划、图谱和状态只是创作辅助，不得限制人物生命力和剧情创造性。

## 2026-11-07 实施状态修订

本节是对早期方案与“后续阶段”描述的实施状态校正；上文保留决策演进记录，以免把历史计划误读为当前实现。

### 已实现

- 原文检索：宇宙有自己的按起点截断 library/index.json；source-canon.json 只记录来源身份，不授权读取父项目全书索引。CLI 与 API 共用 resolveWorldLibraryDir，历史索引缺失时 fail closed。
- SQLite：Create/Fork 生成宇宙自己的 novel.db 历史快照，按章节 ordinal 截断并重绑定 worldId；全书聚合表和未知表不继承。写作状态库、Story State、Story Arc、Story Plan、运行记录与输出独立。
- 分析目录：Create/Fork 从 bounded library 重建本宇宙 analysis/<worldId>/chapter-index.json，不复制源项目未来章节元数据或分析摘要。
- 自动知识重建：Create/Fork 发布后默认异步启动八步任务：analyze-story、analyze-arcs、ensure-style-profile、analyze-profiles、analyze-character-states、analyze-corpus-craft、export-asof-dossier、vane-index。任务状态在 Workbench 展示，可重试；写作、分叉、归档与知识构建通过单进程 per-world 队列和活动任务锁协调。
- 历史资料：export-asof-dossier 只从当前宇宙完整 SQLite 快照导出人物、人物关系、逐章时间线、主线、伏笔、MacGuffin、故事核心和发展可能性，写入 worlds/<worldId>/as-of-analysis/。该目录在下一次 Create/Fork 时明确排除。Style Profile 缺失时从 bounded library 取样重建，不覆盖已有人工资料。
- 原文大文件：Create/Fork 优先使用 copy-on-write reflink，保证 inode 独立；不支持时普通复制回退。不得使用共享 hard-link，避免任一分支修改原文时污染其他分支。
- 上下文隔离：章节生成的 common prompt 已抽取为可测试函数；测试同时覆盖实际 BM25 检索、Story Analysis Context、Corpus Craft、Writing Brief 与最终公共章节 Prompt 的时点 marker 排除。Vane manifest 必须匹配当前 worldId。

### 当前明确边界

- 起点粒度当前为章节级，不支持章节内任意段落/字符偏移；UI 不应暗示更细粒度。
- novel.db 与 bounded library 索引仍为每个宇宙保留时点安全副本；不能直接共享完整索引或全书聚合库。原始 original.txt 的 reflink 是可选物理优化，不是逻辑共享依赖。
- 自动分析是 LLM 对时点证据的解释，系统通过输入截断、证据引用和数据结构校验降低错误，但不能保证文学分析绝对正确。必须在真实作品上抽样核验人物关系、伏笔状态、MacGuffin 和主线判断。
- 当前队列/锁只覆盖单个 Workbench 进程；多进程部署仍需文件锁或数据库级协调。
- 质量验收不应把 Style Regression 或人物画像变成创作 gate；文学性、文笔、艺术风格优先，人物变化和剧情反转必须保留自由度。
