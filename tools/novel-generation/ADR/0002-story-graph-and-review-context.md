# ADR 0002：统一故事图谱与写作/终审上下文

- 状态：Accepted（存储方式已被取代，见下）
- 日期：2026-11-06
- 范围：`tools/novel-generation`

> 现状：v7 起 `story_graph_nodes` / `story_graph_edges` 两张表已删除。它们建好后只被写入，没有任何读取方——写作上下文读的是快照里的 `storyGraph`，审核包也从那里取。原著图现在只存在于 `story_analysis` 快照的 `storyGraph` 字段；续写动态关系、伏笔和 MacGuffin 图谱则从 `story.db` 的 Story State 更新日志即时派生，不再建立只写不读的图表。以下保留当时为什么需要图谱的推理。

## 背景

人物档案、人物关系、主线/支线、伏笔、章级事件和人物发展可能已经分别存在于全文分析快照或 SQLite 表中，但这些信息缺少一个可以表达跨类型关联、供写作和终审共同查询的统一结构。故事核心与 MacGuffin 也需要从全文语料中识别，而不能只依赖每章写作时临时回忆。

## 决策

### 1. 继续使用 SQLite，增加轻量 Story Graph

不引入 Neo4j、外部图数据库或额外服务。沿用每个 world 的 `novel.db`：

- `story_graph_nodes`：节点 ID、类型、标签、属性 JSON、章节来源引用。
- `story_graph_edges`：边 ID、起点/终点、关系类型、标签、属性 JSON、章节来源引用。
- `story_analysis`：保留完整分析快照，包括聚合故事核心观察、MacGuffin 和完整图谱。

图谱节点覆盖故事核心、人物、情节线、伏笔、MacGuffin、章级事件和人物发展可能。边覆盖人物关系、人物参与事件/情节线、伏笔关联情节线、MacGuffin 追逐/推动情节、人物发展可能和核心主线。

分析快照与图谱表在同一个 SQLite 事务中更新，避免不同版本混用。所有图谱数据尽可能保留原文章节来源；人物关系只使用规范姓名或唯一无歧义的个人别名建立连接，共享别名不连边。图谱不根据模糊语义相似度自动补边。

### 2. 全文分析覆盖主要故事结构

现有 `analyze-story` 增加以下抽取内容：

- 故事核心：核心冲突、核心问题、stakes、主题、叙事承诺、主要主线。
- 主线/支线：情节线保留关键转折、未解决问题、关联人物，并标记 main / subplot / unclear。只有真正统摄故事的冲突才标 main。
- 人物互动：在静态关系之外记录关系动态、变化和互动时刻；章级多人事件继续保留实际参与者。
- 伏笔：记录原文线索、首次出现、可能含义、可能回收方式及关联情节线。可能回收不是必须兑现的任务。
- MacGuffin：只记录真正驱动多方行动的目标、物件、信息或人物，并记录追逐者、动机、变化及关联人物/情节线；普通道具不应被泛化成 MacGuffin。
- 人物发展可能：保留互相矛盾的可能性，不把人物弧光固定化。

所有分析项使用模型提供的章节 key 建立来源引用。无法确认时保留不确定，不为填满字段编造答案。

### 3. 不新增专职 Agent

不新增人物 Agent、主线 Agent、伏笔 Agent 或 MacGuffin Agent。它们会重复分析同一语料，增加运行成本、上下文长度和相互矛盾的解释。

现有全文分析流程统一生成故事档案。普通章节、长章节和终审复用同一份按当前任务筛选的上下文；只注入命中的人物、关系、情节线、伏笔、MacGuffin 和一跳图谱关系，不整份灌入。

### 4. 写作与终审的职责不同，但使用同一份参考

写作阶段可以采用、改造、组合或舍弃分析参考。人物可以反复、误判、背叛、和解、黑化或洗白；主线可以偏航；伏笔可以不回收；MacGuffin 可以失去重要性。

终审只将图谱用于核对明确事实、人物知识边界、关键物件归属和因果硬冲突。不得检查人物是否执行预设弧光、伏笔是否按期回收、支线是否推进或 MacGuffin 是否按分析建议发展。无法排除是有意反转、隐瞒或留白时不报问题。

**最高原则仍然是：文学性、文笔、艺术风格，高于其他一切！** 图谱是创作参考，不是正史裁决、人物行为规范、剧情任务或小说质量评分表。

### 5. 审核包提供足够的可检查证据

审核包增加：

- 聚合故事核心和逐批故事核心观察；
- 完整 MacGuffin 列表；
- 完整 Story Graph 节点/边（受体积预算限制时可裁剪）；
- 图谱节点/边类型统计、孤立节点、悬空边和来源引用覆盖；
- 按全书章节范围均匀抽样的多人事件互动；
- 现有的人物、情节线、伏笔、分析请求/响应和写作产物。

孤立节点不自动等于错误；缺少来源引用、悬空边和连接质量需要审核，但模型推断仍需回查原文。审核包不把分析置信度伪装成人工确认。

### 6. 缓存与版本

本轮关系动态、主线/支线分类和故事核心图谱共同使用 `analysisVersion=6` 与独立 v6 缓存指纹。v3/v4/v5 批次缓存缺少新字段，不能迁移成 v6 完整分析；旧缓存保留为历史材料，v6 必须按原文重新分析。旧版本快照不得注入当前写作上下文。

### 7. 续写章节的动态关系、伏笔与 MacGuffin 状态

原著全文分析快照描述原著已经呈现的故事结构；续写章节不能反向改写这份分析快照。每章终审通过后，现有 Story State 管理流程额外提取本章真实发生的关系变化、伏笔生命周期变化和 MacGuffin 状态变化，分别追加到 `relationshipUpdates`、`foreshadowingUpdates` 和 `macguffinUpdates`。

这些记录以稳定对象 ID 和章节级更新 ID 关联人物、线索、关键目标/物件/信息及剧情线；每条更新必须附最终正文逐字证据。checkpoint 恢复按更新 ID 幂等合并。后续规划与终审按任务相关性读取最新状态；终审只检查明确事实冲突，不因人物关系变化、伏笔暂未回收或 MacGuffin 暂无推进而阻断章节。

不新增数据库表或专职 Agent：动态更新保存在现有 `story.db` 的 Story State JSON payload 中；原著图谱仍保存在 `story_analysis.storyGraph`。人物可以改变立场，关系可以破裂或修复，伏笔可以误导或废弃，MacGuffin 也可以失去意义。结构化记录只帮助后续章节记住已经发生的变化，不构成创作任务或人物约束。
动态视图通过 `src/story-state-graph.ts` 从人物、事件、情节线、关系变化、伏笔更新和 MacGuffin 更新派生节点/边；CLI 的 `story-state --type graph` 提供只读检查。连接只使用稳定 ID 和明确姓名，不做模糊实体归并。


## 后果

- 新增数据仍由本地 SQLite 管理，不增加数据库服务和运行时组件。
- 首次运行 v6 全文分析需要重新处理语料，模型成本高于仅复用旧批次缓存；这是获得新字段和新关系信息的必要成本。
- 图谱连接质量受模型抽取和实体匹配能力影响，因此审核包必须保留来源和质量摘要。
- 写作与终审不会因图谱未连接、人物弧光未执行、伏笔未回收或 MacGuffin 方向变化而失败。
