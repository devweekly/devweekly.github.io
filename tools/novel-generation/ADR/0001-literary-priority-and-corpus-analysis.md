# ADR-0001：文学性优先与全文人物/情节分析

- 状态：Accepted
- 日期：2026-11-05
- 范围：`tools/novel-generation`

## 背景

项目需要理解已有小说文本中的人物、主线、伏笔和后续发展空间，以便续写时有足够的上下文。但分析工具很容易把小说变成研究对象：人物被固化为性格标签，成长被拆成固定阶段，情节被整理成必须闭环的任务，伏笔被要求逐项回收，最后让创作服从分析报告。

这与项目目标相反。项目交付的是小说，不是研究报告或设定审计。

## 决策

**文学性、文笔、艺术风格，高于其他一切！**

这是最高优先级的创作原则，不是与连续性、证据、结构、覆盖率或工程指标并列的普通质量维度。发生冲突时，优先保护文学表达、人物生命力、情绪感染力、场景吸引力和读者体验。

人物画像、人物小传、成长可能性、主线、支线、伏笔、连续性记录和数据库状态都只是辅助理解与启发创作的材料，不是对正文的约束：

- 人物不是固定标签。人物可以自相矛盾、反复、冲动、犯错、误判、背叛、和解、黑化、洗白、突然改变，也可以拒绝成长。
- 人物弧光不是每个人必须完成的标准流程。可以有多种互相冲突的未来可能性，也可以没有明显弧光。
- 情节分析不能把所有细节解释成伏笔，不能要求每条伏笔都回收，也不能把推测写成既定事实。
- 后续发展建议允许意外、偶然、荒诞、浪漫、残酷和反常，不以“最合理”或“最安全”作为唯一标准。
- 留白、闲笔、生活细节、无用但迷人的观察，以及暂时无法解释的艺术选择都应被允许。
- 只有明确妨碍读者理解或破坏故事成立的硬伤，才可以触发自动修复。文学偏好、结构整齐、分析完整度和统计指标不得成为重写理由。

## 全文分析实现

新增 `analyze-story` 命令，复用项目已有 CodeBuddy Agent SDK 调用封装，不增加常驻 Agent 或新的模型运行时。

分析流程：

1. 从当前 world 的 SQLite `library_chunks` 读取已导入文本；若尚未迁移，则从现有 `library/index.json` 载入并同步到 SQLite。
2. 按上下文长度分批，将原文片段及 chunk 来源信息交给 LLM。
3. 分析人物小传、故事作用、性格与内在矛盾、欲望、关系、文本中已呈现的变化和人物成长可能性；梳理主线/支线、关键转折、未解问题；识别可能伏笔及不同解释；提出后续发展方向。
4. 跨批次按人物名称、情节线标题和线索文本归并，保留各项分析对应批次的来源片段范围，明确它是上下文定位，不冒充逐条证据证明。
5. 每批输出先缓存到 `.output/<world>/story-analysis/<cache-key>/`，以便中断后复用已完成批次。
6. 所有批次成功后，将完整分析快照一次性写入 SQLite `story_analysis`。分析失败时不覆盖上一次完整快照。

分析数据与 `story_state` 分离。它是可重建的创作参考，不是正史，不直接更新人物当前状态、事件或情节线状态，也不自动成为章节质量门禁。分析中必须区分原文呈现、合理推断和创作可能性；推测不得伪装成原文事实。

## 后续决策：故事核心与轻量 Story Graph（2026-11-06）

- 全文分析增加故事核心观察与 MacGuffin。故事核心包括核心冲突、核心问题、stakes、主题、叙事承诺和原文支持的主要主线；MacGuffin 只指真正驱动多方行动的目标、物件、信息或人物。
- SQLite 新增 `story_graph_nodes` / `story_graph_edges`，不引入 Neo4j 或独立运行时。节点保留分析属性和来源引用；边表达明确的人物关系、事件参与、情节线关联、伏笔承接、MacGuffin 追逐/推动、人物发展可能及故事核心主线。
- 图谱只建立模型明确提供或可精确匹配的关联，不以模糊语义相似度自动连边；孤立节点保留，不自动视为错误。
- 写作与终审共用图谱上下文。写作按任务选择相关节点及一跳关系；终审只用图谱检查明确事实、人物知识边界、物件归属和因果硬冲突，不检查人物是否按预设弧光发展、伏笔是否按期回收或 MacGuffin 是否按分析建议推进。
- 审核包新增故事核心、完整 MacGuffin 列表、图谱节点/边、图谱质量摘要和多人事件互动样本。图谱文件可在体积超限时裁剪，核心与质量摘要优先保留。

## 后果

正面影响：

- 写作前可以从已有文本中获得人物小传、关系、主线、伏笔和创作方向的结构化索引。
- 数据持久化在 SQLite，后续可按人物、情节线或来源片段检索。
- 人物和故事保持开放，不被一份静态分析报告定型。

代价与限制：

- 全文分析需要多次 LLM 调用，耗时与模型成本随语料规模增长。
- 人物跨批只按规范姓名归并；本名/化名/个人绰号仅作带证据的检索元数据，不用于自动实体合并。情节线按规范化标题、来源章节集合和关键转折内容识别重复；同名但来源范围或关键转折不同的记录保留独立 ID。
- LLM 输出是分析意见，不保证每条推断正确；来源引用用于回查，不意味着推断已成为正史。
- 更换或重新导入语料后，应重新运行分析以生成与当前索引对应的快照。

## 验证

- 对批次分组、结构化输出解析和 SQLite 快照读写编写单元测试。
- 运行 `npm run typecheck`、`npm test` 和 `npm run build`。
- 通过 `db-status` 检查 `story_analysis` 是否已写入；实际分析需要在可用的 CodeBuddy 会话环境中运行 `npm run dev -- analyze-story --world <world>`。


## 后续写作上下文接入

完整分析快照可以为普通章节和长章节提供少量相关参考，但不得整份注入。程序按本次创作任务筛选人物、情节、伏笔和发展可能性，并明确告知写作 Agent 可自由采用、改造或舍弃。重新导入语料时必须清除旧分析快照，避免分析结果与当前文本脱节。若筛选结果与文学表达冲突，文学表达优先。


## 后续决策：Pipeline 可靠性与创作上下文

在不增加 Agent 层级、不增加人工审批的前提下，修正会造成错误续写或恢复错误的工程边界：

- 长章节的必改问题必须映射到有效全章场景编号；审查结构无效时自动重试，不能执行空修复。
- 阶段缓存只有在输出通过阶段级结构/语义校验后才算完成；模型实际解析出的主模型和回退链必须进入缓存指纹。
- 长章节场景上下文携带相关人物当前状态和本章累计正文的有界滚动上下文，避免跨场信息丢失。
- 连续性备注表示当前仍有效的事实集合，不做永久追加；状态提取必须给出完整有效集合。
- 全文分析按章节 key 记录每条分析的实际来源；同一人物的多条发展方向分别保存，允许互相矛盾。
- 风格资料只作为参考，不得成为覆盖人物生命力和文学表达的硬性约束。

这些修正服务于“文学性、文笔、艺术风格，高于其他一切！”：工程校验只阻止损坏的流程结果，不评价或标准化小说表达；不通过增加审查 Agent、人物模板或创作字段来解决问题。


长章节的场景数量是执行上限，不是小说结构配额。蓝图可以按情节自然需要少于配置数量；不能为了满足数字而拆开原本连贯的场面。篇幅参考按实际规划出的场景数量重新计算，但仍然只是参考，不是逐场字数验收标准。

文风编辑和局部修复不设置“字数不得减少”或固定比例缩短门槛。可以精简重复和解释过度的内容，但必须保护有效的人物互动、动作、信息和情绪落点；长度变化本身不能证明内容丢失。后续审查继续聚焦读者会认定不可能的硬伤，不以篇幅指标替代文学判断。


## 后续决策：事实来源隔离与分析结果可靠性（2026-11-06）

- 章节生成后首次出现的事实默认是项目原创，不能因模型使用“confirmed”就升级为原著事实。已有事实 ID 保留其原有来源等级；新事件显式记录 canon / inferred / original 来源，生成章节新事件默认 original。
- 人物别名采用分类记录。只有提供原文证据的明确本名、化名或稳定个人别称（name_alias / nickname）参与人物检索；绰号、称号、职位、传承、能力和身份只作为描述信息。别名不参与人物实体合并；共享别名不参与关系解析，除非它唯一指向一个人物。
- 情节线去重同时使用标题和来源章节集合。相同标题、相同来源范围的重复记录合并；同名但来源范围不同的记录保留为独立情节线，并使用包含来源范围的稳定 ID，避免 SQLite 主键冲突。
- 全文分析批次 JSON/schema 解析失败时，保留原始响应并自动进行一次只修复结构、不重做分析的重试。重试失败的批次不写成功缓存、不参与 complete 快照，后续运行可以重试。
- 长章节润色以原稿精修为主，避免无必要地重写或扩写。逐场记录润色前后字数变化仅供诊断，不设比例阈值；润色后仍必须执行完整章节终审。
- 连续性备注只做空白、引号和标点差异的保守去重，不做语义相似度自动合并，以免误删不同事实。

这些是数据来源和流水线完整性约束，不是小说创作约束；不增加人工审批，不以篇幅或字段完整度限制文学表达。

- 旧状态自动修复：加载故事状态时，若事实来源明确标注“续写/续章/衍生/项目原创”，自动将其置信等级降为 original 并回写 SQLite 与兼容 JSON；原著行号来源不变。没有可靠来源的旧事件保持未知，不猜测其正史属性。
- 全文分析快照增加 analysisVersion。旧版本（尤其是未做别名分类的快照）不再进入写作上下文；重新执行 analyze-story 并生成当前版本快照后才恢复注入。

旧版 v3 分析批次缓存可以安全迁移到 v4：保留人物小传、事件、关系、情节线和伏笔分析，丢弃没有分类与原文证据的旧 aliases；缺失或损坏的批次仍按新提示词重跑。这样无需因别名 schema 变化而无条件重跑全书。


## 后续决策：统一故事图谱进入写作与审核（2026-11-06）

**决定：** 在现有全文分析流程中抽取故事核心、主线/支线、人物互动、伏笔、MacGuffin 和章级事件，并以 SQLite 中的节点/边组织。SQLite 仍是唯一数据库，不引入独立图数据库。节点、边保留章节来源引用；人物关系连接只使用规范姓名或唯一无歧义别名。审核包输出故事核心观察、MacGuffin、图谱、图谱质量摘要和跨章节人物互动样本。

**Agent/workflow：** 不增加专职人物 Agent、主线 Agent 或伏笔 Agent。重复分析会增加成本、上下文和相互冲突的解释。现有 analyze-story 负责形成统一故事档案；普通章节、长章节和终审复用按当前任务筛选的同一份上下文。写作阶段可采用、改造或舍弃这些参考；终审只检查明确事实、知识边界、物件归属和因果硬冲突，不检查人物弧光、伏笔回收或 MacGuffin 是否按分析建议执行。

**文学边界：** 图谱表达“模型根据所给原文观察到的关联”，不是作者意图、正史裁决或未来剧情路线。人物可以反复、背叛、误判、转变；伏笔可以不回收；主线可以偏航；MacGuffin 可以失去重要性。任何图谱完整度或边连接都不得成为写作验收标准。

**缓存边界：** analysisVersion=5 增加了故事核心和 MacGuffin 抽取，v3/v4 批次缓存不包含这些字段，不能迁移成 v5 成功结果。v5 使用独立缓存指纹并重新分析原文；旧缓存只保留为历史文件，不会被删除或覆盖。
