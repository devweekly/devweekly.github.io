# 从知识到题目：AI Interview Trainer 的知识建模、测量建模与金融领域实践

## 引言：要建的不是"题库"，而是 Interview Capability Assessment System

传统题库通常把最重要的数据结构定义成"一道题 → 一个答案"。这对考试系统已经足够，但对于一个希望持续理解用户能力、发现知识缺口、进行自适应训练的 AI Interview Trainer 来说，这个抽象层次太低了。

真正需要回答的问题不是"用户答对了哪一道题"，而是"用户掌握了什么知识、哪些概念掌握不牢"。进一步还要区分：他是不会这个概念，还是不会把概念应用到具体场景；他知道答案，但能不能解释原因；改变问题表面形式之后是否仍能答对。

需要特别说明的是，这个 repo 叫 **AI Interview Trainer**，不是"AI Learning Assessment Platform"。因此它的测量对象不只是 knowledge mastery——"知道知识"并不等于"具备面试能力"。一个人可以完全掌握 Kafka 的原理，却未必能在系统设计面试中快速识别约束、明确 trade-off、给出 architecture 并解释 failure mode。

这里的准确关系是：个体的 **Knowledge State** 与 **Competency State** 在 **Interview Context** 下汇合，表现出来的结果才是 **Interview Capability**（详见第十四节）。它不是与 Competency 并列的第三个层，也不是第三种 learner state，而是 $f(Knowledge\ State,\ Competency\ State,\ Interview\ Context)$ 的一次表现输出。

## 一、先把核心论断收敛清楚

全文的论点其实只有五条，后面各节都是对它们的展开或应用，不再重复论证：

1. **Knowledge Model 描述"知道什么"。**
2. **Competency Model 描述"能做什么"。**
3. **Assessment Blueprint 描述"准备测什么"。**
4. **Question 是对这些目标的一次可观测测量。**
5. **Variant 的价值是增加不同条件下的观察机会**——它本身不是 evidence，而是 evidence acquisition 的载体。

对应的核心模型是一条从 Domain 收敛到 Learner State 的链路，但**它不是一条线性管道**：最上层是 Domain；其下 Knowledge Model 与 Competency Model 并行展开——Knowledge Model 以 Concept / Knowledge Component 等知识单元组织领域知识，并在需要诊断时另行定义可作为 latent / mastery state 的 Knowledge Attributes（后者**不一定**是 Concept 的下层，见第二节）；Knowledge 与 Competency 两条支线汇入 Assessment Blueprint，Blueprint 同时声明 Cognitive Task、Assessment Target、Evidence Criterion 与 Context；由 Blueprint 可实例化出**多个** Item；Item 再分出 Canonical 与 Variant 两支；作答产生 Response，Response 经评分与解释成为 Evidence，最终更新 Learner State。

## 二、Concept / Knowledge Attribute / Skill / Competency 的边界

想要把这四者串成一条链是很自然的想法，但那会把本该是网状的关系压成层级树。

### Knowledge Model 的组织方式

**Knowledge Model 以 Concept / Knowledge Component 等知识单元组织领域知识；在需要进行诊断时，才另行定义可作为 latent / mastery state 的 Knowledge Attributes。**

注意这里的措辞，它比"概念的下层"要严格得多：

> **Knowledge Attribute 是为特定诊断目的定义的、预期能够由一组 item 的作答模式识别的知识/技能属性；它不等同于 Concept，也不是所有 Concept 都需要被建模成 Attribute。**

这句话里有三个限定条件缺一不可。**第一，它是为特定诊断目的"定义"出来的**，不是知识体系里天然存在的原子——CDM 中的 attribute 是模型假定的潜在认知属性，认知诊断模型要做的是把它与 item/task performance 建立随机关系，而不是把知识图谱节点直接搬过来当 latent variable。**第二，它必须可被一组 item 的作答模式识别**——孤立一道题支撑不起一个 attribute 的估计。**第三，并非所有 Concept 都需要被建模成 Attribute**——哪些 Concept 值得进一步拆成 diagnostic attribute，取决于诊断目标是否真的需要在那个粒度上区分学习者。

之所以不把它写成 Concept 的下层，是因为同一个 Concept 可以派生出性质差异极大的 attributes，其中有些已经明显混入能力或程序性知识。例如 `Concept = Duration` 可以产生：

- Attribute A —— 理解 duration 的定义
- Attribute B —— 理解 duration 与价格敏感性的关系
- Attribute C —— 能根据 duration 估算一阶价格变化

后两个已经不完全是"静态概念"了。因此不应把两者强制做成 ontology hierarchy。

### Concept、Knowledge Attribute、Competency 是交叉关系

把三者写成 `Concept → Knowledge Attribute → Competency → Assessment Target` 仍然是把网状关系压成层级。它们实际是多对多的交叉：

```text
Concept / Knowledge
        │
        ├──────────────┐
        ▼              ▼
  Knowledge        Skill /
  Attribute        Competency
        │              │
        └──────┬───────┘
               ▼
      Assessment Target
```

原因在于：

- 一个 competency 可能需要多个 attributes；
- 一个 attribute 也可以服务多个 competency；
- **Assessment Target 才是"这一次到底测什么"的具体交叉点。**

### 各层的例子

区分这四层时，例子的措辞很关键——"理解 X"这类说法本身已经带有 cognitive / competency 色彩，不宜用作 Knowledge Attribute 的例子。以 KV Cache 为例：

| 层次 | 示例 | 回答的问题 |
|---|---|---|
| Concept | KV Cache | 知识内容是什么 |
| Knowledge Attribute | 能识别 KV Cache 显存占用的主要决定因素 | 哪个属性是可诊断的 mastery state 变量 |
| Competency | 能根据给定配置估算 KV Cache 显存 | 能做什么 |
| Assessment Target | 验证能否正确完成估算并解释主要变量 | 这次具体要验证什么 |

如果跳过 Knowledge Attribute 这一层，读者很容易误以为 Concept 就是 Q-matrix 的 attribute——实际上并不一定。

## 三、Assessment Blueprint：Question 是实例化结果，不是笛卡尔积

把题目空间写成下面的笛卡尔积很有诱惑力，但它有两个概念问题：

- **Angle、Cognitive Task、Assessment Target 并不天然独立。** 例如 Angle 取 Debugging、CognitiveTask 取 Analyze、AssessmentTarget 取 Diagnose root cause，三者存在明显语义耦合，把它们当作正交维度做乘积会生成大量无意义的组合。
- **Difficulty 的处理也需要拿捏。** Difficulty 应**主要**作为 assessment / item parameter 管理，而不是被误当成知识内容本身。但它并非与生成无关——difficulty target 会影响 scenario 复杂度、prerequisite 数量、distractor quality、reasoning depth 与 information sufficiency，所以它虽不是 content ontology 的维度，却仍然是**生成约束**。

因此更严谨的模型是让 Blueprint 承载一组声明，再由它实例化出 Item。**同一个 Blueprint 可以实例化多个 Item**（Canonical A、Canonical B、Variant C 可以共享同一份 assessment blueprint），实例化时还要带上各自的表达/生成约束：

$$
Item_i = Instantiate(Blueprint,\ Constraints_i)
$$

Blueprint 至少包含这些字段：

| 字段 | 作用 |
|---|---|
| Knowledge / Concept | 这次测量涉及的知识内容 |
| Skill / Competency | 这次测量指向的能力目标 |
| Cognitive Task | 要求学习者执行什么认知过程 |
| Assessment Target | 这次具体要验证什么 |
| **Evidence Criterion** | **什么样的回答才算证明目标达成** |
| Context / Scenario | 在什么情境下测量 |
| Difficulty Target | 期望的题目难度参数 |
| Constraints | 题型、干扰项要求、misconception 覆盖等约束 |

**Evidence Criterion** 是其中最容易缺失、但对 Learner State 最关键的一层。没有它，`Assessment Target → Question → Score` 中间就缺了"什么证据支撑这个分数"这一环。例如：

| 要素 | 内容 |
|---|---|
| Assessment Target | 能解释 KV Cache 为什么降低 decode 计算 |
| Evidence Criterion | 必须指出 K/V 在历史 token 上可复用，并区分 prefill 与 decode；不能只说"减少重复计算" |

对本 repo 尤其重要，因为评分 rubric 与开放题 evaluation 已经存在，Evidence Criterion 正是它们与 Assessment Blueprint 之间的接口。

### Evidence Criterion 与 Scoring Rubric 的分工

既然 repo 里已经有评分 rubric，就必须防止出现两套并列的评分体系。二者的关系是上下游而非平行：

$$
Assessment\ Target \rightarrow Evidence\ Criterion \rightarrow Scoring\ Rubric \rightarrow Evidence
$$

一句话区分：**Evidence Criterion 定义"需要出现什么证据"，Scoring Rubric 定义"这些证据如何被评分"。**

前者是设计期的声明——在出题之前就写清楚，回答中必须出现哪些要点才算目标达成，它决定的是"什么样的事实可以成为 evidence"。后者是评分期的执行标准——给定证据出现与否、完整程度与正确性，把它映射成分数区间。把 rubric 直接当作 Evidence Criterion 用，会让 rubric 里那些关于分数分配的细节反过来污染测量设计；两者分开之后，换一套 rubric 或者调整分档粒度，都不会改变"到底要测什么"。

这也解释了为什么 Evidence Criterion 应该挂在 Blueprint 而不是挂在 Scoring 模块：它是测量意图的一部分，不是评分实现的一部分。

### Blueprint 与 Item Specification 的分工

最后补一层区分，它不需要引入新的领域对象，但能让 Blueprint 不再承担两种性质不同的职责：

$$
Blueprint \rightarrow Item\ Specification \rightarrow Item
$$

**Blueprint 回答"我想测什么"，Item Specification 回答"具体到这一次怎么出题"。** 二者混在一起时，Blueprint 既要承载稳定的测量意图，又要塞满一次性的生成参数，结果是同一份测量目标很难复用出多道题——而这恰恰是前面的 $Item_i$ 公式想要支持的能力。

以 Duration 为例，两层分开之后是这样的：

| 层 | 内容 |
|---|---|
| Blueprint | Concept = Duration；Competency = 利率风险分析；Target = 解释久期价格敏感性；Evidence Criterion = 须说明久期与价格的一阶关系并点明其局部有效性 |
| Item Specification | Role = PM；Scenario = 利率上行；Format = open；Difficulty = senior；Constraint = 不得直接给出票息 |
| Item | 具体的那道题 |

对本 repo 而言，这一层目前**隐含在 Blueprint 的 `Constraints` 里**——分离它不需要改数据结构，只需要在实例化时明确哪些字段属于稳定的测量意图、哪些属于这一次的生成参数。区分清楚之后，同一个 Blueprint 实例化出 Canonical A、Canonical B、Variant C 就有了自然的实现路径：它们共享 Blueprint，各自持有独立的 Item Specification。

## 四、Cognitive Process Dimension：Bloom 不是成长流水线

把 Remember、Understand、Apply、Analyze、Evaluate、Create 写成 `Knowledge → Understanding → Application → ...` 这样的"递进链"是误导性的。

Revised Bloom's Taxonomy 确实包含这六个认知过程，但它更适合被理解为**一个用于描述认知任务复杂度的分类维度**，而不是"一个人必须按这个顺序成长"的发展流水线。

同样重要的是：研究明确强调**不能仅凭题目中的动词判断 cognitive level**。"Explain / Analyze / Evaluate"这类词本身并不足以决定真正测量的认知过程，因此 assessment design 必须同时考虑知识类型与认知过程两个维度。这也是本文把 Knowledge Attribute 与 Cognitive Task 分开建模的原因。

## 五、Variant：增加可观测证据机会的 item mechanism

### Variant 不等于 Evidence

先纠正一个容易说过头的表述：Variant 本身**不是** evidence acquisition mechanism。严格讲三者是串行的：

$$
Variant \rightarrow Response \rightarrow Evidence
$$

即 **Variant 是 stimulus / item generation mechanism，Response 是 observation，Evidence 是经评分与解释后的 observation**。所以准确的说法是：

> **Variant 是增加可观测证据机会的 item mechanism，是 evidence acquisition 的载体，而不是 evidence 本身。**

### 两种 Variant 模式

原稿说 Variant 是"改变 reasoning path / presentation，而不破坏 measurement contract"。这句对当前 repo 是**错的**，因为 Offline Variant 本来就可能改变测量维度。当前 schema 明确区分两种模式：

| 模式 | 来源 | 允许声明 | 保持不变的是 |
|---|---|---|---|
| Presentation Variant | runtime（运行时兜底，默认关闭） | 只改写表达；结构上不允许声明测量面 | Assessment Identity |
| Assessment Variant | offline（离线池资产） | 可声明 `angle` / `cognitiveTask` / `assessment` | Knowledge Identity |

$$
\boxed{Presentation\ Variant \Rightarrow Assessment\ Identity\ Preserved}
$$

$$
\boxed{Assessment\ Variant \Rightarrow Knowledge\ Identity\ Preserved}
$$

### Knowledge Identity 到底是什么

"Assessment Variant 保持 Knowledge Identity"这句话必须给出定义，否则只是一个漂亮术语：

> **本文中的 Knowledge Identity 不是字符串相同，而是指：Assessment Variant 必须保持其 declared knowledge boundary——它可以改变 reasoning path、cognitive task 或 assessment target，但不能把主要被测知识从原 Blueprint 的知识边界迁移到另一核心 Concept / Attribute。**

这里刻意**不**定义成"同一 Concept / Attribute 集合"。因为"集合"这个说法会把 Concept 与 Attribute 绑得太死，而实际上两者可以错配：同一个 Concept 下面挂着不同的 diagnostic attribute，切换过去就可能已经跨出了 Knowledge Identity。以 Duration 为例，它可以对应：

- duration definition
- first-order price sensitivity
- convexity interaction

如果 variant 从"计算 duration"改成"比较 duration 与 convexity 对价格的影响"，说它仍在 `Duration` 之内是可以的，但它很可能已经不是**同一个 diagnostic attribute** 了。判断标准因此不是"是否还叫同一个概念名"，而是**测量重心是否仍在原 Blueprint 声明的知识边界之内**：若仍锚定"Duration 的价格敏感性"，只是引入 Convexity 做对照，则 Knowledge Identity 保持；若重心已移到 Convexity，就更像一个新的 assessment target 而非变体。

这个边界在本 repo 中不是隐含推断出来的，而是显式声明的——最终落到 `assessment.reasoningGoal` 上。

### VariantKind 与测量目标是两件事

另一点必须严格区分：当前 repo 的 `VariantKind` 只有四种取值，全部是**改写风格**：

| kind | 含义 |
|---|---|
| `surface` | 仅改写题干表达 |
| `context` | 在题干中加入简短工程上下文后改写 |
| `surface-options` | 改写题干 + 逐项改写选项 |
| `context-options` | 加入上下文 + 改写题干 + 逐项改写选项 |

并不存在 `comparison` / `debugging` / `decision` / `reasoning-path` 这些正式 VariantKind。把"生成风格"和"测量目标"混在一起，会再次把两个维度搅浑。当前设计其实是清晰的，四个字段各司其职：

| 字段 | 回答的问题 |
|---|---|
| `kind` | 怎么改写 |
| `assessment` | 测什么 |
| `cognitiveTask` | 要求什么认知过程 |
| `angle` | 从什么角度问 |

值得强调的是，`assessment.reasoningGoal` 是判定两条 reasoning path 是否**真的不同**的直接依据——只看 `angle` / `cognitiveTask` 并不够，两者相同也可能 path 相同。

## 六、Knowledge Graph 与 Q-matrix 是两个正交层

"Q-matrix 比 Knowledge Graph 更值得关注"这个判断太绝对了。二者解决的是不同问题，是**互补而非替代**关系。

| 层次 | 回答的问题 | 例子 |
|---|---|---|
| Knowledge Graph / Ontology | 知识之间是什么关系 | Duration related-to Convexity、depends-on Yield、applies-to Bond |
| Q-matrix | 哪道题测哪些属性 | Q1 测 Duration + Yield，Q2 测 Duration + Convexity |

把二者串起来，repo 的架构反而解释得更清楚：**Knowledge Graph 可以帮助组织和发现 Knowledge Attributes，但这不是 Q-matrix 理论的前提。**

Q-matrix 的本质是 $Q_{ij}=1$ 表示 item $i$ 是否需要 attribute $j$。它只规定 item 与 attribute 之间的必要性关系，**并不要求这些 attribute 一定派生自某张知识图谱**——它们也可以来自任务分析、专家标定或错误规则归纳。Tatsuoka 的 rule-space 工作强调的正是从 item response 中识别错误规则与认知状态，而不是"必须先建立知识图谱"。

因此在 assessment 层，真正落下来的是一张 **Q-matrix-like 的 item–attribute mapping**：明确每道题测量哪些属性。Knowledge Graph 是它的上游助力而非必要前置。

## 七、从 Item 到 Evidence：CDM / IRT / Knowledge Tracing 的分工

需要先声明一点：**下表是理论上的 architectural correspondence，不代表当前 repo 已经实现这些 psychometric models。** 它说明的是"这些研究传统各自解释了系统中的哪一部分"，而不是"本系统已经由这五个组件构成"。尤其 Deep Knowledge Tracing 是用 RNN 从交互序列预测知识状态，并不是 Q-matrix 的"自然下一步"。

几条研究传统在这个系统里各有明确位置，不应混为一谈：

| 概念 | 在这个系统里的角色 | 当前 repo 状态 |
|---|---|---|
| Knowledge Graph | Knowledge Model 本体 | **已实现**——`src/data/knowledge/` 的知识节点与关系 |
| Q-matrix | Item → Attribute 的映射 | **近似而非严格**——`topic` / `concepts` / `angle` / `cognitiveTask` 构成一张粗粒度映射表，不是标定过的 0/1 Q-matrix |
| IRT | Item 测量特性的参数化 | **明确未引入**——`domain/learner.ts` 记录了设计决策："不引入 Bayesian / ELO / IRT；升级评分模型的前提是现有信号被证明不够用" |
| Cognitive Diagnosis | 由作答反推属性掌握状态 | **未实现**——现有 proficiency 是均值启发式；`questionChallenger` 里的"区分度"是 LLM 粗粒度 `value` 标签，不是 IRT discrimination 参数 |
| Knowledge Tracing | Learner State 随时间的演变 | **未实现**—— Learner Profile 是 topic 维度的熟练度聚合，有时间维度的 trend / lastSeen，但不是序列模型 |
| Variant Pool | 对同一或相邻 assessment target 的额外观测机会 | **已实现**—— offline variant pool + runtime 兜底 |

"当前状态"这一列比概念对齐更重要：它明确了这套 psychometric stack 是长期演化方向，而不是项目现有能力。读者不应该因为文章把这些理论放在一起讲，就推断 repo 已经是一个完整的 CDM/IRT 系统。

关于 IRT 还需要补一句精度：IRT 用 item parameters 与 latent trait 对 item response 建模；**难度、区分度等参数是不同 IRT 模型中的典型参数，但并非所有模型使用完全相同的参数化**——Rasch 模型在这一点上就与常规 2PL/3PL 有明确区别。因此上表的"参数"应当理解为"测量特性参数化"这一类方法，而不是一套固定参数集。

传统考试关心 $Score = 78$，而认知诊断关心的是属性级的掌握刻画：

| 知识属性 | 掌握状态 |
|---|---|
| Attention | ✓ |
| KV Cache | ✓ |
| RoPE | ✗ |
| MoE Routing | ✗ |
| Quantization | ✓ |

Q-matrix 的示例（行是 item，列是 attribute）：

| 题目 | Attention | Softmax | Scaling | KV Cache |
|---|---|---|---|---|
| Q1 | 1 | 1 | 1 | 0 |
| Q2 | 0 | 0 | 0 | 1 |
| Q3 | 1 | 0 | 1 | 0 |
| Q4 | 1 | 1 | 1 | 1 |

需要注意：Q-matrix 研究特别强调 **item 与 attribute 的映射质量会直接影响认知诊断效果**。对当前 repo 而言，`topic` 更像分类标签，真正具有诊断价值的是 `question → concept(s) → required knowledge attributes → cognitive task → assessment target` 这条链路。

## 八、自动题目生成的正确链路（工程推论，而非论文结论）

Automatic Question Generation 的研究已经持续几十年。Kurdi 等人 2020 年的系统综述分析了 93 篇 AQG 研究，指出 controlled difficulty、question forms/structures、feedback 与 evaluation 等方面仍有明显不足；关于 Neural Question Generation 的综述则强调 educational value，而不仅是 fluent / relevant。

论文**真正支持**的是"自动生成流畅、相关的题目相对容易，但 educational value、difficulty、structure、evaluation 仍然困难"。

由此可以得出一个**工程推论**（注意：这是本项目的判断，不是上述综述直接给出的结论）：如果目标是可控、可诊断的 assessment，最好不要把"从文章直接生成最终题目"作为唯一链路，而应增加知识结构化、assessment blueprint 与 validation 等中间层。

推荐链路是：`Document → Knowledge Extraction → Concept Graph → Assessment Blueprint → Question Generation → Validation → Measurement Calibration`。这与当前 repo 的 Offline pipeline `Canonical → Oversample → Deterministic Validation → Deduplication → Quality Challenger → Top-N → Variant Pool` 是一致的。

## 九、业界实践：skills taxonomy 与 skills architecture

在职业技能与人才管理体系中，可以观察到一个共同方向：**从仅描述岗位或知识，逐渐转向结构化 skills、competencies、roles 与 assessment 的关联**。

这里不把它表述为"整个业界已形成统一的 Job → Skill → Competency → Assessment 标准链"——证据还不足以支撑这么强的判断。能确证的是：

- ESCO 将技能/能力和知识概念分别建模并构造大规模层级体系，其 skill pillar 包含超过 13,000 个概念，同时区分 knowledge、skills、attitudes/values 与 language skills/knowledge；
- CFA Institute 在 2026 年明确区分 **skills taxonomy**（详细能力列表）与 **skills architecture**（进一步把 skills 与 job roles、组织目标和业务结果关联起来）。

也就是说，业界至少已经把 **Taxonomy** 与 **Architecture** 区分开来了。

这对本项目的启发是：`Knowledge Taxonomy` 不等于 `Interview Question Taxonomy`。前者描述世界，后者描述"如何测量一个人对这个世界的掌握程度"。

## 十、金融一：先建 domain ontology，再建教育知识体系

金融领域有一个成熟的行业参考：**FIBO — Financial Industry Business Ontology**，由 EDM Council 主导、并由 OMG 标准化，以 OWL 等机器可处理形式描述金融业务中关注的事物及其关系，覆盖金融业务实体、金融工具、证券、贷款、指标、衍生品等领域。

但必须强调一点：**FIBO 是金融业务 ontology，不是金融教育 curriculum。** 因此正确的用法不是"FIBO → 金融知识体系"的直接映射，而是一条转换链：

`FIBO（domain ontology）→ Knowledge extraction / normalization → Education-oriented knowledge model → Assessment model → Questions`

也就是说，一个金融版 AI Interview Trainer 不应该从"什么是 Bond？"开始，而应该从 `金融世界 → Asset → Security → Debt Security → Bond → Coupon / Yield / Duration / Credit` 这条链开始。

金融知识体系可以进一步分为五层，前四层偏静态知识，第五层才是真正要训练的东西：

**Layer 1：Financial Entities**，即 Bank、Fund、Issuer、Investor、Broker、Exchange、Central Bank、Regulator、Clearing House 等参与主体。

**Layer 2：Financial Instruments**，覆盖 Equity、Bond、Loan、Option、Future、Forward、Swap、ETF、Fund、Mortgage 等工具类型。

**Layer 3：Financial Concepts**，即 Yield、Duration、Convexity、Volatility、Liquidity、Credit Spread、Default Probability、Capital Adequacy、Leverage、VaR、Expected Shortfall 等核心概念。

**Layer 4：Financial Processes**，包括 Trade Execution、Clearing、Settlement、Collateral Management、Credit Assessment、Portfolio Construction、Risk Management、Asset Allocation、Pricing、Hedging、Regulatory Reporting 这些流程环节。

**Layer 5：Decision / Competency**：

| 领域 | 要训练的能力 |
|---|---|
| Pricing | 能否判断价格变化 |
| Risk | 能否识别风险来源 |
| Portfolio | 能否进行资产配置 |
| Credit | 能否识别信用风险 |
| Trading | 能否选择交易策略 |
| Compliance | 能否识别违规行为 |
| Treasury | 能否管理流动性与利率风险 |

## 十一、金融二：时态化事实层与 Source Authority

### 时态化：不要给所有 Concept 强加 Valid Time

金融知识确实有强时间性，但把 Valid Time 提升为**所有 Concept 的统一属性**是错的。

`Duration` 的定义并不特别需要 Valid Time；而监管规则、资本要求、会计处理、税法、市场制度、交易规则则强烈依赖时间与 jurisdiction。

更好的模型是把知识拆成两层：

| 层 | 内容 | 需要的字段 |
|---|---|---|
| Stable Concept | 概念本身的定义，如 Duration | 基本无 |
| Contextual / Temporal Fact | 事实、规则、制度，如监管资本要求 | `validFrom` / `validTo` / `jurisdiction` / `market` / `source` |

这里需要精确区分两件事：**一个概念的定义本身**，与**使用该概念的金融产品/监管处理的 jurisdiction-dependent context**，不是同一回事。以 SOFR 为例，它本身是 USD overnight financing reference rate；说"SOFR 的定义绑定 US jurisdiction"并不准确，准确的表述是：**使用 SOFR 的金融产品与监管处理具有 jurisdiction-dependent context**。混淆二者会让知识模型过度绑定。

否则知识库很容易出现：概念没有错，但是答案在当前时间/市场环境已经不成立。

### Source Authority：Authority 不是单轴等级

金融与 AI 知识的一个关键区别不只是 Time、Market、Role、Scenario，还有 **Authority / Source**。

关键在于：**Authority 是多维的，取决于 source type、jurisdiction、applicability、date 与 claim type，不能简单排成单一等级。** 监管规则、法律法规、会计准则、交易所规则、央行文件、公司披露、行业最佳实践、教材、分析师观点这些来源，拥有的是**不同类型与不同范围**的 authority：

| 来源 | authority 的范围 |
|---|---|
| SEC / FCA / ECB 等监管文件 | 对所辖领域的法律/监管权威 |
| FASB / IFRS 会计准则 | 对会计处理准则的权威 |
| 公司 10-K / 财报 | 对公司自身披露事实的 primary source |
| CFA / 教材 | 对教育性定义有很高参考价值 |
| 分析师报告 | 对"观点/预测"有价值，但不是法规依据 |

因此金融知识节点最好携带 `source`、`sourceType`、`authority`、`jurisdiction`、`validTime` 五个字段。这一层在通用 AI 知识里几乎不需要，但在金融里是刚需。

## 十二、金融三：Knowledge Type 决定题目形态

需要说明的是，下面这组 **Knowledge Type 是针对本项目金融领域的工程化分类，不是 Revised Bloom Taxonomy 的标准 Knowledge Dimension**，不应被当作教育测量领域的标准 taxonomy 使用。

| Knowledge Type | 典型内容 | 题目形态 |
|---|---|---|
| Conceptual | 概念定义与关系 | 解释、辨析 |
| Procedural | 流程与操作顺序 | 排序、步骤补全 |
| Quantitative | PV、Duration、Convexity、VaR、Option Greeks、Credit Metrics、Capital Ratios | 计算与估算 |
| Rule-based | Accounting / Capital / Trading / Compliance rules、Suitability、Disclosure | 规则适用判断 |
| Case-based | Market event、Credit event、Liquidity event、Fraud、Risk event、Regulatory event | 案例分析与决策 |

需要强调的是，这些维度是**可选声明**而非必须做笛卡尔积：金融 Item 的 Blueprint 可以有选择地声明 Knowledge Type、Competency、Context、Role、Decision 等因素，**并非每个 item 都需要全部维度**。写成乘积形式会让人误以为可以做组合枚举，从而产生大量无意义组合。

## 十三、金融四：Role / Scenario / Decision 与 Misconception

### Role / Scenario / Decision

金融知识高度依赖场景。把维度取成 Concept 为 Duration、Scenario 为 rising rate、Role 为 Portfolio Manager、Decision 为 hedge or rebalance、Difficulty 为 senior，就能得到：

> "作为一个固收投资组合经理，如果未来 6 个月利率存在持续上行风险，而组合 duration 明显高于 benchmark，你会如何调整？哪些因素会导致 duration hedging 不完全有效？"

这已经比"什么是 duration？"高了几个层次。同一个 Duration 概念也可以衍生出不同层级的题：

| 层级 | 示例问题 | 定位 |
|---|---|---|
| Concept | Duration 是什么？ | 基础知识题 |
| Apply | 一个债券 duration 为 5，利率上升 50bp，价格大致如何变化？ | 应用题 |
| Analyze | 为什么两个 duration 相同的债券，在利率冲击下可能产生不同价格变化？ | 分析题 |
| Compare | Macaulay Duration 与 Modified Duration 在风险管理中的区别是什么？ | 比较题 |
| Scenario | 当前收益率曲线快速陡峭化，投资组合主要持有长久期国债，应该关注什么风险？ | 场景题 |
| Decision | 如果目标是降低利率风险，同时尽量保持 carry，应该如何调整组合？ | 决策题 |
| Debug | 风险模型报告的利率敏感度与实际 P&L 长期偏差较大，优先检查哪些环节？ | 诊断题 |

这里不是要否定 Define / Recall——对 CFA、财务基础、从业资格考试或初级岗位而言，Define / Recall 本身就是必要能力。准确的表述是：**Recall 不足以代表高级能力**。因此高级金融 interview assessment 不应主要停留在 Define / Recall，而应逐渐增加 Explain、Calculate、Compare、Interpret、Diagnose、Decide、Design。

### Misconception 建模

以 `Concept = Bond Price / Yield` 为例，常见错误认知包括：

| 错误 | 描述 |
|---|---|
| 错误 1 | 利率上升 → 所有债券价格必然等比例下降 |
| 错误 2 | duration 越高 → 债券收益率越高 |
| 错误 3 | duration 完全决定价格变化 |
| 错误 4 | credit spread 与 risk-free rate 是同一个东西 |

于是题目不再只是问"正确答案是什么"，而是要问"这个 distractor 对应哪一种错误模型"。这实际上更接近 Cognitive Diagnostic Assessment。因此金融题库应围绕 Concept 同时维护 Canonical understanding、Common misconceptions、Diagnostic signals 与 Assessment items，这比单纯的 answer/explanation 更有长期价值。

## 十四、Interview Capability：competency 在面试情境下的综合表现

### 不要把三者并列相加

如果把 Knowledge、Competency、Interview Capability 写成简单的加法并列，会造成"双重 competency"——因为 Interview Capability 本身很可能已经包含 Competency（Technical Understanding、Reasoning、Decision Making 本身就是 competency）。

更严谨的关系是汇合而非并列：

```text
Knowledge / Knowledge State
            +
Competency / Skill State
            +
    Interview Context
            ↓
  Interview Capability
```

也就是说，**Interview Capability 是在 interview context 下表现出来的综合 competency**，而不是与 Competency 平行竞争的第三个层。

更进一步，它**不是第三种 state**。Learner State 只有 Knowledge State 与 Competency State 两个，Interview Capability 是这两者在特定情境下的函数输出：

$$
Interview\ Performance = f(Knowledge\ State,\ Competency\ State,\ Interview\ Context)
$$

把它写成第三种 state 会造成两个问题：一是 learner profile 里凭空多出一个需要和另外两个 state 同步更新的变量；二是它无法脱离情境被独立估计——换一个 interviewer、换一道题，测到的 capability 就会变化，因为它本来就是 state 与 context 的联合结果，不存在一个脱离情境的内在量。所以本文把它定位为**表现**而非**状态**：state 留在 learner 侧按 topic / competency 维度跟踪，capability 则在每次会话产出并回收为证据。

### 面试情境额外测量的东西

即便 Competency 相同，面试情境仍会额外暴露一组能力，它们是 competency 在特定压力与约束下的表现：

| 能力 | 含义 |
|---|---|
| Communication | 能否把复杂内容讲清楚 |
| Reasoning | 推理链条是否完整、可追溯 |
| Decision Making | 能否在信息不完全时做出决策 |
| System Design | 能否给出可落地的结构 |
| Trade-off Judgment | 能否识别并权衡冲突约束 |
| Technical Depth | 能否被追问到足够深 |
| Experience | 是否有真实工程判断 |
| Uncertainty Handling | 面对不确定时是否诚实、是否有处理方式 |

因此 Question 是这三者共同的观测工具。尤其对 senior 面试而言，"知道知识"与"具备面试能力"之间的鸿沟恰恰是最需要被测量出来的部分。

## 结论

本文的核心论断就是开头那五句话，这里换一种更紧凑的写法收束：

- Knowledge Model 描述"知道什么"，Competency Model 描述"能做什么"，Assessment Blueprint 描述"准备测什么"。
- Question 是对这些目标的一次可观测测量，即 $Item_i = Instantiate(Blueprint,\ Constraints_i)$——一个 Blueprint 可实例化多个 Item，而不是各维度的笛卡尔积。
- Difficulty 主要作为 assessment / item parameter 管理，同时作为生成约束；Evidence Criterion 负责回答"什么回答才算达标"。
- Variant → Response → Evidence：Variant 是 evidence acquisition 的载体而非 evidence 本身；Presentation Variant 保持 assessment identity，Assessment Variant 保持 **declared knowledge boundary**——可改 reasoning path / cognitive task / target，但不能把主要被测知识迁移出原 Blueprint 的知识边界。
- Evidence Criterion 定义"需要出现什么证据"，Scoring Rubric 定义"这些证据如何被评分"，二者上下游而非并列。
- Knowledge 与 Competency 是交叉关系而非层级；Interview Capability 不是第三种 state，而是 $f(Knowledge\ State,\ Competency\ State,\ Interview\ Context)$ 的表现输出。

把这条链路钉死，剩下所有结构就都有了归位方式：

$$
\boxed{Knowledge \rightarrow Competency \rightarrow Assessment\ Blueprint \rightarrow Item\ Specification \rightarrow Item \rightarrow Response \rightarrow Evidence \rightarrow Learner\ State}
$$

Knowledge Graph、Q-matrix、IRT、Cognitive Diagnosis 与 Knowledge Tracing 从不同角度解释这条链路的不同环节，分别对应知识结构、item–attribute 映射、item 测量特性、属性诊断与 learner state 演化，**它们不是五个可以简单串起来的组件，也不代表当前 repo 已经实现了这套 psychometric stack**。把这条分工守住，系统就不会把"多生成几道题"误当成"多获得一些诊断能力"。

这也是当前 repo 最值得继续演化的方向：最终不是建设一个"拥有很多题目的题库"，而是建设一个能够回答**"一个人究竟掌握了什么、能做什么、还缺什么、缺在哪一种能力上、下一步应该测什么"**的 Knowledge & Competency Assessment System。
