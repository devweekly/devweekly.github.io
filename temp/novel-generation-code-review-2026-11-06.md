# novel-generation 代码分析与精简建议

> 分析日期：2026-11-06  
> 评估基准：`src/content/blog/ai-long-form-story-writing-2026.md`（《AI 如何写好长篇故事》）  
> 审查对象：`tools/novel-generation/` 当前默认分支代码、测试、README、AGENTS 与 ARCHITECTURE。  
> 范围：代码审查与改进建议；本报告不直接修改小说生成实现。

## 结论

当前项目已经不是简单的 Prompt 拼接器。它具备原文导入与检索、全文分析、人物和情节知识库、普通章节与长章节两条生成流水线、结构化审查、有限修复、故事状态持久化和阶段恢复。核心方向是正确的，尤其是把文学性置于结构完整性、统计指标和分析覆盖率之上，并把原文事实、推断和项目原创分开处理。

下一阶段不建议继续增加 Agent 数量或再造一套记忆系统。真正值得投入的是：减少重复的全文改写调用；让人物目标、选择、代价和事件后果成为更可靠的写作上下文；把故事事实与读者已知信息区分开；让伏笔和情节线从“分析结果”变成按需检索的辅助信息；同时降低两条写作流水线的维护成本。

从代码结构看，主要问题不是缺少功能，而是已有功能逐渐叠加后，职责边界、数据重复和调用成本开始变得复杂。建议先做小范围重构和质量验证，不进行大规模架构替换。

## 一、按长篇叙事原则检查当前实现

### 1. 故事事实与读者信息：目前覆盖不完整

文章强调，故事世界里实际发生的事件，与作者向读者披露这些事件的顺序并不是一回事。悬念、惊奇和好奇心依赖读者当前掌握的信息，而不只是事件本身是否记录完整。

当前实现已经有几类相关数据：

- `story_state`：承接续写中的人物、事件、事实、情节线和连续性备注。
- `story_analysis` / `novel_*`：保存全文人物、关系、情节线、伏笔和章节事件分析。
- `story-analysis-context.ts`：按当前任务从分析快照挑选少量内容，作为可选参考注入。
- `chapter-review.ts`：检查人物知识、时空、因果、能力和世界规则等连续性问题。

但这些数据主要描述“发生了什么”和“人物现在是什么状态”，还没有形成足够清晰的“读者在当前章节之前知道什么”。人物知道某个秘密，不代表读者已经知道；某个事件已经发生，也不代表应该立即向读者解释。

**建议：增加轻量的叙事信息状态，不要再增加一套庞大的知识库。**

可以先在章节规划和审查结果中表达三类信息：

1. 人物知识：哪些角色知道、误解或怀疑什么。
2. 读者知识：哪些事实已经明确披露，哪些只是暗示，哪些仍被隐藏。
3. 披露意图：本章是揭示、误导、强化怀疑，还是暂时不触碰。

这不需要为每个细节建立数据库实体。先让章节蓝图能够描述关键秘密和披露策略，再由终审检查是否意外泄底、前后矛盾或把应当保留的悬念解释掉。只有在真实写作中反复出现信息管理问题时，再考虑持久化。

### 2. 人物目标与选择：数据字段不少，写作决策还可以更聚焦

`story-analysis.ts` 已抽取人物欲望、性格矛盾、关系、已观察到的变化和可能的成长方向；`story-state.ts` 则保存人物 profile、当前目标、知识、关系和 arcMilestones。写作提示也要求人物通过行动和选择推动情节。

这与文章中的 Want / Need、人物矛盾、外部/人际/内部冲突原则一致。但目前人物数据比较容易变成“字段齐全的人物档案”，而不是能帮助模型作出具体选择的材料。

**建议：把人物上下文从静态属性转向当前情境中的决策压力。**

在每章或每场需要时，优先提供：

- 当前人物想得到什么，以及眼下最怕失去什么；
- 他掌握的信息、错误判断和不知道的事情；
- 他与场景中其他人物的利益冲突；
- 当前可选行动及其可能代价；
- 最近一次真正改变人物处境的选择。

这些内容不必全部成为必填字段，也不应要求正文逐项解释。可以由规划 Agent 根据现有 profile、状态和场景生成一个简短的“当前决策上下文”。状态管理员只记录正文已经发生的变化，不反过来要求正文为了填字段而安排人物弧光。

反派视角也应作为按需推演，而不是每场固定启动一个“反派 Agent”。只有出现策略博弈、对抗或重要谈判时，才要求模型站在对手掌握的有限信息和资源条件下，推演其合理选择。

### 3. 情节因果与多层结构：已有主线规划，缺少轻量的长期约束视图

普通章节已有主线方案、创意备选和主编蓝图；长章节已有场景蓝图。全文分析也保存主线、支线、关键转折和未解决问题。整体上已经覆盖“全书方向—卷—章—场景”的多层结构。

目前更值得补的是情节之间的关系，而不是更复杂的情节树。一个事件可能是另一个事件的原因、前提、误导或后续兑现；只记录情节线标题和状态，仍可能让模型重复相似冲突，或者忘记某个决定造成的长期后果。

**建议：先使用现有数据构造轻量的因果关联，不急于引入图数据库。**

优先支持四种关系：原因、依赖、信息揭示、后续兑现。可以从事件 ID、章节 ID、情节线 ID 和伏笔 ID 之间建立关系。第一阶段只用于规划上下文和审查，不把它变成自动剧情约束，也不要求每个事件都必须连边。

卷级主线仍由作者或规划阶段决定；中间路径允许变化。不要让系统为了“图谱闭合”强迫故事回收所有伏笔。

### 4. 连载节奏与升级闭环：当前缺少题材相关的显式推演

文章指出，持续升级不应只是数值越来越大，而应改变人物的社会位置、信息权限、行动范围、责任和关系，并产生新的代价与冲突。

目前 `story-analysis.ts` 会抽取情节线和发展可能性，章节规划也能考虑冲突、悬念和后续空间，但没有明确提示模型检查“本次突破改变了什么，以及因此出现了什么新问题”。

**建议：把升级闭环作为题材可选的规划检查，而不是全类型小说的固定模板。**

对于升级、冒险、经营、权力斗争等适用题材，规划时询问：人物获得了什么新能力或位置？付出了什么成本？哪些原本无法接触的人、信息或资源现在出现了？新位置又带来了什么义务、威胁或关系变化？不适用的章节无需输出这些内容。

## 二、代码结构与冗余点

### 1. 普通章节与长章节存在明显的流程重复

主要位置：

- `src/workflow.ts`
- `src/long-chapter.ts`
- `src/chapter-review.ts`
- `src/stage-cache.ts`
- `src/story-state.ts`

两条流水线都要读取初始状态、组织公共上下文、调用模型、写阶段缓存、审查正文、执行有限修复、提取状态并保存。长章节额外增加场景拆分、逐场检索、滚动上下文和跨场审查。

目前通过共享 `chapter-review.ts`、`stage-cache.ts` 和 `workflow.ts` 的状态合并函数复用了一部分逻辑，但两条主流程仍各自维护大量相似的 Prompt 组织、缓存调用、产物写入和状态提取代码。以后修复一个通用问题，容易只改到其中一条路径。

**建议：抽取少量稳定的共享服务，不要抽象成通用 Agent 框架。**

优先提取三个边界：

- `ChapterRunContext`：统一装载世界设定、状态快照、检索资料、分析参考、模型配置和运行目录。
- `StageRunner`：统一阶段调用、缓存指纹、模型回退记录、输出校验和阶段产物写入。
- `Finalization`：统一最终审查结果处理、状态提取、状态校验、数据库提交和质量摘要。

普通章节和长章节继续各自控制业务流程。长章节的逐场循环、全章上下文和跨场修复不应被塞进通用抽象。

### 2. 普通章节的对白修订与文风修订可能重复劳动

`workflow.ts` 当前先生成初稿，再调用人物对话编辑，之后调用叙事声音编辑。两个阶段都需要读取整章正文，也都可能调整句子、动作、节奏和叙述表达。提示词虽然限定了职责，但模型很难保证“只改对白”或“只改叙述声音”，后一个阶段还可能覆盖前一个阶段的有效改动。

这会产生三个问题：额外模型调用和 token 成本；全文多次改写导致原本有效的表达被抹平；定位问题时很难判断是哪一轮引入了退化。

**建议：改为一次主修订 + 按需专项修订。**

默认由一个文学编辑阶段同时检查人物对白和叙述声音，但要求优先保留有效段落，只修改确实存在的问题。只有当对白存在明显同质化、人物声音混乱，或叙述视角和语气确实失控时，才启动专项修订。专项修订应尽量返回局部替换或带位置的修改建议，而不是无条件重写整章。

长章节逐场修订也应遵循同一原则：不要为了每个场景都执行相同的润色步骤而增加调用。场景质量足够时可以跳过。

### 3. 公共 Prompt 上下文重复注入，存在成本和注意力浪费

`workflow.ts` 的 `common` 包含世界设定、完整故事状态、前情摘要、检索原文、全文分析参考、续写材料、风格资料和任务 brief。主线 Agent、创意 Agent、主编、正文生成、对白编辑和文风编辑多次注入这份公共上下文，再叠加各阶段自己的输入。

重复注入本身不一定错误：独立 query 不共享会话，需要每次提供必要上下文。但目前所有阶段并不需要相同粒度的信息。例如创意发散未必需要完整人物状态和大段原文；对白编辑需要人物声音和当前正文，却不一定需要整份世界设定；状态提取需要旧状态和最终正文，不需要创意备选。

**建议：按阶段构建上下文，而不是所有 Agent 共用同一个大 Prompt。**

将上下文分为任务必需、事实核对、人物相关、文学参考四类。每个阶段只取所需内容。尤其是完整 `story_state`，应优先改成当前场景涉及人物、相关情节线、关键事实和必要连续性备注的子集；状态管理员仍然读取完整旧状态，以便正确合并。

不要简单地把上下文全部压缩成摘要。事实核对需要保留可回查的原文证据，人物和读者知识也不能被过度摘要丢失。

### 4. 多套分析入口的职责边界需要收敛

当前有 `analyze`、`analyze-story`、`analyze-world`、`index-story`、`analyze-arcs` 等入口：

- `analyze`：按检索片段抽取候选实体、事件和关系。
- `analyze-story`：按章节批次分析人物、情节线、伏笔、事件和发展可能性。
- `analyze-world`：多 Agent 文件交接，形成主线、创意、文风、人物关系、世界观与连续性报告。
- `index-story`：把章节目录与检索片段映射，建立成书知识库结构。
- `analyze-arcs`：基于章级事件生成卷级梗概。

这些命令并非完全重复，但它们都在不同程度上分析人物、事件、关系、主线或卷级结构。用户需要理解多个入口的执行顺序，代码也需要维护多种结果格式和数据来源。

**建议：保留不同分析目的，收敛公共底层和默认路径。**

`index-story` 是确定性索引步骤，应保留。`analyze-story` 作为全文分析主入口。`analyze-world` 更像研究/人工协作工作台，不应成为正式写作的必需依赖。`analyze` 只有在需要逐片段证据标注或实体证据检索时才运行，不应被描述成续写前的必做步骤。`analyze-arcs` 可以作为可选的卷级摘要生成，不必维护独立的另一套人物或情节状态。

下一步应明确每类数据的唯一写入来源，避免同一人物或事件在多种分析产物里被反复解释、互相覆盖。

### 5. 故事状态、全文知识库和分析快照需要保持单一事实来源

当前将 SQLite 故事状态、`story_analysis` 快照和 `novel_*` 成书知识库分开，是合理设计：

- 故事状态回答“续写现在处于什么状态”。
- 成书知识库回答“已经写出的全文包含什么”。
- 分析快照保存模型对全文的归纳和创作可能性。

不建议把它们合并成一张表，也不建议让全文分析直接覆盖当前人物状态。但应进一步明确哪些字段是权威数据、哪些是可重建投影、哪些是模型推断。特别是人物关系、情节线和伏笔在分析快照与故事状态中可能同时存在，必须避免将“模型认为可能如此”自动升级成已发生事实。

**建议：保留现有三层，只加强来源标记和写入边界。** 不新增第四套长期记忆，也不要把所有分析报告全文反复注入写作上下文。

### 6. CLI 与路径处理逐渐成为集中式入口负担

`src/cli.ts` 同时承担命令解析、参数验证、模型诊断、语料分析、数据库查询、章节生成、回归实验和输出格式化。当前规模尚可运行，但新增命令会继续扩大入口文件，也增加参数间组合错误的风险。

**建议：不必引入命令框架。** 将每个命令的参数解析和执行逻辑移入对应的 command 模块，CLI 只负责分派。参数校验可以用已有 Zod 依赖定义小型 schema，尤其是 `--shard`、`--merge-only`、`--limit`、`--resume-dir` 等存在组合约束的参数。

同时统一项目根目录和 world 目录解析，不要让各模块依赖当前工作目录的隐式假设。当前文档要求所有命令从工具目录执行，短期可保留，但路径解析最好集中管理。

### 7. 阶段文件很多，但不应简单删除

当前每个阶段会保留 Prompt 结果、草稿、修订稿、审查报告和状态更新。对模型调用失败、恢复和质量退化定位来说，这些产物有价值。

问题是所有阶段产物都默认长期保留，运行目录可能越来越大；有些中间文件只是完整正文的多个副本。

**建议：把“恢复必需”与“审计诊断”区分开。**

- 恢复必需的阶段输出、指纹、manifest 和初始状态快照必须保留。
- 最终正文、最终质量摘要、最终状态更新和审查结论应长期保留。
- 中间全文副本可以按配置保留；默认保留最近一次运行的必要文件，成功归档后允许清理冗余全文副本。
- 发生失败或用户要求诊断时，保留完整运行现场。

清理策略必须在阶段完成和最终提交后执行，不能删除恢复所需的 checkpoint。

## 三、优先修复与验证的工程风险

以下是建议在下一轮代码修改中优先验证的项目。它们比增加新的 Agent 更影响可靠性。

### P0：状态提交必须与章节归档形成可恢复的一致性边界

当前流程先完成正文审查，再提取状态并写入 SQLite，同时还保存阶段文件和兼容 JSON 快照。中断可能发生在数据库提交、文件写入或章节归档之间。

`loadRunStoryState` 已保存初始状态快照，能避免恢复时重复叠加状态；这是正确方向。但还需要验证数据库提交成功而运行归档失败、状态 JSON 快照写入失败、同一 run 重复恢复等路径。

建议给每次运行明确状态：`drafted`、`reviewed`、`state_prepared`、`committed`、`archived`。不必引入消息队列或分布式事务；使用 SQLite 事务和运行 manifest 即可。恢复时根据阶段状态判断是重试归档还是重做状态提交，不能重复应用同一章的增量。

### P0：模型输出解析与业务校验必须分开

`model-json.ts` 已提供平衡括号截取、控制字符修复和 JSON 解析；`story-analysis.ts`、`world-analysis.ts` 等模块使用共享解析器。这减少了多处重复实现。

但“能够解析 JSON”不等于“分析结果正确”。尤其是人物归并、事件来源、章节归属、伏笔状态和人物关系，仍需要业务规则验证。建议所有模型输出入口都采用同一顺序：提取 JSON、语法修复、Zod schema、业务约束、原文证据校验。修复只允许处理格式错误，不能自动编造缺失字段或把不确定结果变成确定事实。

### P1：全文分析合并必须保证批次完整性和可重跑性

`story-analysis.ts` 已有批次缓存、语料哈希、批次布局、`maxChars`、模型和 Prompt 版本指纹，并对 `--merge-only` 与 shard/limit 的非法组合做保护。这些机制应保留。

建议进一步验证：部分批次失败时旧的完整快照是否继续可用；同一语料更换模型或 Prompt 后是否正确失效；并行 shard 是否可能覆盖彼此文件；分析版本变化时是否能明确区分旧快照和新快照。只有全部批次通过业务校验后，才允许替换当前完整快照。

### P1：长章节终审需要防止“局部通过、整体失真”

`long-chapter.ts` 已有逐场生成、滚动上下文、分批审查、逐场润色和全章终审。全章终审是必要的，不能因为逐场审查通过就省略。

建议重点验证修复后的场景是否仍保持前后场人物位置、人物知识、物品归属、时间顺序和情绪连续性。修复 Agent 不应只满足单条问题描述而引入新的跨场矛盾。测试应覆盖多场景问题定位、一个问题影响多个场景、场景重排和修复后复查失败。

### P1：模型回退与阶段缓存必须记录实际模型身份

当前缓存应基于实际模型解析结果和回退链，而不是只记录用户传入的 `--model`。普通与长章节路径都应遵循同一规则。模型配置、Prompt、thinking/effort profile 或输入资料变化时，旧阶段结果不能被误复用。

另外，严格模型模式应在普通和长章节、分析和回归路径中表现一致。模型回退是运行可靠性策略，不应让用户误以为最终正文由指定模型生成。

### P2：检索召回质量优先于引入向量数据库

当前 `library.ts` 使用 BM25 风格词项和中文二元组检索，适合精确词语和名称查询，但对隐喻、别名、跨段指代和语义相近表达存在局限。

不建议仅因为 RAG 常用向量检索就立即增加向量数据库。先用真实续写任务建立检索评测集：问题、正确章节/片段、必须命中的事实、错误召回。比较现有 BM25、别名扩展、章节/人物元数据过滤和混合检索的召回率与噪声。只有现有方法在真实案例中反复漏掉语义相关证据，再增加 embedding 或 reranker。

## 四、建议去掉或合并的内容

| 项目 | 建议 | 原因 |
|---|---|---|
| 默认每章分别执行对白编辑和文风编辑 | 合并为一个默认文学编辑阶段，专项任务按需启用 | 两轮都重写全文，成本高且容易相互覆盖 |
| 所有 Agent 共用完整 `common` 上下文 | 改成阶段级上下文构造 | 不同阶段需要的信息不同，减少重复 token 和无关注意力 |
| 每次运行无条件保留所有全文中间版本 | 保留恢复与审计必需产物，其余按需归档 | 避免输出目录膨胀，但不损害故障恢复 |
| `analyze` 被当作全文续写前置步骤 | 限定为证据抽取的可选任务 | 全量逐片段调用成本高，不应阻塞正常写作 |
| `analyze-world` 作为常规生成链依赖 | 保留为研究/人工协作工作台 | 文件交接分析与正式章节生成目标不同 |
| 另建一套人物弧光状态机 | 不做 | 人物可以反复、倒退和突然改变，状态机容易把人物写成流程图 |
| 立即增加图数据库、向量数据库或常驻 Agent | 暂不做 | 当前瓶颈主要是上下文组织、重复改写和数据边界，不是缺少基础设施 |
| 以句长、对白比例、伏笔回收率作为自动质量门槛 | 继续保持关闭 | 统计指标不能替代文学判断，也可能诱导模型改坏正文 |

## 五、建议补充的能力，但控制实现规模

### 1. 章节规划中的“读者期待”检查

在章节蓝图中允许模型说明：本章延续了读者正在等待的哪个问题，本章会兑现什么局部回报，又会留下什么新的疑问。不是每章都必须制造悬念；日常、关系和情绪章节也可以兑现阅读期待。

终审只检查是否发生明显的信息泄露、前后矛盾或承诺被无意遗忘，不要求每章都以钩子结尾。

### 2. 对手决策模拟按场景触发

当章节涉及博弈、追捕、谈判、权力冲突或高智商对抗时，规划阶段可以临时推演对手视角：对手掌握什么信息、有哪些资源、风险偏好如何、当前最合理的选择是什么。再让主角应对。

这比长期维护一个固定的“反派 Agent”更简单，也更符合文章中对手应有独立逻辑的原则。

### 3. 伏笔管理增加“最后触及”和“当前读者认知”

现有全文分析已保存伏笔首次出现、可能解释、候选兑现方式和状态。可以补充最后一次推进章节，以及读者当前能观察到的线索强度。它帮助规划阶段避免长期遗忘，也避免每章都机械提醒模型“回收伏笔”。

伏笔的可能解释必须保持不确定；分析结果不能自动变成作者承诺。

## 六、测试与验收建议

当前项目有 TypeScript 构建和 node:test 测试基础。后续不应只增加纯函数测试数量，而应补充能够暴露长篇创作问题的场景测试。

建议新增以下回归用例：

1. **人物知识边界**：角色不能使用尚未获知的信息；读者已经知道但角色不知道的秘密不能被无意写进角色内心。
2. **人物选择与代价**：角色在资源、关系或风险发生变化后，行动应能承接当前处境；不要求每次都符合人物标签。
3. **因果与长期后果**：前章重大决定在后续章节仍能被检索和体现，不因摘要压缩而消失。
4. **伏笔披露控制**：模型能区分已揭示、仅暗示、角色误解和作者暂时隐藏的信息。
5. **升级后的新冲突**：能力或地位提升应允许带来新的限制和责任，而非只生成更强敌人。
6. **编辑阶段非破坏性**：专项润色不得删除有效情节、人物互动、信息揭示和情绪落点；无问题的段落应允许原样保留。
7. **恢复与幂等性**：在状态提交前后、章节归档前后中断并恢复，不重复提交同一章节的状态变化。
8. **长章节跨场连续性**：人物位置、物品、知识、时间和未完成行动在场景之间保持一致。

质量评估应以盲评和人工阅读为主，至少分别观察：文学感染力、人物声音、人物行为可信度、情节吸引力、信息披露效果、连续性硬伤。不要把这些维度简单合并成一个总分，更不能让总分直接决定自动重写。

## 七、实施顺序

建议按以下顺序推进，先控制改动面：

**第一阶段：减少不必要的生成调用**

- 将对白与文风编辑合并为默认文学编辑阶段，保留按需专项修订。
- 为各阶段建立最小必要上下文，避免重复注入完整状态和全部资料。
- 对长章节逐场修订增加跳过条件。
- 保留阶段缓存、实际模型指纹和失败现场。

**第二阶段：提高长篇叙事记忆质量**

- 在章节规划中增加人物当前决策压力和读者信息状态。
- 用现有事件、情节线和伏笔 ID 建立轻量因果关联。
- 增加按场景触发的对手视角推演。
- 让升级闭环只在适用题材和情节中启用。

**第三阶段：收敛工程结构**

- 抽取共享的运行上下文、阶段执行和最终提交逻辑。
- 拆分 CLI 命令实现。
- 明确 `story_state`、`story_analysis` 和 `novel_*` 的唯一写入来源。
- 为阶段产物增加保留与清理策略。

每一阶段都应使用同一批代表性章节做前后对照。不能仅以模型调用次数下降或测试通过作为成功标准；如果减少一次编辑调用后人物对白和叙事声音明显变差，就不应为了节省成本而强行合并。

## 最终判断

`novel-generation` 当前最有价值的部分是：文学性优先原则、原文事实与项目原创的来源隔离、可恢复的阶段执行、结构化连续性审查，以及全文分析结果作为可选参考而不是剧情命令。

最需要控制的是“工程流程逐渐替代小说创作”：规划 Agent、创意 Agent、对白 Agent、文风 Agent、审查 Agent 和状态管理员都可以帮助写作，但它们不应该让一章小说经过太多次无差别重写，也不应该把人物、伏笔和情节变成必须逐项完成的任务清单。

因此，下一轮最值得做的不是增加 Agent，而是减少重复改写、缩小各阶段上下文、增强人物选择和读者信息管理，并让普通章节与长章节共享稳定的基础设施。保留创作自由，把工程约束集中在事实边界、恢复能力和真正破坏阅读理解的硬伤上。
