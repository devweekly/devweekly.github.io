# Semantic View 漂移检测与 Git 发布工作流

本文把“发现漂移并放入 Git”落实为可重复执行的工程流程。目标是持续回答四个问题：Git 中批准的定义是什么；Snowflake 当前实际是什么；差异影响哪些语义元素和业务指标；怎样安全修复、验证、发布或回滚。

Git 是批准的变更历史与期望状态的存储位置，不是 Snowflake 实际状态的替代品。只把 YAML 提交到 Git、只比较文件 diff，或只成功执行 verify-only，都不能证明已部署环境与仓库一致。

## 1. 漂移类型与检测范围

| 漂移类型 | 比较对象 | 常见原因 | 风险 | 推荐处理 |
|---|---|---|---|---|
| 源表结构漂移 | 已批准的元数据基线 vs 当前 Snowflake 表列/类型 | 列删除、重命名、类型修改、新增列、对象迁移 | YAML 表达式失效或含义变化 | 重新导出元数据、分析依赖、更新 mapping、重新生成与验证 |
| Semantic View 定义漂移 | Git 中已批准 YAML vs Snowflake 已部署定义 | 控制台手工修改、绕过 CI 部署、部署到错误版本 | 实际语义与评审结果不一致 | 导出当前定义并做语义 diff；决定保留、回收或正式纳入 Git |
| 发布版本漂移 | Git 期望 commit/版本 vs 各环境部署记录 | 部署遗漏、部署错环境、部分发布失败 | Dev/UAT/Prod 行为不同 | 比较版本标识和部署记录，按发布流程补齐或回滚 |
| 依赖漂移 | mapping/YAML 依赖 vs 当前数据库对象 | 表替换、视图定义变化、关系键变化 | 查询可运行但结果变化 | 依赖图分析、关系/粒度检查、结果回归 |
| 业务语义漂移 | 已批准指标定义/known-answer 结果 vs 当前查询结果 | 上游规则变化、单位/币种转换变化、过滤条件变化 | 数字变化但语法验证仍通过 | 业务 owner 评审、独立 SQL 对账和黄金问题回归 |
| 权限/安全漂移 | 已批准角色与策略基线 vs 实际 grants/policies | 手工授权、角色继承变化、策略解绑 | 数据暴露或查询范围变化 | 独立安全检查；不能依赖语义层描述或 Prompt |
| 测试覆盖漂移 | mapping 要求的测试 vs 仓库实际测试 | 新增指标但未加回归、测试被删除/跳过 | 发布门禁失去保护 | CI 检查必需测试映射；缺失时失败或阻断发布 |

新增列通常是提示而非自动失败：若 Semantic View 不依赖该列，可记录并评估；被引用列删除/改名、类型不兼容、关系键或粒度变化应默认视为高风险。不能仅凭列名推断业务含义。

## 2. Git 中应该保存什么

建议把以下可审查、可复现的制品纳入版本控制：

- 业务设计 Markdown：粒度、指标公式、单位/币种、时间规则、空值规则、关系预期、排除项和业务 owner。
- semantic_mapping.json：业务概念到物理对象、字段、YAML 路径、证据、审批状态和测试的映射。
- Semantic View YAML：期望部署定义。人工修复应先更新设计/mapping，再重新生成或审查 YAML。
- 元数据基线：可提交脱敏、只包含元数据的 schema snapshot，标注环境、数据库/schema、导出时间和来源 commit。若组织不允许提交环境元数据，则提交可重放的导出配置与基线摘要，并将完整快照存于受控制品存储。
- 依赖清单：源表、字段、关系键、逻辑表、UDF、其他视图和策略依赖，以及无法静态解析的部分。
- 测试资产：本地结构检查、mapping 检查、关系/粒度测试、known-answer queries、独立参考 SQL、烟雾测试和预期结果。
- 验证报告：门禁命令、结果、时间、工具版本、目标环境标识和失败原因；不得包含凭据或业务行数据。
- 发布清单：Git commit SHA、Semantic View 完全限定名称、环境、verify-only 结果、部署时间、审批人、回归结果及回滚版本。

不要把 .work 临时目录、凭据、客户级数据或无法解释来源的快照直接提交。需要入库的基线应有明确文件名、生成命令和审查规则。建议目录组织如下；可按现有约定调整，但必须确定唯一权威路径，避免同一份定义在多个位置独立演进。

    temp/snowflake-semantic-view/
      design/
        position_analytics.md
      mappings/
        position_analytics.mapping.json
      baselines/
        dev/
          source_metadata.json
          deployed_semantic_view.yaml
      tests/
        known_answers/
        reference_sql/
      reports/
      position_analytics.yaml
      scripts/

## 3. 建立初始基线（首次执行）

首次启用漂移检测时，不能直接把当前 Snowflake 状态当成批准基线。

1. **确认环境和对象身份。** 明确 Snowflake account/region、database、schema、role、warehouse、Semantic View 完全限定名称。使用只读/最小权限身份读取；记录环境标识，不记录凭据。
2. **拉取当前 Git 版本。** 记录 commit SHA 和工作区是否干净。存在未提交变更时，先明确是否纳入本次基线，不能把不确定状态标成已批准。
3. **导出源表元数据。** 对设计中的每张源表运行 scripts/export_semantic_metadata.py，保存临时快照；核对目标环境和导出时间。任何对象读取失败都要明确列出，不能把不完整快照作为完整基线。
4. **读取已部署 Semantic View 定义。** 使用目标 Snowflake 版本支持的官方读取能力，例如官方文档中的 SYSTEM$READ_YAML_FROM_SEMANTIC_VIEW（先确认函数签名和账号支持），或采用经过验证的受控导出方式。保存原始定义作为审计证据，再生成比较用规范化副本。不要假定导出格式、排序或注释与仓库 YAML 完全相同。
5. **建立依赖清单。** 将 YAML 中的 base tables、逻辑表、关系、主键、维度、事实、指标和过滤器，与真实源表列及 mapping 对齐。记录无法静态解析的表达式、动态 SQL、UDF 和策略依赖。
6. **执行本地与服务端验证。** 运行 YAML 结构检查、mapping 检查，再执行 verify-only；在隔离开发环境部署后运行烟雾测试、关系/粒度测试和已批准参考 SQL。
7. **进行业务对账。** 选择关键指标、日期边界、空值、重复键、多事实表 join、跨日期持仓等代表性场景。将 Semantic View 查询与独立可信 SQL 对账，由业务 owner 确认口径。
8. **审查并提交基线。** PR 至少审查设计、mapping、YAML、元数据基线/摘要、测试和风险。基线提交后记录 commit SHA 与实际部署对象版本。未完成对账或审批的对象标记为“未建立可信基线”，不能宣称漂移检测已启用。

## 4. 每次 PR 的检测步骤

每个影响设计、mapping、YAML、SQL 测试、元数据导出脚本或发布配置的 PR，都按以下顺序执行。

### 4.1 静态检查（不需要 Snowflake 连接）

1. 检查 JSON/YAML 格式、必需字段、重复名称和未解析引用。
2. 运行 scripts/validate_semantic_view_yaml.py <yaml-path>。
3. 运行 scripts/validate_semantic_mapping.py --mapping <mapping-path> --metadata <snapshot-path> --yaml <yaml-path>。
4. 对比 PR 前后的依赖清单，列出新增、删除、重命名候选和类型变化的表列、关系键、逻辑表、指标及过滤器。
5. 检查 mapping 中每个关键指标是否关联已存在的测试；测试被删除或未执行时不能静默通过。
6. 对当前脚本未覆盖的表达式级列引用明确报告“未验证”。基础表存在性检查不能包装成完整依赖验证。

### 4.2 连接 Snowflake 的验证（需要受控凭据）

1. 连接 PR 指定的非生产环境，先核验当前 account、role、database、schema 与预期值；不匹配立即停止。
2. 重新导出当前元数据，不复用过期快照作为实时检查结果。
3. 比较当前元数据与 Git 基线。每个差异都列出对象、变化前后、受影响的 YAML 路径/指标、严重级别、证据和建议。
4. 对候选 YAML 执行 Snowflake verify-only。它验证服务端可接受性，不证明查询结果业务正确。
5. 仅在明确授权后部署到隔离开发环境。生产环境不应由 PR 检查自动部署。
6. 执行 SQL smoke tests、关键指标独立 SQL 对账和黄金业务问题回归；保存测试报告及 Git commit SHA。
7. PR 通过门禁的条件是所有必需检查 PASS，或经授权对非阻断项作出有记录的例外。NOT RUN 不能被转换为 PASS。

若 CI 无法访问 Snowflake，可把静态检查设为必需门禁，并通过受控部署流水线或定时任务完成实时漂移检测；必须明确合并前没有实时环境证据。

## 5. 部署后与定时漂移检测

PR 检查不能发现合并后有人在 Snowflake 控制台手工修改对象的情况，因此还需要部署后核对和定时检测。

### 部署后核对

1. 发布流水线记录候选 Git commit SHA、目标环境、Semantic View 名称和发布批次 ID。
2. verify-only 通过后部署到目标环境。
3. 重新读取已部署对象定义，规范化后与该 commit 中的 YAML 比较。
4. 对比对象依赖和元数据版本，运行关键 smoke tests 与 known-answer 回归。
5. 只有定义比较与回归均通过，才把环境发布记录标记为成功。部署 API 返回成功但读回定义不一致时，判定失败并排查。

### 定时检测（例如每日或每次上游 schema release 后）

1. 使用专门的只读服务身份连接每个受监控环境。
2. 验证身份与环境，导出源表元数据和已部署 Semantic View 定义。
3. 与该环境最后一次批准的 Git 发布基线比较，而不是简单地与仓库当前 HEAD 比较；HEAD 可能包含尚未发布的候选版本。
4. 保存差异报告：检测时间、环境、期望 commit、当前对象版本、差异类型、影响对象、严重级别和处理状态。
5. 发现阻断级漂移时通知负责人，阻止对象继续晋级或标记环境不合规；不要自动把生产上的未知变化写回 Git。
6. 新增无关列等非阻断差异可登记待评估事项；只有确认是期望变更后才更新基线。
7. 保留报告和审计记录，避免将完整敏感元数据写入公开日志。

必须区分“上游 schema 有变化”和“Semantic View 实际受影响”。新增无关列不一定需要修改 YAML；被引用列删除/改名、类型变化、关系键或粒度改变必须执行依赖分析和回归。

## 6. 如何规范化后比较 YAML

Snowflake 导出的定义和仓库 YAML 可能在键顺序、格式、默认值或注释上不同。原始文本 hash 不适合单独作为漂移判据。

- **原始快照层：** 保存原始导出供审计；hash 只能证明文件是否完全相同，不直接代表语义等价。
- **规范化语义层：** 解析 YAML 后，将明确不影响语义的键顺序/格式差异规范化，再比较名称、基础表、逻辑表、关系、主键、维度、事实、指标表达式、过滤器、描述/同义词及相关设置。

不要随意删除描述、同义词或过滤器来“消除噪音”，因为它们可能影响检索和查询行为。未知字段应保留并报告，不能在规范化时丢弃。规范化器必须有单元测试，覆盖键顺序变化、空值/默认值、未知字段和表达式字符串。无法可靠规范化的差异标记为需要人工审查。

## 7. 差异严重级别与处置规则

| 级别 | 示例 | 默认动作 |
|---|---|---|
| BLOCKER | 被引用的表/列不存在；mapping 未批准；对象部署到错误环境；关键指标结果不一致；权限策略意外变化 | 阻止部署/晋级；修复后重跑受影响门禁 |
| HIGH | 列类型不兼容；连接键或粒度改变；线上定义与批准版本不一致；关键测试缺失 | 阻止晋级，要求数据工程师/业务 owner 评审 |
| MEDIUM | 新增未使用列；非关键描述或同义词变化；非关键对象版本不同 | 评估影响并登记处置 |
| LOW | 纯格式差异或可证明不影响语义的序列化变化 | 记录规范化结果，不触发不必要的重新部署 |

严重级别不能只由 LLM 判断。可机械确定的差异由脚本分类；业务影响由 mapping 和依赖关系辅助；无法判断的差异升级人工审查。

## 8. 发现漂移后的处理流程

发现差异后不要自动覆盖任何一边。

1. **冻结证据：** 保存 Git commit、环境标识、原始导出、元数据快照、时间和脱敏日志。
2. **分类：** 确定是源表 schema、Semantic View 定义、部署版本、依赖、业务结果还是安全策略漂移。
3. **确定权威来源：** 业务定义以经批准的设计/mapping 为准；期望部署定义以经审查的 Git commit 为准；实际运行状态以 Snowflake 读回结果和查询测试为证据。生产手工修改不自动成为权威。
4. **分析影响：** 从变化的表/列/关系键追踪到 YAML 路径、指标、known-answer 查询和下游消费者；检查粒度、join fan-out、空值、币种、时间规则和权限。
5. **选择修复路径：**
   - 变更有意且已批准：先更新设计和 mapping，再生成 YAML、更新测试并提交 PR。
   - 上游发生未计划的兼容性变更：与源表 owner 协调，恢复兼容接口或按变更流程更新模型。
   - Snowflake 被未经批准地修改：比较实际定义与 Git 期望；确认后从批准 commit 重新部署，或先让合法修改走 PR 纳入版本控制；禁止无审查覆盖。
   - 业务结果变化但结构未变：暂停晋级，检查数据分布、转换逻辑、参考 SQL 与口径审批。
6. **重新验证：** 从受影响的最早门禁开始运行，不要只重跑最后一个部署步骤。重新导出元数据后执行静态检查、verify-only、开发部署、结构/关系测试和 known-answer 对账。
7. **发布或回滚：** 发布只引用经过审批的 commit；回滚到上一个已知良好的 Git commit/部署制品，并重新运行验证。回滚语义定义不一定能回滚上游数据或表结构，因此数据层变更需要独立的兼容/恢复计划。
8. **关闭事件：** 记录根因、影响范围、修复 commit、测试证据、部署版本、审批人及新增检测规则。

## 9. 最小实现路线

避免一开始就建造复杂平台，按以下顺序增量实施。

**M1 — Git 基线与静态门禁**
- 明确设计、mapping、YAML、测试的权威路径。
- PR 中运行 JSON/YAML 解析、现有脚本检查和测试文件存在性检查。
- 保存 mapping 到源表列的依赖清单；表达式解析能力不足处明确标记覆盖缺口。

**M2 — 元数据 schema drift**
- 扩展元数据导出，纳入环境标识、时间戳和必要的类型信息。
- 新增确定性的 metadata diff 脚本，输出新增/删除/改名候选/类型变化。
- 改名候选只能提示人工确认，不能把“旧列消失 + 新列出现”自动判为同一列。
- 将差异映射到受影响语义元素和测试。

**M3 — 已部署定义 drift**
- 通过官方受支持的读取方式导出已部署 Semantic View。
- 新增 YAML 解析/规范化与语义 diff，保留未知字段。
- 记录每个环境最后批准部署的 commit SHA，比较环境当前状态与该环境发布基线。

**M4 — 结果与安全 drift**
- 建立关键指标的 known-answer/独立 SQL 回归。
- 对关系基数、重复键、行数膨胀、半可加指标、日期边界和空值增加测试。
- 权限、Row Access Policy、Masking Policy 等使用单独的审计/策略检查，不以 Semantic View YAML diff 代替。

**M5 — 发布闭环**
- 将 verify-only、隔离开发部署、回归、审批、生产晋级和回滚记录连成流水线。
- 定时检查已部署环境，告警并创建可追踪的修复任务。
- 对每次发布保留“commit → 验证报告 → 部署对象 → 回归结果”的完整关联。

每个阶段都应提供脚本、输入/输出 schema、fixture 测试、失败案例和清晰的 NOT RUN 语义。只有文档步骤、没有可执行检测器时，不能声称漂移检测已自动化。

## 10. 最终发布门禁

- [ ] 设计与 mapping 已由对应 owner 批准。
- [ ] 元数据来自目标环境，时间和环境身份已核对。
- [ ] 物理引用与表达式依赖检查通过，未覆盖项已显式审查。
- [ ] YAML 结构检查与 Snowflake verify-only 通过。
- [ ] 关系基数、事实粒度、fan-out 和关键数据质量测试通过。
- [ ] 关键指标与独立参考 SQL/known-answer 结果一致。
- [ ] 当前部署定义与批准 commit 一致，或差异已有正式审批。
- [ ] 权限和安全策略已独立验证。
- [ ] 发布、回滚版本、验证报告和审批记录可追溯。

若任何必需项为 FAIL 或 NOT RUN，不得报告“漂移检查通过”；必须说明实际覆盖范围和缺失证据。
