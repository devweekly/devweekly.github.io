# 业务需求访谈与知识获取工作手册

## 1. 目的与原则

本手册用于与 Business Partner、Business Analyst、业务运营人员、产品负责人和 Subject Matter Expert（SME）开会，系统获取业务需求与隐性业务知识。适用于数据分析、指标定义、报表改造、Semantic View 建模、AI Agent 和数据产品项目。

核心原则：**让业务人员讲业务场景和真实案例，不要求他们设计技术方案。** 访谈者负责追问、归纳、记录和验证；技术团队之后再把已确认的业务定义映射到数据模型、SQL、Semantic View 或应用实现。

会议不是单纯收集字段清单，也不是让参会者现场设计数据库。需要同时理解业务目的、使用者、术语、指标、粒度、时间口径、规则、例外、决策和验收方式。

## 2. 会议结束时必须拿到什么

至少形成以下产出；暂时无法确认的内容必须记录为待确认事项，不得用猜测补齐。

1. **业务目标与决策场景**：要解决的问题、使用者、使用频率、结果将影响什么决策。
2. **业务术语表**：术语、业务定义、同义词、容易混淆的概念、业务 owner。
3. **指标清单**：指标名称、定义、计算逻辑、单位、币种、正负号、聚合方式、适用范围和负责人。
4. **分析维度与粒度**：业务上每条记录代表什么，用户通常按哪些维度查看或比较。
5. **时间规则**：事件发生时间、入账时间、估值时间、报告日期、时区、截止时间、历史重述规则。
6. **业务规则与例外**：筛选条件、状态、排除项、边界条件、缺失数据处理和例外流程。
7. **真实案例与预期结果**：至少一个正常案例；重要指标还应包含边界、异常或争议案例。
8. **数据来源线索**：业务人员目前从哪里得到数字、使用哪些报表或系统、谁维护这些数据。不要要求业务人员准确提供物理表名。
9. **验收标准**：业务如何判断结果正确、允许的差异、必须通过的场景。
10. **决策与未决事项**：已确认的决定、待确认问题、责任人和截止日期。

## 3. 会前准备

### 3.1 明确会议范围

会前用一两句话写明要讨论的业务问题，例如：“了解组合市值和持仓集中度的业务定义、估值日期规则以及业务人员如何核对结果。”

不要把范围写成技术任务，例如“讨论 Semantic View YAML 字段”。技术对象应由技术团队内部处理。

### 3.2 邀请合适的参与者

根据主题邀请：
- **Business Partner / 业务负责人**：解释目标、优先级和决策用途。
- **Business Analyst**：解释现有流程、业务规则、用户需求和验收标准。
- **SME / 一线操作人员**：提供实际操作、例外和边界案例。
- **报表或数据使用者**：解释现有数字如何被使用、核对和质疑。
- **技术人员**：倾听并在必要时澄清数据可行性，但不要过早把讨论带入实现细节。

一个人可能承担多个角色。若指标口径存在争议，应确认谁有权作最终业务决定，而不是以参会人数投票。

### 3.3 请业务方带来材料

优先请求真实、已脱敏的材料：
- 当前使用的报表、Excel、业务说明或操作手册；
- 指标定义、政策文件或计算说明；
- 一两个已知正确的案例及其预期结果；
- 一个曾经引发争议或需要人工调整的案例；
- 常见的筛选条件、报告日期和下游使用方式。

若没有正式文档，不要把它视为没有规则；可以让业务人员演示平时如何完成任务，并逐步追问。

## 4. 建议会议议程（60 分钟）

| 时间 | 环节 | 目标 |
|---|---|---|
| 0–5 分钟 | 说明目标与范围 | 让参会者知道要解决什么问题，以及本次不讨论什么 |
| 5–15 分钟 | 业务流程与决策 | 理解谁在何时使用结果、要做什么决定 |
| 15–30 分钟 | 术语与指标 | 逐个确认重要概念、定义和计算口径 |
| 30–40 分钟 | 时间、粒度与业务规则 | 挖掘默认假设、边界和例外 |
| 40–50 分钟 | 真实案例走查 | 用实际数字验证理解，而不是只记录口头定义 |
| 50–57 分钟 | 复述与确认 | 由访谈者用自己的话总结，请业务方纠正 |
| 57–60 分钟 | 未决事项与后续 | 指定问题负责人、所需证据和完成日期 |

若讨论范围较大，应拆成多场会议。不要为了在一小时内完成而跳过案例验证。

## 5. 访谈问题：按顺序由业务目标深入到规则

不必逐字照读所有问题。根据对方回答继续追问；遇到抽象表述时，始终回到最近一次真实业务案例。

### 5.1 业务目标与使用方式

先理解为什么需要这些信息。

- 你通常在什么情况下需要回答这个问题？
- 谁会使用结果？是日常运营、管理报告、客户沟通、风险判断还是其他用途？
- 看到这个数字后，你会采取什么行动或做出什么决定？
- 现在通过什么方式获得答案？要经过哪些步骤？
- 目前最耗时、最容易出错或最常引发争议的地方是什么？
- 多久使用一次？对结果的时效性有什么要求？
- 如果结果错了，可能造成什么后果？哪些错误最不能接受？
- 这次需求解决后，怎样才算真正有价值？

追问提示：业务方说“我想看表现”时，继续问“具体用哪个数字判断表现？与什么比较？结果会改变什么行动？”

### 5.2 业务术语与概念

目标是避免同一个词在不同团队中含义不同，或不同词实际指同一概念。

- 你提到的“净敞口”“市值”“活跃客户”等词，具体指什么？
- 在你们的工作中，这个词是否有正式定义？
- 有没有其他团队使用不同的名称或定义？
- 哪些概念听起来相似，但不能混为一谈？
- 这个概念是否有包含项和排除项？
- 哪份政策、报告或业务负责人可以作为权威依据？
- 如果两个系统给出的定义不同，业务上以哪个为准？由谁决定？

记录时要区分：业务定义、常用别名、来源证据和待确认的歧义。不要仅仅记录一个词及其技术字段名。

### 5.3 指标定义与计算口径

每个关键指标都要单独走查。

- 这个指标在业务上是什么意思？请用自己的话解释。
- 你会怎样手工计算或核对它？
- 分子、分母、组成部分和排除项分别是什么？
- 这个数是金额、数量、比例、比率还是状态？
- 如果是金额，使用什么币种？是否需要换算？使用什么汇率口径？
- 正数和负数各代表什么？
- 这个指标可以相加吗？可以取平均值吗？如果可以，在哪些条件下？
- 按产品、组合、地区、客户或日期拆分时，定义是否改变？
- 是否存在最低门槛、阈值、封顶、舍入或精度规则？
- 哪个现有报表或案例可以证明计算结果正确？
- 如果不同报表的数字不一致，通常如何排查？

特别追问：
- **总量与比率**：比率通常不能直接求和；汇总时是否应重新计算分子和分母？
- **时点与期间**：期末持仓是某一时点的状态，不等于期间累计流量。
- **平均值**：是简单平均还是加权平均？权重是什么？
- **去重**：按什么业务实体去重？同一实体出现多次时保留哪条？
- **净额与总额**：是否抵销、净额化或扣除某些项目？
- **缺失值与零值**：没有数据、未知、不适用和数值为零是否代表不同意思？

不要满足于“按标准公式计算”。请对方指出标准的名称、版本或实际案例；如果现场无法提供，记录为待确认。

### 5.4 粒度与分析维度

业务人员通常不会说“数据粒度”，访谈者需要用具体例子帮助他们说明。

- 一条记录在业务上代表什么？一笔交易、一项持仓、一个客户一天的状态，还是一份月度报告？
- 同一对象一天内可能出现多条记录吗？为什么？
- 通常需要按哪些类别查看、比较或汇总？
- 能否同时按组合、证券和估值日期查看？
- 一个业务对象可能属于多个类别吗？
- 按某个维度汇总后，是否可能重复计算？
- 哪些维度是必需的，哪些只是方便筛选？
- 是否需要查看历史状态，而不仅是当前状态？

如果业务方无法抽象回答，让对方拿一份真实报表指出一行、一列和一个汇总数字分别代表什么。

### 5.5 时间与历史规则

时间问题是很多“数字看起来正确、业务上却错误”的根源。

- 报告上的日期指事件发生日、处理日、入账日、估值日，还是数据提取日？
- 使用哪个时区？一天的业务截止时间是什么？
- 周末、节假日或数据延迟时，采用什么规则？
- 当前数据会被后续更正吗？历史报告是否随之变化？
- 需要查询当时已知的信息，还是使用最新修正后的信息？
- 比较前一天、上月末或去年同期时，日期如何选取？
- 如果一个业务对象在期间内更改分类或状态，历史查询按当时状态还是当前状态？
- 期间开始和结束日期是否包含在查询范围内？

对金融数据，应明确估值时点、交易日期、结算日期、报告日期和汇率日期是否不同；不能仅凭字段名推断。

### 5.6 业务规则、状态和例外情况

先问正常流程，再问“不正常时怎么办”。

- 正常情况下，这个流程如何完成？
- 哪些记录应该被纳入？哪些必须排除？
- 不同状态（例如待处理、已确认、已撤销）如何处理？
- 撤销、重做、重复、迟到或更正的数据怎么处理？
- 某些字段缺失、无效或互相矛盾时怎么办？
- 是否存在手工覆盖或例外审批？由谁批准？
- 规则是否因产品、地区、客户类型或业务日期而异？
- 有没有“虽然不常见，但发生时必须正确处理”的情况？
- 哪些规则来自正式政策，哪些只是团队惯例？

追问“如果……会怎样？”例如：“如果交易在月底后才入账，但业务日期属于月底，应该归到哪个期间？”这类问题能揭示未写进文档的隐性规则。

### 5.7 来源、核对与信任

不要要求业务人员设计物理数据模型，而是了解他们信任哪些业务证据。

- 你目前从哪个系统、报表或文件取得这个数字？
- 哪个来源是正式或权威来源？是否存在临时替代来源？
- 这个数字由哪个团队维护？
- 你平时用什么方法检查数字是否合理？
- 有哪些常见的人工调整？调整依据在哪里记录？
- 哪些情况下你会不相信结果，进而找谁核实？
- 有没有一个已知正确的样例，可以用于今后验证？
- 如果两个来源冲突，采用什么优先顺序？

数据工程师之后负责将业务来源映射到具体表、列和数据管道。不要让业务人员猜测底层数据库字段。

### 5.8 权限、敏感性和使用边界

- 哪些角色可以查看这些信息？
- 是否有客户、账户、交易对手或员工数据等敏感内容？
- 不同角色看到的内容是否不同？
- 哪些信息可以汇总展示，哪些不允许导出或进一步拆分？
- 结果是否会用于客户决策、监管报告或其他受控用途？
- 是否需要保留查询依据、审批记录或报告版本？

业务访谈提供业务限制线索，最终权限和合规要求仍需由数据所有者、安全和合规负责人确认。

### 5.9 验收标准与优先级

- 交付后，你会怎样判断结果正确？
- 哪几个问题必须先做到，哪些可以后续再做？
- 对哪些案例必须得到精确结果？哪些允许一定误差？
- 能否提供期望结果或已经核准的参考报告？
- 结果延迟多久仍可接受？
- 哪些错误必须阻止发布？
- 谁拥有最终业务验收权？

尽量把“准确、快速、方便”等抽象要求转化为可检查的标准。例如：“对给定组合和估值日，市值应与已核准的参考报告一致；差异超过约定阈值时必须解释并得到批准。”

## 6. 用真实案例验证：不要只收集口头描述

至少选择一个正常案例和一个边界或异常案例。由业务人员说明输入、处理过程和预期结果，访谈者复述后请其确认。

建议按下面的模板逐项填写：

| 项目 | 要记录的内容 |
|---|---|
| 业务问题 | 这个案例要回答什么问题？ |
| 输入条件 | 日期、业务对象、筛选范围、状态等 |
| 业务规则 | 使用哪些定义、计算方法和排除规则？ |
| 预期结果 | 业务人员认为正确的数字或结论 |
| 核对依据 | 正式报表、政策、人工计算或业务审批记录 |
| 边界情况 | 更正、缺失、重复、跨期、特殊状态等 |
| 确认人 | 谁确认规则，谁确认结果？ |
| 状态 | 已确认、待补证据、有争议 |

案例走查要继续追问：“为什么这个结果是对的？”如果答案只是“系统一直这样显示”，还没有获得足够的业务依据。

## 8. 如何处理模糊答案和意见冲突

业务人员的第一种说法通常只是起点，不一定是完整定义。

当对方说“通常这样处理”时，追问“什么情况下不这样处理？”；说“按标准口径”时，追问“标准在哪里，谁维护？”；说“和现有报表一致”时，追问“具体哪份报表、哪个日期、哪组数据？”；说“应该是这样”时，记录为假设，不要当成已确认规则。

如果两个业务方给出不同定义：
1. 先记录双方的原始说法和适用场景，不急于判断谁对。
2. 用具体案例确认差异是否来自日期、范围、状态、币种、粒度或业务目的不同。
3. 找到正式政策、业务控制文件或有决策权的 Owner。
4. 如果实际存在多个合法口径，为它们分别命名并说明适用场景；不要强行合并成一个指标。
5. 未获得授权决定前，标记为待确认，不要让技术团队自行选择业务答案。

## 9. 会后整理与确认流程

会后尽快完成以下步骤：

1. 整理会议记录，区分**已确认事实、业务假设、访谈者推断和待确认问题**。
2. 将关键术语和指标整理成业务词汇表与指标定义表。
3. 把口头规则转化为可检查的条件，并附上支持它的案例或业务依据。
4. 为每个未决问题指定负责人、所需材料和截止日期。
5. 将会议摘要和关键定义发给参与者确认，明确回复期限。
6. 根据反馈修订文档，记录变更及确认人。
7. 只有在关键定义和高风险歧义得到解决后，才进入相应的技术建模与实现；低风险待办可按约定保留，但必须明确标注。

建议把业务定义、案例和确认状态纳入版本管理。技术团队可以在后续阶段把已确认的业务概念映射到物理字段、Semantic View、SQL 和自动化测试，但不能将技术映射反过来当作业务定义的唯一证据。

## 10. 面向 Semantic View 项目的特别提醒

Semantic View 建模之前，重点确认：

- 指标的业务定义和权威 Owner；
- 事实记录的业务粒度；
- 指标能否相加、求平均或跨维度汇总；
- 时间、估值日、币种、汇率和历史更正规则；
- 业务术语、同义词和容易混淆的概念；
- 关系背后的业务含义及可能的重复计数；
- 可用于验证的已核准问题与预期结果；
- 不同角色的可见范围和合规限制。

不要在访谈中要求业务人员提供 YAML、表名、字段名、JOIN 条件或 SQL。业务方确认的是“业务上是什么、为什么、何时适用、什么结果才算正确”；数据工程师和架构师负责确认“现有数据是否支持、如何映射、如何计算和如何测试”。

**最终质量标准：** 一个没有参加会议的工程师，读完已确认的访谈记录后，应能理解业务问题、准确解释关键指标、识别主要例外，并知道如何验证实现结果；如果仍需要依靠访谈者的记忆才能理解，说明记录还不完整。
