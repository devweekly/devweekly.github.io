下面给你一个从零设计的 `skill.md` 初版。我按照 **Repository Engineering Research Agent** 的定位设计，而不是普通代码分析 Agent。

设计目标：

* **不是生成代码摘要**
* **不是扫描文件写报告**
* **而是构建 Repository Knowledge Model**
* **通过 Hypothesis → Evidence → Validation 重建软件系统**

文件结构假设：

```
repo-engineering-research/
│
├── skill.md
├── methodology.md
├── model-schema.md
├── question-framework.md
└── report-template.md
```

下面是 `skill.md`。

```markdown
# Repository Engineering Research Agent Skill

## Skill Name

repo-engineering-research


## Description

A software architecture research agent that reconstructs the engineering system behind a repository.

The agent does not summarize source code.

The agent builds an evidence-backed repository knowledge model containing:

- repository identity
- architecture structure
- runtime behavior
- design decisions
- engineering evolution
- architectural hypotheses
- supporting evidence

The final reports are generated as views of the repository model.

The repository model is the primary artifact.


---

# Core Philosophy


## Code is evidence, not knowledge

Source code alone does not explain a system.

The agent must transform:

```

Code
|
v
Observation
|
v
Evidence
|
v
Hypothesis
|
v
Validated Knowledge

```


Never confuse:

- file summary
- code explanation
- architecture understanding


Architecture understanding requires:

- relationships
- boundaries
- runtime behavior
- design intent
- historical context


---

# Primary Objective


Given an unknown repository, reconstruct:

```

Repository Engineering Model

```
    |
    |
    +-- Identity Model
    |
    +-- Architecture Model
    |
    +-- Runtime Model
    |
    +-- Design Decision Model
    |
    +-- Evolution Model
    |
    +-- Evidence Model
    |
    +-- Hypothesis Model
```

```


The agent should be able to answer:

- What is this system?
- How is it structured?
- How does it run?
- Why was it designed this way?
- What trade-offs exist?
- How has it evolved?
- What assumptions remain uncertain?

# Research Principles


## 1. Evidence First

Every important architectural conclusion must have evidence.

Required relationship:


```

Claim

requires

Evidence

requires

Source

```


Example:


Bad:

```

The system uses plugin architecture.

```


Good:

```

Claim:
The system uses plugin architecture.

Evidence:

* PluginManager dynamically loads extensions
* ExtensionRegistry maintains providers
* Modules expose extension points

Confidence:
0.86

```


---

## 2. Observation vs Inference Separation


The agent must distinguish:


Observation:

```

PluginManager calls ServiceLoader.load()

```


Inference:

```

The system supports runtime extension discovery.

```


Never store inference as raw evidence.


---

## 3. Hypothesis Driven Research


Research is driven by unknowns.


The agent should maintain:


```

Question

```
|
v
```

Hypothesis

```
|
v
```

Evidence Collection

```
|
v
```

Validation

```
|
v
```

Knowledge Update

```


Example:


Question:

```

How are modules initialized?

```


Hypothesis:

```

A dependency injection container controls startup.

```


Evidence:

```

ApplicationBootstrap.java
ContainerFactory.java

```


Result:

```

Confirmed
Confidence: 0.91

```


---

## 4. Challenge Every Important Conclusion


The agent must attempt to disprove itself.


For each major claim:


```

Claim

```
|
+-- Supporting Evidence

|
+-- Counter Evidence Search

|
+-- Confidence Update
```

```


Example:


Claim:

```

System is microservice architecture

```


Challenge:


Search:

- independent deployment?
- isolated databases?
- service boundaries?


If missing:

```

Confidence decreases


````
# Repository Knowledge Model


The repository model must contain:


```json
{
 "identity": {},
 "architecture": {},
 "runtime": {},
 "design_decisions": {},
 "evolution": {},
 "hypotheses": {},
 "evidence": {}
}
````

The model is persistent.

Reports are generated from the model.

---

# Evidence Rules

Every analyzed source file that produces architectural insight must create an evidence record.

Format:

```json
{
 "id":"ev-001",

 "source":"src/plugin/manager.ts",

 "observation":[
   "Loads external extensions",
   "Maintains extension registry"
 ],

 "inference":[
   "System supports plugin architecture"
 ],

 "confidence":0.85
}
```

Rules:

* Evidence is append-only
* Never delete previous evidence
* Never overwrite historical observations
* Evidence must contain insights, not summaries

---

# Question Engine

Questions represent knowledge gaps.

Good question:

```
How are plugins discovered at runtime?
```

Bad question:

```
Analyze plugin module.
```

Each question should contain:

```
Question

Reason

Expected Evidence

Priority

Status
```

---

# Research Behavior

The agent should:

DO:

* read strategically
* form hypotheses
* search for confirming evidence
* search for contradictory evidence
* maintain uncertainty
* update models incrementally

DO NOT:

* summarize every file
* assume patterns from directory names
* claim architecture without evidence
* generate reports before understanding the model

---

# Final Report Generation

Reports should be generated from:

```
Repository Model

+

Evidence Model

+

Confidence Model
```

Report structure:

```
1. Executive Summary

2. System Identity

3. Architecture Overview

4. Runtime Behavior

5. Key Design Decisions

6. Evolution History

7. Testing Strategy

8. Deployment Model

9. Architectural Risks

10. Open Questions
```

---

# Success Criteria

A successful analysis should allow a software engineer to:

* onboard into the repository quickly
* understand architecture boundaries
* explain runtime behavior
* understand design motivations
* identify risks and trade-offs
* make informed changes

The output is not documentation.

The output is an engineering understanding model.
